---
title: "agentx serve"
description: "Keep watching and report whenever something changes."
---

`agentx serve` is what the desktop app runs in the background. It scans the machine once, then rescans whenever anything it inventories changes, and reports again only when the inventory changed. It also checks your skills for updates. You rarely need to run it yourself.

## What serve repairs at start

When serve starts, before its first snapshot, it checks every skill against what is on disk and reports one line for every skill that is not `restored`:

```text
reconcile beta: modified
reconcile release-notes: repaired
snapshot 1: 3 configurations, 6 skills
```

- One of your own skills whose worktree or library symlink went missing is checked out again from its branch: `repaired`. So is one whose Git pointers broke because `~/.agentx` moved.
- One of your own skills that serve cannot put back, because a Git command you ran is waiting in its worktree or the worktree is on another branch, is reported as `worktree missing`. Finish or abort the Git command, or switch the worktree back to its branch, then run [`agentx skill place <name>`](/cli/fork#recover-a-skill-of-your-own).
- A folder in the way of one of your own skills is reported as an `adopt candidate` and left as it is. Adopt it with [`agentx skill place <name> --force`](/cli/fork#something-in-the-way).
- A managed skill you edited is `modified`; one whose folder is gone is `installable`, as is one of your own skills you have not placed on this machine. A skill no source manages is `unmanaged`.

Serve never deletes or overwrites anything to repair it. A skill that is fine is `restored` and prints no line.

## Maintenance

Once a day, serve tidies the account repo in `~/.agentx/account.git` in the background: it packs loose objects and refs with `git maintenance run`. It deletes nothing and never registers a scheduled job with your system.

## What counts as a change

Serve watches agentx itself, the library and every skills directory an agent client reads, including the ones clients keep under their own configuration such as `~/.claude/skills`. An edit inside a skill counts, not only a skill added or removed. Edit a skill with any editor or another tool and the next snapshot shows it. A skill of your own shows as `modified` as soon as you edit it, and as `current` again once you [publish](/cli/skill#publish-a-skill) it with `agentx skill publish`. A commit you make with Git in its worktree does not make it `current`: the edits stay unpublished until you publish them. Serve never publishes or commits for you.

A change outside the inventory, such as a skill in a directory no installed client reads, causes a rescan that prints nothing.

## Run it

```sh
agentx serve
```

```text
snapshot 1: 3 configurations, 5 skills
update pdf: 3f2a9c1 -> 8b1e0f4, 2 files
snapshot 2: 3 configurations, 6 skills
```

Each `snapshot` line means the inventory changed; a change that leaves the inventory as it was prints nothing. Each `update` line is a skill with an update available. Close the process's stdin, or press Ctrl-C, to stop it. Either way serve exits `0`.

The desktop app runs serve with [`--json`](/cli/output#json-output). It then also gets the whole inventory, a notice when a skill changes state, and answers to its own refresh and search requests.

## Update checks

Serve checks your managed skills, your own included, for updates as [`agentx skill check-updates`](/cli/skill#check-for-updates) does: once when it starts, right after the first snapshot, and then every thirty minutes. Each check also fetches every source you added, even the ones you have not installed anything from, as [`agentx source fetch --all`](/cli/source#fetch-a-source-again) would. A machine without any source has nothing to fetch, and serve runs no git for it. With an account remote set, each check also fetches it and reports what your other machines published to your own skills placed here.

A check only records what it found; nothing is ever applied. Every check lists every available update again, so the `update` lines repeat while the update is available. Apply an update with [`agentx skill update`](/cli/skill#update-a-skill).

A source that cannot be fetched, because you are offline or the repository moved, is a warning starting `update check:` that names it and any skills it left unchecked. Serve warns once, not on every check. It warns again only when the reason changes, and it says so on a line of its own when the source can be fetched again:

```text
warning: update check: https://github.com/me/skills: git fetch: fatal: unable to access 'https://github.com/me/skills/': Could not resolve host: github.com; not checked: pdf
info: update check: https://github.com/me/skills can be fetched again
```

The checks in between log the failure as a debug line, which `--verbose` shows, and serve keeps running. A skill whose new version agentx refuses to import, and a source that was fetched but could not be read, are warned about on every check. The other `update check:` warnings say what an update leaves out or renames, or that a whole check failed.

Serve cannot fetch a source that [`agentx import`](/cli/export#import-onto-another-machine) brought back until you add it again. Run `agentx source add <url>` to fetch it, or `agentx source add <url>#<pin>` for a pinned source so that it stays pinned.

Checks run in the background: scans go on while a check waits on the network, and a check still running when the next one is due is not started twice.

To check more or less often, set `AGENTX_CHECK_INTERVAL` to a duration such as `10m` or `2h` before starting serve. Serve refuses to start with exit code 1 when it is not a positive duration.

## Run one pass

```sh
agentx serve --once
```

Scans once, prints the snapshot and exits. It repairs nothing and runs no update check or maintenance. For an inventory to read, run [`agentx scan`](/cli/scan) instead.

## One serve per home

Only one serve runs per agentx home. Starting a second one exits with code 6 and names the lock file, `serve.lock` in agentx home. Stop the running one first.

## When watching is not possible

If a directory cannot be watched, serve exits with code 6 and an error naming the directory and the cause. On Linux this usually means the inotify watch limit is reached; raise `fs.inotify.max_user_watches`. Serve never polls instead.

On macOS the released binary watches through FSEvents, which handles a library of any size. A macOS binary built without cgo watches through kqueue instead, which needs one open file per watched file and reaches the default limit of 256 with a few dozen skills; raise the limit with `ulimit -n`, or use the released binary.

A skills directory that does not exist yet is not watched. Serve picks it up at the next rescan after it appears.
