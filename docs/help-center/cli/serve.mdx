title: "agentx serve"
description: "Keep watching and report whenever something changes."
---

`agentx serve` is what the desktop app runs in the background. It scans the machine once, then rescans when a skill or agentx's own state changes. It reports again only when the inventory changed. It also checks your skills for updates when it starts. You rarely need to run it yourself.

This page uses the terms [agentx home](https://github.com/grundmanise/agentx/blob/main/GLOSSARY.md) (`~/.agentx`) and [store](https://github.com/grundmanise/agentx/blob/main/GLOSSARY.md).

## Run it

```sh
agentx serve
```

```text
inventory 1: 3 configurations, 5 skills
update pdf: 3f2a9c1 -> 8b1e0f4, 2 files
inventory 2: 3 configurations, 5 skills
```

The first `inventory` line is the inventory when serve starts. Each later `inventory` line means the inventory changed. A change that leaves the inventory as it was prints nothing. Each `update` line is a skill with an update available. To stop serve, press Ctrl-C or close its stdin. Serve then exits with code `0`.

The desktop app runs serve with [`--json`](/cli/output#json-output) and talks to it in JSON-RPC 2.0 over its stdin and stdout: it runs its commands through serve, asks for a rescan and searches your sources. The JSON output also carries the whole inventory and a notice each time a skill changes state.

## What counts as a change

Serve watches agentx home (`~/.agentx`), the library and the skills directory of every agent client agentx knows, such as `~/.claude/skills`. It also watches the folders where the Vercel skills CLI and Skillshare record the skills they install. It does not watch the clients' MCP configuration files: a change there shows at the next rescan.

Serve sees a skill added, removed or edited, whatever tool made the change. The next inventory shows it. The inventory also carries this machine, its settings and its sources, so a change such as `agentx config set` or `agentx source add` in a terminal reaches the desktop app too. The inventory lists the skills another tool installed that agentx does not manage, so the desktop app offers to [import](/cli/skill-import) them as soon as that tool records them. A hub skill shows as `modified` as soon as you edit it, and as `current` again once you [publish](/cli/skill#publish-a-skill) it with `agentx skill publish`. A commit you make with Git does not publish your edits. Serve never publishes or commits for you.

## What serve repairs at start

When serve starts, before the first inventory, it repairs your hub skills. If a hub skill's [worktree](/cli/fork#where-your-skills-live) or library symlink is missing or broken, for example after you moved `~/.agentx`, serve checks it out again from its branch. Serve prints no line for this. The first inventory shows the repaired skills.

Serve does not repair a hub skill in these cases. [`agentx skill list`](/cli/skill#list-your-skills) shows a warning for each one that says what to do:

- A Git command you ran in its worktree, such as a merge, is unfinished, or the worktree is on another branch. Finish or abort the Git command, or switch the worktree back to the skill's branch. Then run [`agentx skill place <name>`](/cli/fork#recover-a-hub-skill).
- A folder of yours is where the hub skill belongs. Serve leaves it as it is. Adopt it with [`agentx skill place <name> --force`](/cli/fork#something-in-the-way).

Serve repairs only what is missing or broken. It does not delete or overwrite your files.

## Update checks

When serve starts, it checks your [managed skills](/cli/skill#list-your-skills) for updates once, right after the first inventory, as [`agentx skill check-updates`](/cli/skill#check-for-updates) does. To check again later, run `agentx skill check-updates`. The check runs in the background, so scans go on while it waits on the network.

The check also:

- Fetches every source you added, as [`agentx source fetch --all`](/cli/source#fetch-a-source-again) does, including sources you have not installed from.
- Fetches your hub when a hub skill is placed on this machine, and reports what your other machines published to it.

The check only records what it found, and when it ended. The next inventory carries both together. Apply an update with [`agentx skill update`](/cli/skill#update-a-skill).

While serve runs, it also checks your [hub](/hub) every 10 minutes for what your other machines published. This check is light: it asks the remote which versions it holds, and fetches only when they differ from what this machine last fetched. If the hub cannot be reached, serve warns once and stays quiet until a check succeeds again.

A source that cannot be fetched, because you are offline or the repository moved, is a warning starting `update check:` that names it and any skills it left unchecked:

```text
warning: update check: https://github.com/me/skills: git fetch: fatal: unable to access 'https://github.com/me/skills/': Could not resolve host: github.com; not checked: pdf
```

Serve keeps running. Other `update check:` warnings name a skill or source the check could not check, and say what to do next.

Serve also fetches a source that your settings name and this machine never fetched, for example because an [`agentx snapshot apply`](/cli/snapshot#apply-a-snapshot) stopped before it added it, or because you copied your settings from another machine. It keeps the source's [pin](/cli/source#pin-a-source).

## Maintenance

When serve starts, it tidies the store (`~/.agentx/store.git`) in the background, at most once a day. It deletes nothing.

## Run one pass

```sh
agentx serve --once
```

Serve scans once, prints the inventory and exits. It repairs nothing, watches nothing and runs no update check or maintenance. To read the full inventory, run [`agentx scan`](/cli/scan).

## Answer a browser on this machine

```sh
agentx serve --listen localhost --origin http://localhost:1420
```

```text
listening: ws://127.0.0.1:53124/
token: 4KQZ7MXB...
inventory 1: 3 configurations, 5 skills
```

With `--listen`, serve also answers on a WebSocket, so that a page in a browser on this machine can be its client. It is for the development of agentx. The app does not need it.

- **Address**: pass a loopback address, such as `localhost`, `127.0.0.1` or `[::1]`, with a port if you want a fixed one, such as `localhost:4319`. Without a port, serve takes a free one. Serve refuses any other address, so other machines cannot connect.
- **Token**: serve makes a new token each time it starts and prints it once. A client must present it. Keep it secret: a client that has it can run any agentx command as you.
- **Origin**: pass `--origin` for each web page address that may connect, such as your development server. Without `--origin`, no browser can connect.

A client speaks JSON-RPC 2.0. It can run agentx commands, ask for a rescan and search your sources, and it gets every inventory as serve reports it. The [CLI contract](https://github.com/grundmanise/agentx/blob/main/docs/spec/cli-contract.md#the-websocket-door) describes the protocol.

Keep the terminal open: serve stops when you press Ctrl-C or its stdin closes, and it then stops every command a client started.

## One serve per home

Only one serve runs for each agentx home (`~/.agentx`). A second `agentx serve --once` exits with code 6 and names the lock file, `~/.agentx/serve.lock`. A second `agentx serve` prints the same error and keeps running without scanning, so that the app can still run commands through it. Each `refresh` request tries the lock again. Once the other serve stops, the next `refresh`, or Retry in the app, makes this serve start scanning. If its stdin closes before then, it exits with code 6.

## When watching is not possible

If a directory cannot be watched, serve prints an error naming the directory and the cause, and keeps running. It stops watching, so it rescans only when the app asks it to. On Linux this usually means the inotify watch limit is reached. Raise `fs.inotify.max_user_watches`, then restart serve.

On macOS, use the released binary or the Homebrew build. A binary [built from source](/install#build-from-source) without cgo soon reaches the default open-file limit. Raise it with `ulimit -n`.

Serve cannot watch a skills directory that does not exist yet. When another change causes a rescan, serve finds the new directory and watches it from then on.

## When the first scan fails

If the first scan fails, for example because Git is missing, serve prints the error and keeps running. Fix the cause, such as installing Git. The next change, or a rescan the app asks for, scans again and prints the first inventory.
