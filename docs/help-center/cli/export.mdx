---
title: "agentx export and import"
description: "Copy one machine's settings to another, with a list of the skills to bring back."
---

Export writes your settings and a list of your skills to a file. Import restores the settings on another machine and tells you what that machine can bring back on its own.

An export holds no skill content. It records where each skill came from, never what is in it. Content comes back from your account repo, or from installing the skill again.

## Export this machine

```sh
agentx export ~/agentx-export.json
```

```text
✓ exported the settings and 12 lineage records to ~/agentx-export.json
  the export holds no skill content: the account repo and 'agentx skill add' restore that
```

The file holds:

| Part | What it is |
|---|---|
| `settings` | Your [settings](/cli/config) exactly as the file holds them: label, sources, disabled configurations, copy modes. |
| `skills` | One record per skill agentx manages: its name, its kind, `managed`; where it is published to, its `source`, which for your own skills is your account remote and is left out while you have none; for a skill you forked, where it came from, its `upstream`; the version it is based on; and whether this machine placed it anywhere. |
| `machine` | The id and label of the machine you exported from. |

The file is readable by you alone, because it holds your settings. Treat it as you treat `settings.json`.

agentx refuses to overwrite a file that is already there. Pass `--force` to replace it:

```sh
agentx export ~/agentx-export.json --force
```

A path that names a directory is refused whether or not you pass `--force`: give the path of the file to write.

Two exports of an unchanged machine are the same file, byte for byte.

## Import onto another machine

```sh
agentx import ~/agentx-export.json
```

```text
Replace the settings in ~/.agentx/settings.json with those of my-laptop from ~/agentx-export.json? [y/N] y
✓ imported the settings of my-laptop from ~/agentx-export.json
3 skills in the export: 1 present, 1 missing, 1 at a different version
  pdf     managed  present    https://github.com/example/skills/skills/pdf
  xlsx    managed  missing    https://github.com/example/skills/skills/xlsx
  review  managed  different  ssh://git@github.com/you/forks
  only the settings were written: add each source again, then install a missing skill with 'agentx skill add <source>'
    agentx source add https://github.com/example/skills#release
    agentx source add ssh://git@github.com/you/forks --account
```

Import writes your settings and nothing else. It creates no account repo, fetches nothing, installs nothing and places nothing.

Your source list comes back with its pins, but no source is fetched. Before you install anything from a source, run the `agentx source add` line import prints for it. Import prints these lines even when the export lists no skills. For a pinned source the line is `agentx source add <url>#<pin>`; running `agentx source add <url>` alone would unpin the source. Your account remote gets an `agentx source add <url> --account` line.

Import leaves out whether you could write to each source. That depends on this machine's credentials, so agentx checks it again here.

When the URL or the pin holds anything but letters, digits and `._/:@%+=,#-`, import puts it in single quotes, so the line runs as printed in a POSIX shell such as bash or zsh. The export file supplies both, and quoting keeps a `$`, `&` or quote in them from running as a command.

The listing says what this machine's account repo has of each skill:

| State | Meaning |
|---|---|
| `present` | This machine holds that skill at that version: as a branch of its account repo, or, for one of your own skills, on the [account remote](/cli/source#add-your-account-remote) you set. When the library still holds the skill, place it with [`agentx skill place`](/cli/skill). One of your own skills whose branch the account repo holds but the library does not comes back with `agentx skill place <name>` too. When the library no longer holds a skill of a source, bring it back with [`agentx skill add`](/cli/skill). Install one of your own skills that only the account remote holds with [`agentx skill add --name <name>`](/cli/skill#install-your-skills-on-another-machine). |
| `missing` | Neither the account repo nor the account remote has a branch for it. For a skill of a source, add its source with [`agentx source add`](/cli/source), then install it again with [`agentx skill add`](/cli/skill). One of your own skills you never published to the account remote cannot be restored on this machine: installing its upstream again brings back the upstream skill, not your fork of it. |
| `different` | The account repo holds that name at another version, or as one of your own skills where the export had a skill of a source, or the other way round, or the account remote holds that skill at another version, as when it was published again after the export. |

A fresh machine has no account repo, so every skill reads `missing` there. Add your account remote before you import, with `agentx source add <url> --account`, and the skills of yours you published read `present`: the listing then tells which of your own skills the remote keeps for you. Install each one with [`agentx skill add --name <name>`](/cli/skill#install-your-skills-on-another-machine), or all of them with `agentx skill add --all`.

## Confirm without a terminal

Import replaces settings, so it asks first. Pass `--yes` to answer in advance:

```sh
agentx import ~/agentx-export.json --yes
```

Use `--yes` in scripts and wherever there is no terminal. Without it, and without a terminal to ask at, import exits with code 6 and changes nothing. Answering anything but `y` or `yes` does the same.

## Move to a new machine

1. On the old machine, run `agentx export ~/agentx-export.json`.
2. Copy the file to the new machine.
3. If you publish your own skills, add your account remote on the new machine with `agentx source add <url> --account`.
4. On the new machine, run `agentx import ~/agentx-export.json`.
5. Run each `agentx source add` line the import printed, exactly as printed. It names the pin of a pinned source, `<url>#<pin>`, and `agentx source list` shows the pins too.
6. Install what the listing calls missing with `agentx skill add <source>`.

Import restores the settings and nothing else, so the sources it lists are not yet on the new machine. Until you add a source again, `agentx source fetch` and `agentx skill add` exit with code 5 and say the source was not fetched. They name the same `agentx source add` line, pin included, so following that hint keeps the pin too.

## When an import is refused

| Exit code | Cause |
|---|---|
| 5 | The file is not there. |
| 6 | The file is not an agentx export, is truncated, is larger than 8 MiB, is of a schema version this agentx does not read, carries a field it does not know, or holds settings it would not write. |
| 6 | A skill record agentx would not write: a kind other than `managed`, a commit that is not a commit id, a subpath on one of your own skills, an upstream on a skill of a shared source, or a version that does not add up. The message names the skill. |
| 6 | The settings hold something agentx never writes: a URL with a token in it, in `url` or `alias`; an access other than `writable` or `read-only`; two account remotes; another source naming the repository of the account remote; a pin or default branch that is not a ref git accepts; a date not in RFC 3339 UTC; a label with a control character in it or longer than 256 bytes; a source or a configuration listed twice; a list out of order. The message names the entry and the rule. |
| 6 | You answered no, or there was no terminal to ask at and `--yes` was not given. |

A refused import changes nothing: your settings stay exactly as they were.
