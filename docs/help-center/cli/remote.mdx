---
title: "Account remote"
description: "Publish your forks to a Git repository you own, and pull what your other machines published."
---

The account remote is a Git repository you own, such as a private repository on GitHub. Publish a fork to it from one machine, and pull it on another. Only forks travel: managed skills, update checks and sources stay on each machine.

The account remote is a [source](/cli/source) of the fork layout: it holds one branch per fork, and `agentx source list` shows it with `(account)`. The `agentx remote` commands are other names for source commands: `remote set <url>` is `agentx source add <url> --account`, and `remote unset` is `agentx source remove` of the account remote.

A machine without a remote keeps the whole history of every fork, with commit, diff and revert. Attach a remote when you want a backup, or a second machine.

## Attach a remote

Create an empty repository on your Git host, then attach it:

```sh
agentx remote set git@github.com:you/skills.git
```

```text
✓ the account remote is now ssh://git@github.com/you/skills; it holds 0 forks; you can write to it
```

- Give any URL Git reaches: `https://`, `ssh://`, `git@host:path`, `file://` or an absolute path. agentx records it in its canonical form, as it records a source.
- To name the repository by its HTTPS URL and reach it over SSH, add `--push-url git@github.com:you/skills.git`: agentx fetches and pushes forks there. `--push-url=` clears it.
- Keep credentials out of the URL. Use a Git credential helper or an SSH key, as for any repository: agentx runs `git` with your own settings, so they apply. A URL with a password or a token in it is refused with exit code 1.
- agentx reaches the repository first. One Git cannot reach is refused with exit code 3, and nothing changes.
- Attaching a different URL forgets what the old remote held. Your forks stay as they are, and publish to the new remote.
- A source you added with `agentx source add` cannot become the account remote while you have skills installed from it, nor while it names the same repository by another URL: agentx stops with exit code 6. Remove the source first with `agentx source remove <url>`.

Check which remote is set with `agentx remote show`:

```text
ssh://git@github.com/you/skills  fork  writable  2 forks
```

Detach it with `agentx remote unset`: your forks and their history stay, and nothing on the remote changes.

An earlier agentx kept the account remote as the Git remote `origin` of its own repository. The next agentx command that changes something, such as `agentx source fetch --all`, moves it into your settings; [`agentx doctor`](/cli/doctor) names it until then.

## Publish a fork

```sh
agentx publish release-notes
```

```text
✓ published release-notes as 4c2e9a1
```

- Publishing pushes your commits, and nothing else. Commit your edits first with [`agentx skill commit`](/cli/fork#commit-your-edits). A fork with uncommitted edits still publishes its commits, and agentx names it with a warning.
- `agentx publish --all` publishes every fork with commits the remote does not have.
- Each fork goes to its own branch, `skills/<name>`. Publishing one fork leaves your other forks' commits where they are.
- When another machine published commits of the fork first, agentx takes them in before it pushes, as [`agentx pull`](#pull-what-another-machine-published) does. Commit or discard your edits first: a fork with uncommitted edits stops with exit code 6.
- agentx never forces a push. When the remote rejects one, for example because another machine published meanwhile, run `agentx pull <name>`, then publish again.
- To delete a fork's branch from the remote, remove the fork with [`agentx skill remove <name> --remote`](/cli/fork#remove-a-fork).

### Push automatically

Turn on auto-push to publish your commits without running `agentx publish`:

```sh
agentx config set auto_push true
```

- The desktop app's background process, [`agentx serve`](/cli/serve), pushes a fork's commits once you stop committing to it for a minute, so a run of commits goes out as one push.
- It pushes commits only. It never commits your edits for you: commit them with `agentx skill commit` when you want them published.
- It only pushes forks the remote already holds. Publish a new fork the first time with `agentx publish <name>`. A fork whose branch was deleted from the remote, for example with `agentx skill remove <name> --remote` on another machine, is not pushed again until you publish it.
- It never merges. When the remote holds commits of the fork that you do not have, and you have commits it lacks, it leaves the fork alone and warns you once: run `agentx publish <name>` to take them in and publish.
- It never pushes over a different fork of the same name. It warns you once instead: rename yours with `agentx skill rename <name> <new>`, then publish that one.
- Auto-push is off by default. Turn it off again with `agentx config set auto_push false`.

## Install a fork on another machine

On a second machine, attach the same remote, then list the forks it holds that this machine has not installed:

```sh
agentx skill list --remote
```

```text
1 skill
  pdf  managed  current  https://github.com/anthropics/skills/skills/pdf  4 placements
2 installable forks on the account remote
  release-notes  fork  installable  https://github.com/acme/skills/release-notes
  standup        fork  installable  (none)
Install one with agentx skill add --from-account <name>.
```

- `--remote` fetches the remote first. A remote Git cannot reach stops with exit code 3.
- Each row names the upstream the fork's own commits record, or `(none)` for a skill you created with `agentx skill new`.
- A branch on the remote that agentx cannot install as a fork is left out with a warning: one whose name is not a valid skill name, or whose history records no fork id.

Install one:

```sh
agentx skill add --from-account release-notes
```

```text
✓ added https://github.com/acme/skills at 7d1e0b2: 3 skills; you can write to it
✓ installed release-notes from the account remote at 4c2e9a1: 1 placement
  claude-code  symlink  ~/.claude/skills/release-notes -> ~/.agents/skills/release-notes
```

- It is the same fork, with its id and its whole history. Commit here and publish, and the commits go to the same branch.
- agentx places it into every enabled configuration, as `agentx skill add` does. Pass `--to <configuration>` to choose, and `--copy` for copies.
- When this machine has not added the fork's upstream source, agentx adds it, so that [`agentx skill check`](/cli/skill) finds the fork's updates here too. A source it cannot fetch does not stop the install: run the `agentx source add` line the warning prints.

### When the library already holds the name

- **A managed copy of the same upstream, unedited**: the fork takes its place. Its placements stay as they are: symlinks now lead to the fork, and a copy keeps the managed version until `agentx skill place <name>` refreshes it. Files Git ignores in it, such as a `.DS_Store`, move into the fork.
- **A managed skill with an update merge pending**: agentx stops with exit code 4. Finish the merge, or give it up with `agentx skill update <name> --abort`, then install again.
- **A managed copy with your edits, or any other folder**: agentx stops with exit code 6 and changes nothing. Pass `--keep-local` to move the folder into the fork as it is: its whole content replaces the fork's as uncommitted edits, and files Git ignores stay with it. A folder older than the fork's latest commits then shows those commits undone, so check the edits with `agentx skill diff <name>` first. Then keep the edits with [`agentx skill commit`](/cli/fork#commit-your-edits), or drop them with [`agentx skill revert`](/cli/fork#undo-edits).
- **A symlink**: agentx stops with exit code 6, even with `--keep-local`. Remove the link, then install again.

## Pull what another machine published

```sh
agentx pull release-notes
```

```text
✓ pulled release-notes: merged the account remote, committed as 9abcdef
```

- When this machine has no commits of its own, agentx moves the fork to the published commit: a fast-forward, with nothing new committed.
- When both machines committed, agentx merges the two with Git, and commits the merge on the fork's branch, as `release-notes: merge the account remote (desktop)`.
- Leave out the name to pull every fork placed on this machine. A fork that cannot be pulled does not stop the others.
- Commit or discard your edits first: a fork with uncommitted edits stops with exit code 6 when the remote has something new.
- `agentx skill update <name>` pulls a fork first, then takes its new upstream version, as two commits.

### Which upstream version the merge records

A fork remembers the upstream version it was last updated from, so that its next update merges correctly. When two machines took the same version, the merge keeps it. When they took different versions of the same upstream, the merge records the newer one, but only when the source's history on this machine proves it newer: run [`agentx source fetch`](/cli/source) first to fetch that history. Otherwise the merge keeps this machine's version. At worst, the next update then conflicts where both versions changed the same lines. No content is lost.

When a pull brings a newer upstream version than the update your last [`agentx skill check`](/cli/skill) found, agentx drops that update, so `agentx skill update` never takes the fork back to the older version. Run `agentx skill check` again to look for anything newer.

### Resolve a conflict

When both machines changed the same lines, your fork stays as it is, folder and branch alike, and the merge waits in a Git worktree, `~/.agentx/merges/<name>`. The pull, or the publish that took in the remote's commits first, exits with code 4 and lists the files:

```text
release-notes conflicts with the account remote in 1 file
notes.md: both modified
```

Resolve it as you resolve an update's conflict: fix each file with Git in `~/.agentx/merges/<name>/<folder>` and `git add` it, then run `agentx pull <name>`. `agentx skill update <name>` completes it too, but `agentx publish` does not: while the merge waits and the remote has something new, publishing stops with exit code 4, so complete the merge with `agentx pull <name>` first, then publish. Give the merge up with `agentx skill update <name> --abort`. See [Resolve a conflict](/cli/fork#resolve-a-conflict).

A binary file or a symlink that both machines changed conflicts as a whole, with no markers: the waiting merge holds this machine's version. Keep it, or take the other machine's with `git checkout --theirs <file>`, then `git add` it.

When both machines took the same upstream version, sync them before you edit the skill again. Until they have synced once, an edit on one machine conflicts on the other machine's pull or publish, even when that machine changed nothing, if it touches a line the version changed, a line your fork had changed from upstream, or a line next to either. A line put back to the older text conflicts the same way rather than being undone. Keep the lines you want.

## Two forks with one name

Every fork has a permanent id. A skill you create on two machines under the same name is two forks, with two ids. agentx never mixes them: once one is published, publishing or pulling the other stops with exit code 6:

```text
error: the account remote's skills/release-notes is a different fork than release-notes on this machine, so release-notes cannot be published
hint: rename yours with 'agentx skill rename release-notes <new>', then publish that one
```

[Rename](/cli/fork#rename-a-fork) yours, then publish it under its new name.

## Exit codes

- `1`: the URL is not one Git reaches as it is, carries a password or a token, or names a ref with `#`; the push URL breaks the rules of [`--push-url`](/cli/source#push-over-another-url); `publish` is given both a name and `--all`, or neither; `skill add --from-account` is given no name, a source, `--skill`, `--all`, `--except` or `--fetch`; or `--keep-local` is given without `--from-account`.
- `3`: Git cannot reach the account remote.
- `4`: a fork has a merge waiting, or the pull or publish left one waiting for you to [resolve](#resolve-a-conflict); or the managed skill a fork would take the place of has an update merge pending.
- `5`: the name is not a skill of this machine; the remote holds no fork of that name to install; or the fork to install, or the folder `--keep-local` keeps, has no `SKILL.md`.
- `6`: no account remote is set; a source you installed skills from, or another URL of the same repository, is in the way of `remote set`; the skill is not a fork; the fork to install is installed already, or the library holds a symlink, edits or a folder of its own at its name; the remote's branch of that name is [another fork](#two-forks-with-one-name), names no fork id, or shares no commit with yours; the fork has uncommitted edits and the remote has something new; the remote rejected the push; the fork's worktree is missing, needs repair or is not on its branch; or the fork, or its branch on the remote, changed while it was being pulled or published.
- `7`: another agentx command is running. Retry when it finishes.
- `8`: the account repo in agentx home cannot be read or written. Run `agentx doctor`.
