---
title: "Your own skills"
description: "Create skills of your own, or fork installed ones, each with a history in the account repo."
---

Your own skills are the skills you create with `agentx skill new` or fork with `agentx skill fork`. agentx keeps the history of each one in the [account repo](/#key-terms) on this machine, `~/.agentx/account.git`. To use them on your other machines, publish them to your [account remote](/cli/source#add-your-account-remote), a Git repository you own. You need an account remote only when you publish. Every client sees your own skills like any other skill.

A skill you fork from an installed skill keeps its upstream, the skill it came from, so you can take in newer versions later. A skill you create has no upstream.

## Create a skill

```sh
agentx skill new release-notes --description "Write release notes from the merged pull requests."
```

```text
✓ created release-notes in /home/me/.agents/skills/release-notes: 4 placements
  claude-code  symlink  /home/me/.claude/skills/release-notes -> /home/me/.agents/skills/release-notes
  codex        library  /home/me/.agents/skills/release-notes
  cursor       symlink  /home/me/.cursor/skills/release-notes -> /home/me/.agents/skills/release-notes
  gemini-cli   library  /home/me/.agents/skills/release-notes
  always available to universal clients: codex, gemini-cli
No account remote is set: run 'agentx source add <url> --account', then 'agentx skill publish release-notes' to publish it.
```

The skill starts from a template: a `SKILL.md` with the name and the description in its frontmatter and a line that asks for the instructions. Open `~/.agents/skills/release-notes/SKILL.md` in your library and write the instructions. Leave out `--description` to fill it in later.

agentx links the skill into every enabled client, as [`agentx skill add`](/cli/skill#install-a-skill) does. Each link is a placement. Clients that read the library directly, such as Codex and Gemini CLI, need no link. See [Clients that see every skill](/cli/skill#clients-that-see-every-skill).

To publish the skill:

1. Set an account remote once: `agentx source add <url> --account`. The last output line shows only while none is set.
2. Publish the skill by name: `agentx skill publish release-notes`.

Until you publish it, `agentx skill list` shows the skill as `not published`. `agentx skill publish` with no name skips skills that you never published.

`agentx skill list` shows the skill as `managed`. Its source column shows your account remote URL with `(account)`, or `account remote not set`.

### Choose a name

Use 1 to 64 lowercase letters, digits and hyphens, with no hyphen at the start or end and no two in a row, such as `release-notes`.

agentx refuses the name, and changes nothing, when:

- it breaks the rule above;
- you already have a skill of that name, even with different capital letters. For example, a skill you installed as `Notes` blocks `notes`;
- your library or `~/.agentx/worktrees` already holds something under that name.

## Fork a skill

Fork a skill to edit it with a history of your own. You can fork a skill agentx installed, a skill you put in your library yourself, a [plugin's skill](#fork-a-plugins-skill) or [one of your own skills](#fork-one-of-your-own-skills). An installed or library skill is replaced by its fork:

```sh
agentx skill fork pdf
```

```text
✓ forked pdf; the fork replaces it wherever it was
```

- The fork replaces the skill under the same name. Every client that had the skill now sees the fork.
- The fork keeps the skill's files as they are now, your edits included.
- The fork is one of your own skills. [Publish it](#create-a-skill) as you publish a skill you create.
- A fork of an installed skill remembers the version it came from, so `agentx skill list` shows its upstream after `from`, and you can update it to newer versions later.
- [Files that stay local](#files-that-stay-local), such as a `.DS_Store`, move with the skill and are never published.

agentx cannot fork a skill in its place, and stops with exit code 6, when:

- the library entry is a symlink you made;
- the skill folder holds its own `.git`;
- the library and `~/.agentx` are on different file systems.

Fork it [under a new name](#fork-under-a-new-name) instead. For a `.git` folder, you can also move it out of the skill first.

### Fork under a new name

```sh
agentx skill fork pdf --name my-pdf
```

```text
✓ forked pdf as my-pdf: 4 placements; pdf stays as it was
  claude-code  symlink  /home/me/.claude/skills/my-pdf -> /home/me/.agents/skills/my-pdf
  codex        library  /home/me/.agents/skills/my-pdf
  cursor       copy     /home/me/.cursor/skills/my-pdf
  gemini-cli   library  /home/me/.agents/skills/my-pdf
  always available to universal clients: codex, gemini-cli
```

- The fork sits beside the skill, which stays exactly as it was.
- agentx writes the new name into the fork's `SKILL.md`, as part of the fork's first commit.
- The fork goes into the same clients as the skill, with a copy wherever the skill has a copy.
- Use a new name to fork a skill whose own name breaks the [naming rule](#choose-a-name), such as `My_Skill`.

### Fork one of your own skills

One of your own skills already owns its name, so fork it under a new one: `agentx skill fork my-pdf --name pdf-letters`. The new skill starts from the last commit of the one you fork and keeps its history. The new skill includes your unpublished edits. Publish it to put it on your account remote. See [Unpublished edits are kept](#unpublished-edits-are-kept).

The new skill holds the skill's folder alone. A file you committed with Git next to the folder, such as a `README.md` at the root of the worktree, stays with the skill you forked. If the original skill is missing from your library, agentx does not place the new skill in any client. Place it with [`agentx skill place`](/cli/skill#place-a-skill-you-already-have).

### Fork a plugin's skill

```sh
agentx skill fork format
```

```text
• claude-code: the fork owns the bare name and the plugin's copy stays reachable under the plugin's prefix, so the model sees both
• codex: both load, the plugin's copy under the plugin's namespace
• gemini-cli: it reads the library, so it sees format whether or not it has formatter
✓ forked format from plugin formatter as format: 2 placements; the plugin's copy stays as it was
  claude-code  symlink  /home/me/.claude/skills/format -> /home/me/.agents/skills/format
  codex        library  /home/me/.agents/skills/format
  always available to universal clients: codex, gemini-cli
```

- agentx leaves the plugin as it is. The fork goes into your library and into the enabled clients that have the plugin. Clients that read the library also see it.
- The lines before the result say what each client sees: the fork, the plugin's copy, or both. agentx cannot turn the plugin's copy off.
- When several plugins provide a skill of the same name, name the plugin: `agentx skill fork formatter:format`.

## Publish your edits

Edit one of your own skills in any editor or agent, through your library. `agentx skill list` shows it as `modified` until you publish the edits. agentx publishes only when you run `agentx skill publish`.

```sh
agentx skill publish release-notes -m "Cover reverted pull requests"
```

Publishing records your edits as one commit and pushes it to your account remote. See [Publish a skill](/cli/skill#publish-a-skill). You can also commit with Git in `~/.agentx/worktrees/<name>`. The next publish pushes your commits. With `-m`, it combines them into one commit with your message.

### Unpublished edits are kept

`agentx skill update`, `agentx skill fork` and `agentx skill rename` keep your unpublished edits. They save the edits first, then run. The edits stay unpublished: `agentx skill list` shows the skill as `modified`, and `agentx skill diff` shows the edits. If you edit the skill while the command runs, it stops with exit code 6. Run it again. A new skill that `agentx skill fork` makes starts from those edits, so it shows as `current`.

To discard your edits before you run such a command, put the skill's last commit back with Git in its worktree, then delete the files you added:

```sh
git -C ~/.agentx/worktrees/<name> restore --source=HEAD --staged --worktree .
git -C ~/.agentx/worktrees/<name> clean -fd
```

These commands keep files that Git ignores, such as a local `.env`.

To drop edits that an update, fork or rename already recorded, reset the skill's worktree to the commit `agentx skill diff <name>` compares with, such as its last published version:

```sh
git -C ~/.agentx/worktrees/<name> reset --hard <commit>
```

This drops every commit made since that one, an update's merge included.

## Read a skill's history

```sh
agentx skill history release-notes
```

```text
9b41c07  2026-10-02 14:03  Tighten the examples  foreign  1 file
4c2e9a1  2026-10-02 11:20  release-notes: edit SKILL.md and add examples.md (laptop)  2 files
e07d5b2  2026-10-01 09:12  Create release-notes  1 file
```

- Commits are listed newest first, each with the number of files it changes in the skill. Add `--json` to see the file names.
- `foreign` marks a commit that you or an agent made with Git.
- `import` marks an upstream version: the one the fork started from, and each one an update merged in. Its date is the upstream commit's date.
- With `--json`, each commit is a `history` event with its full message, its author and the machine that wrote it. A file outside the skill folder, such as a `README.md` at the root of the worktree, starts with `../`.

## See what changed

```sh
agentx skill diff release-notes
```

`skill diff` shows your unpublished edits. It compares the skill folder with the version you last published. A skill you never published is compared with the version you created or forked. [Files that stay local](#files-that-stay-local) do not show.

To compare with an earlier commit, use `--commit` with an id that `agentx skill history` lists:

```sh
agentx skill diff release-notes --commit e07d5b2
```

## Take a new upstream version

A fork of an installed skill keeps its upstream. [`agentx skill check-updates`](/cli/skill#check-for-updates) finds newer upstream versions for it. Read an update, then take it:

```sh
agentx skill diff release-notes --update
agentx skill update release-notes
```

```text
✓ updated release-notes from 1a2b3c4 to 5d6e7f8, committed as 9abcdef
```

- agentx merges the new version into your fork. Your changes are kept, and upstream changes to lines you did not touch come in.
- The merge is committed on the skill's branch, as `release-notes: merge upstream 5d6e7f8 (laptop)`. Nothing is pushed: the fork shows as `modified` until you [publish](/cli/skill#publish-a-skill) it.
- With an [account remote](/cli/source#add-your-account-remote) set, agentx first [updates the fork to what your other machines published](/cli/skill#update-to-what-another-machine-published), then merges the new version on top, as two commits. If Git cannot reach the remote, agentx warns and takes the upstream version alone.
- Your unpublished edits are kept. See [Unpublished edits are kept](#unpublished-edits-are-kept).
- [Files that stay local](#files-that-stay-local) are kept. If the new version holds a file at a path your ignore rules cover, that file replaces your local one, as `git checkout` does.
- `agentx skill update --all` updates every managed skill with an update, your own skills included.
- A skill you created, or forked from a skill agentx did not install or from a plugin's skill, has no upstream. For such a skill, `skill update` only takes what your other machines published. Without an account remote, it stops with exit code 6.
- If two machines took different upstream versions, run `agentx source fetch` before you update.

### Resolve a conflict

When your commits and the update change the same lines, your skill stays as it is, folder and branch alike, and the merge waits in a Git worktree, `~/.agentx/merges/<name>`. The command exits with code 4 and lists the files:

```text
release-notes conflicts with its update from 1a2b3c4 to 5d6e7f8 in 1 file
notes.md: both modified
```

1. Resolve each file with Git in `~/.agentx/merges/<name>/<folder>`: edit it, or run `git checkout --ours <file>` or `git checkout --theirs <file>`, then `git add` it. Running `git commit` there is optional, with any message: agentx still records which upstream version the fork now has.
2. Run `agentx skill update <name>` again. agentx commits the merge on the skill's branch and lays it out in the skill's folder.

- If you edit the skill while the merge waits, agentx keeps the edits. If they conflict, resolve them the same way.
- Give the merge up with `agentx skill update <name> --abort`. Your skill, its branch and the update stay as they were.

A conflict with what another machine published waits the same way. The first line then reads `release-notes conflicts with the account remote in 1 file`. See [Update to what another machine published](/cli/skill#update-to-what-another-machine-published).

- A binary file or a symlink that both machines changed conflicts as a whole, with no markers: the waiting merge holds this machine's version. Keep it, or take the other machine's with `git checkout --theirs <file>`, then `git add` it.
- If two machines take the same upstream version, publish from one and update the other before you edit again. Otherwise the next update can conflict. Resolve it and keep the lines you want.

## Where your skills live

```text
~/.agentx/worktrees/release-notes/.git                Git's pointer to the account repo
~/.agentx/worktrees/release-notes/release-notes/      the skill
~/.agents/skills/release-notes -> ../../.agentx/worktrees/release-notes/release-notes
```

- The branch is `skills/<name>` in the account repo. Plain `git` reads it: `git --git-dir ~/.agentx/account.git log skills/release-notes`.
- agentx checks the branch out in `~/.agentx/worktrees/<name>`. You can run Git there.
- Your library holds a symlink to the skill.

agentx writes commits with your Git `user.name` and `user.email`. If you have not set them, it uses the machine label.

### Files that stay local

Publishing one of your own skills records what Git would record in any repository: files your `.gitignore`, your global Git ignore file or the [`ignore_system_files`](/cli/config) list cover stay on your machine and are never published. If the skill holds a Git repository, agentx refuses to publish it. To publish anyway, list that repository in the skill's `.gitignore`.

## Recover a skill of your own

agentx puts one of your own skills back from its branch when something on disk went missing. `agentx skill list` names what is wrong, and so does the desktop app; any other `agentx skill` command warns about it once before its own output. Fix it with `skill place`:

```sh
agentx skill place release-notes
```

```text
✓ placed release-notes in 2 configurations
  claude-code  symlink  /home/me/.claude/skills/release-notes -> /home/me/.agents/skills/release-notes
  cursor       symlink  /home/me/.cursor/skills/release-notes -> /home/me/.agents/skills/release-notes
✓ checked release-notes's worktree out again from its branch
```

- A deleted worktree is checked out again from the skill's last commit on this machine, and the library symlink is written again. Edits not yet recorded in a commit are gone with the deleted folder. Everything agentx or you committed comes back, published or not.
- A library symlink that is missing or leads nowhere is written again.
- A worktree whose Git pointers broke, for example because you moved `~/.agentx`, is repaired with `git worktree repair`. agentx does not repair a copied worktree.
- If a Git command you ran in the worktree, such as a merge, is waiting for you, finish or abort it first.
- If you switched the worktree to another branch, switch it back to the skill's branch first, with the `git switch` command agentx names.

The desktop app's background process, [`agentx serve`](/cli/serve#what-serve-repairs-at-start), makes the same repairs when it starts.

### Something in the way

agentx never deletes or overwrites a folder of yours to recover a skill. When a folder sits where the skill's worktree or library symlink belongs, `skill place` stops with exit code 6 and changes nothing:

```text
error: /home/me/.agentx/worktrees/release-notes is in the way of release-notes's worktree, so nothing was placed
hint: run 'agentx skill place release-notes --force' to adopt it: its content becomes the skill's unpublished edits
```

This happens when a worktree's registration was removed with Git, or when another tool replaced the library symlink with a copy. Add `--force` to adopt the folder:

```sh
agentx skill place release-notes --force
```

- A folder at `~/.agentx/worktrees/<name>` becomes the skill's worktree again, with its files kept. It must hold only the skill folder. Move other files out first.
- A folder at the library entry moves into the skill's worktree. If the worktree already holds edits of its own, publish or discard them first. If its skill folder holds files Git ignores, such as a local `.env`, move the ones you want to keep into the folder you adopt first; agentx names them and changes nothing. [System files](/cli/config) such as a `.DS_Store` are discarded with it.
- A symlink of yours at the library entry is replaced; it holds no files.

If the folder has no `SKILL.md`, `skill place` stops with exit code 5 and changes nothing. Add a `SKILL.md` first.

What you adopt shows up as unpublished edits. Keep them with `agentx skill publish <name>`. `--force` on a skill with nothing in the way stops with exit code 6.

## Rename a skill of your own

Rename one of your own skills with `skill rename`:

```sh
agentx skill rename release-notes changelog
```

```text
✓ renamed release-notes to changelog: 1 placement
  claude-code  symlink  /home/me/.claude/skills/changelog -> /home/me/.agents/skills/changelog
```

A rename works on this machine alone. The old name's folder, worktree and branch go, and the skill carries on under the new name.

- The renamed skill is the same skill: it keeps its id and every commit of the old one. Its `SKILL.md` carries the new name.
- It is placed where the old one was, as a copy wherever the old one was a copy.
- If the new name is taken or a merge is waiting, the rename stops and nothing changes. Your unpublished edits move to the renamed skill. See [Unpublished edits are kept](#unpublished-edits-are-kept).
- Only your own skills can be renamed. A skill you installed from a shared source, or one agentx does not manage, stops with exit code 6.
- Only the skill folder moves. Files Git ignores, such as a local `.env`, and files beside the skill folder in the worktree are deleted. Copy the ones you want first.
- The renamed skill shows as `modified` until you publish it under its new name.

The first publish of the new name renames it on the account remote:

```sh
agentx skill publish changelog
```

```text
✓ published changelog as 3f2a9c1
✓ deleted skills/release-notes from the account remote (renamed to changelog)
```

- The first publish under the new name removes the old name from your account remote. If it cannot, it warns once. Then remove the old name with `agentx skill remove <old> --remote`.
- Your other machines keep the old name until you remove it there. To get the new name there, run `agentx skill add --name <new>`, then `agentx skill remove <old>`.
- If the account remote refuses because the old branch is its default branch, make another branch the default, then run `agentx skill remove <old> --remote`.

If the removal fails after the renamed skill was made, the error says so. Finish the rename with the `agentx skill remove <old>` command it names.

If you edited or committed to the old skill while the rename ran, the removal stops, since the renamed skill lacks that work. To keep it, remove the renamed skill with `agentx skill remove <new>` and run the rename again, which records the edits. To drop it, run `agentx skill remove <old>`.

## Remove a skill of your own

Remove one of your own skills from this machine with `skill remove`:

```sh
agentx skill remove release-notes
```

- agentx removes the skill from every client, your library and `~/.agentx`.
- Unpublished edits are deleted. Publish them first to keep them.
- If a merge is waiting, or Git is running in the worktree, agentx does not remove the skill. Finish or abort first.
- The skill's branch stays on the account remote, and every other machine keeps the skill until you remove it there.

Add `--remote` to delete the skill's branch from the account remote as well:

```sh
agentx skill remove release-notes --remote
```

- Run it again if the account remote could not be reached. With the skill gone from this machine, it deletes the branch on the account remote alone.
- A hosting service refuses to delete a repository's default branch. If the first skill you published became the default branch, make another branch the default on the hosting service, then run the command again.
- If the account remote's branch of that name is [another skill](/cli/skill#two-skills-with-one-name), agentx refuses to delete it.

Your other machines keep the skill. The next time one of them fetches the account remote, it shows the skill as `not published`, as it shows a skill you never published:

- With no published version left to compare with, that machine compares the skill with the commit that created it, so it also shows as `modified` if it changed since then.
- A bare `agentx skill publish` there skips the skill and names it, so it does not bring the branch back.
- Remove it there with `agentx skill remove <name>`. To keep it on the account remote after all, publish it by name from that machine with `agentx skill publish <name>`, which puts its branch back.

To take one of your own skills out of one configuration only, use `--from`, as for any skill: see [Remove a skill](/cli/skill#remove-a-skill).

## Exit codes

For what each code means, see [Exit codes](/cli/output#exit-codes). For `agentx skill publish`, see the [`agentx skill` exit codes](/cli/skill#exit-codes). These causes are special to your own skills:

| Code | Cause | What to do |
|---|---|---|
| 1 | `skill remove` is given both `--remote` and `--from`; `skill rename` is given the skill's own name; the description is more than one line, holds a control character or is longer than 1024 bytes; `skill diff` is given both `--update` and `--commit`, or an empty `--commit`. | Fix the command line. |
| 3 | `skill remove --remote` cannot reach the account remote, or the remote refused to delete the skill's branch. `skill update` cannot reach the account remote for a skill with no upstream. | Check your network and credentials, then run the command again. |
| 4 | The skill you fork, rename or remove has a merge pending, or `skill update` left a merge for you to [resolve](#resolve-a-conflict). | Finish the merge, or give it up with `agentx skill update <name> --abort`. |
| 5 | agentx cannot find the skill you named in your library or in a plugin. For `skill remove --remote`, the account remote does not hold it either. `skill place` finds no `SKILL.md`. `skill update` names a forked skill whose upstream source you removed. | Check the name. Add a `SKILL.md`, or add the source again. |
| 6 | The name breaks the [naming rule](#choose-a-name), or a skill or folder already has it. | Choose another name. |
| 6 | The skill cannot be forked, renamed, updated or removed as it is. For example: it is not one of your own skills; an installed skill is missing from the library, so there is nothing to fork; several plugins provide the name; the skill holds a Git repository its `.gitignore` does not cover; Git is running in its worktree; the account remote holds [another skill](/cli/skill#two-skills-with-one-name) of that name; or the skill has no upstream and no account remote is set. | Read the message, then see the section for that command. |
| 6 | A folder is in the way, or `--force` is given with nothing in the way. | See [Something in the way](#something-in-the-way). |
| 6 | The skill changed while the command ran. | Run the command again. |
| 7 | Another agentx command is running. | Retry when it finishes. |
| 8 | agentx cannot read or write the account repo, or a forked skill's history does not say which upstream version it is based on. | Run `agentx doctor`. |
