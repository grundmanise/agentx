---
title: "agentx adopt"
description: "Take over the skills the vercel skills CLI installed, without reinstalling them or touching your files."
---

The vercel skills CLI installs skills into `~/.agents/skills`, the same library agentx uses, and records each install in a lock file. `agentx adopt` reads that lock file and takes those skills over. Each skill keeps its directory as it is and gains an upstream, so agentx can tell your edits apart from the version you installed.

agentx only reads the lock file. The file stays as it is.

## See what can be adopted

```sh
agentx adopt
```

```text
3 skills of the vercel skills lock file in the library
  pdf      candidate  https://github.com/anthropics/skills/skills/pdf   its source is not added yet; adopting adds and fetches it
  xlsx     managed    https://github.com/anthropics/skills/skills/xlsx  agentx already manages it
  scraper  refused    (none)                                            scraper names no source agentx can read
Adopt them with agentx adopt --all.
```

With no flags, the command only shows what it found. It writes nothing and makes no network calls.

| State | What it means |
|---|---|
| `candidate` | agentx can adopt it |
| `managed` | agentx already manages it |
| `refused` | agentx cannot adopt it, and the row says why. See [Refused skills](#refused-skills) |

## Adopt skills

Adopt every candidate:

```sh
agentx adopt --all
```

```text
✓ added https://github.com/anthropics/skills at 3f2a9c1: 12 skills; write access unknown
✓ adopted pdf from https://github.com/anthropics/skills under skills/pdf at 9c1d0ab
  base 4e7b21c: the version the lock file recorded, found in the source; the directory differs from it, so what differs is a local modification
```

Or name skills with `--skill`, once for each:

```sh
agentx adopt --skill pdf --skill xlsx
```

For each skill, agentx:

1. Adds its source if you do not have it yet, as [`agentx source add`](/cli/source) does, pinned to the ref in the lock file. This also brings back a source you removed.
2. Finds the upstream version you installed and records it as the skill's [base](#how-agentx-finds-the-base).

Your files stay as they are. If a skill fails, agentx still adopts the others and lists the failures at the end.

Afterwards the skills are ordinary managed skills:

```sh
agentx skill list
```

```text
1 skill
  pdf  managed  modified  https://github.com/anthropics/skills/skills/pdf  4 placements
```

### Skills from one source at different refs

agentx keeps one ref for each source, its pin. The lock file records a ref for each skill, so skills from the same source can have different refs. agentx then pins the source to the ref of the skill whose name comes first alphabetically, and warns you:

```text
warning: https://github.com/anthropics/skills was installed at more than one ref (v1.2.0, main); it is added pinned to v1.2.0. To change the pin, run 'agentx source add https://github.com/anthropics/skills#<ref>' and adopt again
```

agentx looks for the other skills' versions in the history of the pinned ref. If it cannot find one, see [When agentx cannot find the base](#when-agentx-cannot-find-the-base).

To choose the pin yourself, add the source at that ref before you adopt. If you already have the source, this changes its pin:

```sh
agentx source add https://github.com/anthropics/skills#main
agentx adopt --all
```

## How agentx finds the base

The base is the upstream version you installed. agentx compares your directory with it, so your edits stay yours when you update the skill later.

agentx checks these in order and uses the first that works:

1. **The folder hash in the lock file.** agentx looks for that version of the skill's directory in the source, in the last 500 commits that changed it. This also works for a skill the source has since deleted.
2. **Your directory.** If your files match the source's current version exactly, agentx records that version.

To name the version yourself, use `--base`. It replaces both checks. See [Choose the base yourself](#choose-the-base-yourself).

If your directory differs from the base, agentx says so, and `agentx skill list` shows the skill as `modified`. See what you changed with [`agentx skill diff <name>`](/cli/skill#see-what-you-changed).

## When agentx cannot find the base

If both checks fail, agentx warns you and leaves the skill unmanaged:

```text
warning: pdf: the version pdf was installed at cannot be established: no version of skills/pdf in https://github.com/anthropics/skills at 3f2a9c1, or in the 500 commits of it behind that, has the folder hash /home/me/.agents/.skill-lock.json recorded, and the directory is not the version https://github.com/anthropics/skills at 3f2a9c1 holds
error: 1 of 3 skills could not be adopted: ...
hint: leave it unmanaged, or name the version it came from with 'agentx adopt --skill pdf --base <commit, branch or tag>'
```

This usually means the lock file has no usable folder hash, and you edited the skill after you installed it. agentx records only upstream versions as a base, so it leaves the choice to you: name the version, or leave the skill unmanaged.

### Choose the base yourself

Name the version you installed:

```sh
agentx adopt --skill pdf --base v1.2.0
```

```text
✓ adopted pdf from https://github.com/anthropics/skills under skills/pdf at 7d40a19
  base 1b9e05f: the version named with --base; the directory differs from it, so what differs is a local modification
```

- `--base` takes a commit, a branch or a tag of the source, with one `--skill`.
- Name branches and tags as the repository publishes them. `git ls-remote <url>` lists them.
- The version must be in the history of the source's pin. To use a version from another branch, change the pin first:

```sh
agentx source add https://github.com/anthropics/skills#main
```

### Leave it unmanaged

An unmanaged skill stays in your library and keeps working in every client. `agentx skill list` shows it as `unmanaged`, and agentx leaves its updates to you. To adopt it later, run `agentx adopt --skill <name> --base <commit, branch or tag>`.

## Refused skills

| Reason | What to do |
|---|---|
| The library entry is a symlink, or has no `SKILL.md` | Leave it as it is. agentx manages real skill directories only |
| One of your own skills on this machine has the same name | Nothing: that skill already has its own history |
| The lock file names no source agentx can fetch | Install the skill from a git source with [`agentx skill add`](/cli/skill) |
| The lock file names a path outside the repository, or a path with a control character or a leading or trailing space | Fix the entry, or install the skill instead |
| agentx cannot fetch the source | Check the URL and your credentials, then run again |

## Where agentx reads the lock file

agentx reads both files the vercel skills CLI uses:

- `$XDG_STATE_HOME/skills/.skill-lock.json`, or `~/.local/state/skills/.skill-lock.json` when that variable is unset
- `~/.agents/.skill-lock.json`

If both files list a skill differently, agentx warns you and uses the file the vercel skills CLI writes to now: the `$XDG_STATE_HOME` one when that variable is set, and `~/.agents/.skill-lock.json` otherwise.

If a lock file is unreadable JSON or has no `skills` object, agentx stops. Fix the file or move it aside.

agentx skips an entry that is not an object or names no source. If one field has the wrong type of value, agentx warns you, drops that field and reads the rest of the entry.
