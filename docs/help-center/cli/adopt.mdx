---
title: "agentx adopt"
description: "Take over skills agentx does not manage yet: the ones the Vercel skills CLI or Skillshare installed, and unmanaged skills on this machine."
---

`agentx adopt` takes over skills that agentx does not manage yet. It handles two kinds of skill:

- **A skill another tool installed.** The Vercel skills CLI and Skillshare both record where each skill they installed came from. `agentx adopt` reads those records and installs each skill from its source, the way [`agentx skill add`](/cli/skill#install-a-skill) does. Afterwards agentx manages the skill: it knows the source and can update it.
- **An unmanaged skill.** A skill no tool recorded, in your library or in a client's own skills folder, becomes [one of your own skills](/cli/fork), with its files as they are. See [Adopt an unmanaged skill](#adopt-an-unmanaged-skill). A recorded skill that agentx cannot install from its record is taken over the same way. See [Take over a recorded skill](#take-over-a-recorded-skill).

agentx only reads the other tool's files. They stay as they are.

## See what can be adopted

```sh
agentx adopt
```

```text
Found 4 skills installed by the Vercel skills CLI and Skillshare.

Ready to adopt (1)
  pdf  vercel  https://github.com/anthropics/skills/skills/pdf

Ready to take over as your own (1)
  scraper  vercel  scraper was installed from a local source, which is not a git repository agentx can fetch

Cannot adopt (1)
  notes  vercel  notes is a skill of the account remote on this machine

Already managed by agentx (1)
  xlsx

To adopt:
  agentx adopt --all           every skill under "Ready to adopt"
  agentx adopt --skill <name>  one skill, also one under "Ready to take over as your own"
                               or an unmanaged skill no tool installed
```

With no flags, the command only shows what it found. It writes nothing and makes no network calls.

The preview lists the skills the other tools recorded. It does not list unmanaged skills: find those with [`agentx skill list`](/cli/skill#list-your-skills) and [`agentx scan`](/cli/scan). The last line names the command that takes a skill over. When no skill is listed under `Ready to take over as your own`, it reads `To take over an unmanaged skill no tool installed: agentx adopt --skill <name>`.

The skills are grouped by what adopting would do with them:

| Group | What it means |
|---|---|
| Ready to adopt | agentx can adopt it. The row shows the source it comes from |
| Ready to take over as your own | agentx cannot install it from its record, and the row says why. `agentx adopt --skill <name>` takes it over as one of your own skills. See [Take over a recorded skill](#take-over-a-recorded-skill) |
| Cannot adopt | agentx cannot adopt it, and the row says why. See [Refused skills](#refused-skills) |
| Already managed by agentx | agentx already manages it. There is nothing to do |

The tool column shows only when both tools installed skills on this machine. When agentx already manages every skill, the preview says `Nothing to adopt: agentx already manages every one.`

To look at the skills of one tool only, name it: `skills-cli` for the Vercel skills CLI, or `skillshare`. This works with `--all` and `--skill` too:

```sh
agentx adopt skillshare
agentx adopt skillshare --all
```

## Adopt skills another tool installed

Adopt every skill that is ready:

```sh
agentx adopt --all
```

```text
✓ added source https://github.com/anthropics/skills: 12 skills
✓ adopted pdf from https://github.com/anthropics/skills under skills/pdf: 2 placements
  claude-code  symlink  /home/me/.claude/skills/pdf -> /home/me/.agents/skills/pdf
  cursor       symlink  /home/me/.cursor/skills/pdf -> /home/me/.agents/skills/pdf
```

Or name skills with `--skill`, once for each:

```sh
agentx adopt --skill pdf --skill xlsx
```

For each skill, agentx:

1. Adds its source if you do not have it yet, as [`agentx source add`](/cli/source#pin-a-source) does, pinned to the ref the record names. This also brings back a source you removed.
2. Installs the skill from that source at the version the source holds now, and places it in every enabled client, as `agentx skill add` does.

If a skill fails, agentx still adopts the others and lists the failures at the end.

Afterwards the skills are ordinary managed skills:

```sh
agentx skill list
```

```text
1 skill
  pdf  managed  current  https://github.com/anthropics/skills/skills/pdf  2 placements
```

## What happens to the directory

Adopting replaces what the other tool left in the library with the version it installs. That covers the directory the Vercel skills CLI copied, the symlink Skillshare puts in `~/.agents/skills`, and any edit you made in there.

agentx has no flag that keeps an edit. To keep one, copy the skill under a new name before you adopt it, then adopt the copy as one of your own skills. This works when the library entry is a directory, as the Vercel skills CLI leaves it:

1. Copy the directory: `cp -R ~/.agents/skills/pdf ~/.agents/skills/my-pdf`. The new name must follow the [naming rule](/cli/fork#choose-a-name).
2. Set `name` in `~/.agents/skills/my-pdf/SKILL.md` to `my-pdf`. agentx adopts the copy without this step too, but `agentx scan` then lists both skills as `pdf`.
3. Adopt the copy, then the skill:

   ```sh
   agentx adopt --skill my-pdf
   agentx adopt --skill pdf
   ```

`my-pdf` is now one of your own skills and holds your edit. `pdf` holds the version its source holds. To place `my-pdf` in your other clients, run [`agentx skill place my-pdf`](/cli/skill#place-a-skill-you-already-have).

Skillshare keeps its own copy of each skill in its folder, `~/.config/skillshare/skills` by default. agentx never touches that folder, so your edits there stay.

## Adopt an unmanaged skill

An unmanaged skill is a skill agentx does not manage and no other tool recorded: a directory you put in your library, `~/.agents/skills`, or in a client's own skills folder, such as `~/.claude/skills`. Adopt it by name:

```sh
agentx adopt --skill notes
```

```text
✓ adopted notes
No account remote is set: run 'agentx source add <url> --account', then 'agentx skill publish notes' to publish it.
```

- The skill becomes [one of your own skills](/cli/fork), with its files as they are. agentx records them as the first commit of the skill's history.
- agentx installs and fetches nothing. The skill has no upstream, so `agentx skill update` only takes what your other machines published.
- [Publish it](/cli/fork#create-a-skill) as you publish a skill you create. The last output line shows only while no account remote is set.
- [Files that stay local](/cli/fork#files-that-stay-local), such as a `.DS_Store`, move with the skill and are never published.
- Give `--skill` once for each skill to adopt several.

agentx looks for the name in this order:

1. The other tools' records. A skill one of them recorded is [adopted from its source](#adopt-skills-another-tool-installed), unless agentx cannot use the record: see [Take over a recorded skill](#take-over-a-recorded-skill).
2. Your library.
3. Each client's own skills folder.

If you name a tool, such as `agentx adopt skillshare --skill notes`, agentx reads that tool's records only and adopts no unmanaged skill.

### From your library

`agentx skill list` shows an unmanaged skill in your library as `unmanaged`. agentx adopts it in its place:

- The directory moves to `~/.agentx/worktrees/<name>`, and your library holds a symlink to it. See [Where your skills live](/cli/fork#where-your-skills-live).
- Every client that saw the skill still sees it. agentx adds no placement.
- To place the skill in your other clients, run [`agentx skill place <name>`](/cli/skill#place-a-skill-you-already-have).

### From a client's folder

When your library has no skill of that name, agentx adopts the directory of that name in a client's own skills folder:

```sh
agentx adopt --skill jot
```

```text
✓ adopted jot from /home/me/.claude/skills/jot: 1 placement
  claude-code  symlink  /home/me/.claude/skills/jot -> /home/me/.agents/skills/jot
  always available to universal clients: codex, gemini-cli
```

- The directory moves into your library, and a symlink to the library takes its place. The client sees the skill as before.
- Clients that read the library directly, such as Codex and Gemini CLI, now see the skill too. See [Clients that see every skill](/cli/skill#clients-that-see-every-skill).
- If several clients hold a directory of that name with the same files, agentx moves the first one and replaces each of the others with a symlink. A client that reads the library directly gets no symlink: it sees the skill in the library.
- If those directories hold different files, agentx stops with exit code 6 and names them. Keep one, remove or rename the others, then run the command again.
- A client that held no directory of that name gets no placement. Run [`agentx skill place <name>`](/cli/skill#place-a-skill-you-already-have) to place the skill there.
- agentx reads each client's own skills folder for your user, enabled or not. The directory must hold a `SKILL.md`. A skill inside a project is left alone, and so is a plugin's skill: [fork a plugin's skill](/cli/fork#fork-a-plugins-skill) instead.

### When the name is taken

If another skill already has the name, agentx stops with exit code 6 and changes nothing. The message says which skill holds the name:

| What holds the name | What to do |
|---|---|
| A managed skill in your library, with nothing else of that name in a client's folder | Nothing: agentx already manages the skill. |
| A managed skill in your library, while a client's folder holds another directory of that name | Rename the directory and adopt it under the new name. Or follow the hint to put the library's skill in its place, which discards what the directory holds. |
| A skill agentx manages whose library directory is gone | Rename the directory and adopt it under the new name. Or follow the hint: put your own skill back with `agentx skill place <name>`, or stop managing the other skill with `agentx skill remove <name>`. |
| A skill on your account remote, when you adopt from a client's folder | Move the directory aside and install the published skill with `agentx skill add --name <name>`. Or rename the directory and adopt it under the new name. |

A name that differs from another skill's only by capital letters counts as taken.

### When agentx cannot adopt the skill

agentx also stops, and changes nothing, in these cases:

| Cause | Exit code | What to do |
|---|---|---|
| No record, library skill or client folder has that name | 5 | Check the name with `agentx skill list` and `agentx scan`. |
| The name breaks the [naming rule](/cli/fork#choose-a-name), such as `My_Skill` | 6 | Rename the directory to a valid name, then adopt it. |
| The library entry, or the entry in the client's folder, is a symlink | 6 | Replace the link with the directory it points to. |
| The skill holds its own `.git` | 6 | Move the `.git` out of the skill. |
| `~/.agentx/worktrees/<name>` already exists | 6 | Move it aside. |
| The directory and `~/.agentx` are on different file systems | 6 | Keep your library and `~/.agentx` on one file system. For a client's folder, move the directory into your library yourself, then adopt it. |
| A plugin provides the skill | 6 | [Fork the plugin's skill](/cli/fork#fork-a-plugins-skill). |
| The skill changed while the command ran | 6 | Run the command again. |

## Take over a recorded skill

Some records name no source agentx can install the skill from. When this machine holds such a skill as a directory, the preview lists it under `Ready to take over as your own`, with the reason. Take it over by name:

```sh
agentx adopt --skill scraper
```

```text
✓ adopted scraper
```

- agentx takes the skill over as it takes over [an unmanaged skill](#adopt-an-unmanaged-skill): it becomes one of your own skills, with its files as they are, your edits included. It has no upstream.
- agentx cannot use a record that names a source that is not a git repository, such as a local path, a repository Skillshare tracks as a whole, no source agentx can read, or a path that is not a folder of the repository.
- Name the skill with `--skill`, without a tool name. `agentx adopt --all`, and a run that names a tool, such as `agentx adopt skills-cli --skill scraper`, take no skill over: they report it as refused.
- A skill agentx can install from its record is always installed from its source. To keep an edit to it, see [What happens to the directory](#what-happens-to-the-directory).
- The causes under [When the name is taken](#when-the-name-is-taken) and [When agentx cannot adopt the skill](#when-agentx-cannot-adopt-the-skill) stop this command too. For example, a skill Skillshare linked into your library is a symlink to Skillshare's folder: the preview lists it under `Cannot adopt`, and `agentx adopt --skill` stops with exit code 6. Replace the link with the directory it points to, then run the command again.
- If this machine holds no directory to take over, agentx stops with the record's own reason and hint.

The other tool's record stays, since agentx never changes that tool's files. Afterwards:

- `agentx adopt` lists the skill under `Cannot adopt`, as `<name> is a skill of the account remote on this machine`.
- `agentx adopt --all` adopts the other skills, names this one as not adopted and exits with code 6.

## After adopting from the Vercel skills CLI

The Vercel skills CLI installs into `~/.agents/skills`, the library itself, and links your clients' folders to it, so after adopting nothing else moves: the library directory is agentx's, and the links are the placements. Stop using that CLI for the adopted skills. Good to know: `skills update` rewrites the library directory with the newest upstream version, which agentx then shows as `modified` against the version it installed; `skills remove` deletes the directory and its lock entry, and `agentx skill list` then names the `agentx skill add` command that installs the skill again.

## After adopting from Skillshare

Adopting moves a skill to agentx completely: the library gets a real directory, and Skillshare's links in your clients' folders, such as `~/.claude/skills/pdf`, become links to the library. You are done with Skillshare for that skill. Uninstall Skillshare, or stop running it, and leave its folder as it is or delete it.

Good to know: Skillshare does not know about the adoption. If you run `skillshare sync` afterwards, it puts its own links back, or removes the adopted directory once you uninstalled the skill there, and your clients read Skillshare's copy again. Running `agentx adopt --all` again repairs that: agentx installs each such skill again and the adoption is whole. A skill you also uninstalled from Skillshare is no longer in its records, so `agentx adopt` cannot see it; `agentx skill list` then names the `agentx skill add` command that installs it again.

### Skills from one source at different refs

agentx keeps one ref for each source, its pin. The records name a ref for each skill, so skills from the same source can have different refs. When a run adds a source, agentx pins it to the ref of the first skill the run adopts from it, in alphabetical order. If those skills have different refs, agentx warns you:

```text
warning: https://github.com/anthropics/skills was installed at more than one ref (v1.2.0, main); it is added pinned to v1.2.0. To change the pin, run 'agentx source add https://github.com/anthropics/skills#<ref>' and adopt again
```

A source you already have keeps its pin. To choose the pin yourself, add the source at that ref before you adopt. If you already have the source, this changes its pin:

```sh
agentx source add https://github.com/anthropics/skills#main
agentx adopt --all
```

## Grouped Skillshare skills

Skillshare can install a skill into a group, such as `frontend/ui`. In every tool's skills folder it names that skill `frontend__ui`, with two underscores. agentx adopts it under that name. To shorten it, rename the skill afterwards:

```sh
agentx skill rename frontend__ui ui
```

## Refused skills

| Reason | What to do |
|---|---|
| One of your own skills on this machine has the same name | Nothing: that skill already has its own history |
| The record names no source agentx can fetch, such as a local path | [Take the skill over](#take-over-a-recorded-skill) with `agentx adopt --skill <name>`, or install it from a git source with [`agentx skill add`](/cli/skill) |
| Skillshare tracks the whole repository, as a `_name` folder with skills inside | Add the repository with `agentx source add` and install its skills with `agentx skill add` |
| The record names a path outside the repository, or a path with a control character or a leading or trailing space | Fix the entry, or install the skill instead |
| The source no longer holds a skill at that path | Leave it unmanaged, or install another skill |
| agentx cannot fetch the source | Check the URL and your credentials, then run again |

When the reason lies in the record itself, as in the second, third and fourth rows, and this machine holds the skill as a directory, `agentx adopt --skill <name>` [takes the skill over](#take-over-a-recorded-skill) instead.

A refused skill stays in your library as it is and keeps working in every client. `agentx skill list` shows it as `unmanaged`.

## Where agentx reads the records

For the Vercel skills CLI, agentx reads both lock files:

- `$XDG_STATE_HOME/skills/.skill-lock.json`, or `~/.local/state/skills/.skill-lock.json` when that variable is unset
- `~/.agents/.skill-lock.json`

If both files list a skill differently, agentx warns you and uses the file the Vercel skills CLI writes to now: the `$XDG_STATE_HOME` one when that variable is set, and `~/.agents/.skill-lock.json` otherwise.

For Skillshare, agentx reads `.metadata.json` in the folder Skillshare installs into:

- `~/.config/skillshare/skills` by default, or under `$XDG_CONFIG_HOME` when that variable is set
- the folder `sources.skills` names in `~/.config/skillshare/config.yaml`, or the older `source` key, when either is set

Skillshare migrates its older `registry.yaml` and the `.skillshare-meta.json` files beside each skill into `.metadata.json` the next time it runs. If agentx finds nothing to adopt, run a Skillshare command such as `skillshare list` first.

If a record file is unreadable JSON, or a configuration file is unreadable YAML, agentx stops. Fix the file or move it aside.

agentx skips an entry that is not an object or names no source. If one field has the wrong type of value, agentx warns you, drops that field and reads the rest of the entry. A skill both tools recorded is adopted from the Vercel skills CLI's record, with a warning.
