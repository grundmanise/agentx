---
title: "agentx adopt"
description: "Take over the skills the Vercel skills CLI or Skillshare installed, so agentx can update them."
---

The Vercel skills CLI and Skillshare both record where each skill they installed came from. `agentx adopt` reads those records and installs each skill from its source, the way [`agentx skill add`](/cli/skill#install-a-skill) does. Afterwards agentx manages the skill: it knows the source and can update it.

agentx only reads the other tool's files. They stay as they are.

## See what can be adopted

```sh
agentx adopt
```

```text
3 skills installed by another tool
  pdf      vercel      candidate  https://github.com/anthropics/skills/skills/pdf   its source is not added yet; adopting adds and fetches it
  xlsx     skillshare  managed    https://github.com/anthropics/skills/skills/xlsx  agentx already manages it
  scraper  vercel      refused    (none)                                            scraper names no source agentx can read
Adopt them with agentx adopt --all.
```

With no flags, the command only shows what it found. It writes nothing and makes no network calls.

| State | What it means |
|---|---|
| `candidate` | agentx can adopt it |
| `managed` | agentx already manages it |
| `refused` | agentx cannot adopt it, and the row says why. See [Refused skills](#refused-skills) |

## Adopt skills

Adopt every candidate:

```sh
agentx adopt --all
```

```text
✓ added https://github.com/anthropics/skills at 3f2a9c1: 12 skills; write access unknown
✓ adopted pdf from https://github.com/anthropics/skills under skills/pdf at 9c1d0ab: 2 placements
  claude-code  symlink  /home/me/.claude/skills/pdf -> /home/me/.agents/skills/pdf
  cursor       symlink  /home/me/.cursor/skills/pdf -> /home/me/.agents/skills/pdf
```

Or name skills with `--skill`, once for each:

```sh
agentx adopt --skill pdf --skill xlsx
```

For each skill, agentx:

1. Adds its source if you do not have it yet, as [`agentx source add`](/cli/source#pin-a-source) does, pinned to the ref the record names. This also brings back a source you removed.
2. Installs the skill from that source at the version the source holds now, and places it in every enabled client, as `agentx skill add` does.

If a skill fails, agentx still adopts the others and lists the failures at the end.

Afterwards the skills are ordinary managed skills:

```sh
agentx skill list
```

```text
1 skill
  pdf  managed  current  https://github.com/anthropics/skills/skills/pdf  2 placements
```

## What happens to the directory

Adopting replaces what the other tool left in the library with the version it installs. That covers the directory the Vercel skills CLI copied, the symlink Skillshare puts in `~/.agents/skills`, and any edit you made in there.

To keep an edit, fork the skill first. A fork keeps your files and their history, under a name of your choice:

```sh
agentx skill fork pdf --name my-pdf
agentx adopt --skill pdf
```

Skillshare keeps its own copy of each skill in its folder, `~/.config/skillshare/skills` by default. agentx never touches that folder, so your edits there stay.

## After adopting from Skillshare

Adopting moves a skill to agentx completely: the library gets a real directory, and Skillshare's links in your clients' folders, such as `~/.claude/skills/pdf`, become links to the library. You are done with Skillshare for that skill. Uninstall Skillshare, or stop running it, and leave its folder as it is or delete it.

Good to know: Skillshare does not know about the adoption. If you run `skillshare sync` afterwards, it puts its own links back, or removes the adopted directory once you uninstalled the skill there, and your clients read Skillshare's copy again. Running `agentx adopt --all` again repairs that: agentx installs each such skill again and the adoption is whole. A skill you also uninstalled from Skillshare is no longer in its records, so `agentx adopt` cannot see it; `agentx skill list` then names the `agentx skill add` command that installs it again.

### Skills from one source at different refs

agentx keeps one ref for each source, its pin. The records name a ref for each skill, so skills from the same source can have different refs. When a run adds a source, agentx pins it to the ref of the first skill the run adopts from it, in alphabetical order. If those skills have different refs, agentx warns you:

```text
warning: https://github.com/anthropics/skills was installed at more than one ref (v1.2.0, main); it is added pinned to v1.2.0. To change the pin, run 'agentx source add https://github.com/anthropics/skills#<ref>' and adopt again
```

A source you already have keeps its pin. To choose the pin yourself, add the source at that ref before you adopt. If you already have the source, this changes its pin:

```sh
agentx source add https://github.com/anthropics/skills#main
agentx adopt --all
```

## Grouped Skillshare skills

Skillshare can install a skill into a group, such as `frontend/ui`. In every tool's skills folder it names that skill `frontend__ui`, with two underscores. agentx adopts it under that name. To shorten it, rename the skill afterwards:

```sh
agentx skill rename frontend__ui ui
```

## Refused skills

| Reason | What to do |
|---|---|
| One of your own skills on this machine has the same name | Nothing: that skill already has its own history |
| The record names no source agentx can fetch, such as a local path | Install the skill from a git source with [`agentx skill add`](/cli/skill) |
| Skillshare tracks the whole repository, as a `_name` folder with skills inside | Add the repository with `agentx source add` and install its skills with `agentx skill add` |
| The record names a path outside the repository, or a path with a control character or a leading or trailing space | Fix the entry, or install the skill instead |
| The source no longer holds a skill at that path | Leave it unmanaged, or install another skill |
| agentx cannot fetch the source | Check the URL and your credentials, then run again |

A refused skill stays in your library as it is and keeps working in every client. `agentx skill list` shows it as `unmanaged`.

## Where agentx reads the records

For the Vercel skills CLI, agentx reads both lock files:

- `$XDG_STATE_HOME/skills/.skill-lock.json`, or `~/.local/state/skills/.skill-lock.json` when that variable is unset
- `~/.agents/.skill-lock.json`

If both files list a skill differently, agentx warns you and uses the file the Vercel skills CLI writes to now: the `$XDG_STATE_HOME` one when that variable is set, and `~/.agents/.skill-lock.json` otherwise.

For Skillshare, agentx reads `.metadata.json` in the folder Skillshare installs into:

- `~/.config/skillshare/skills` by default, or under `$XDG_CONFIG_HOME` when that variable is set
- the folder `sources.skills` names in `~/.config/skillshare/config.yaml`, or the older `source` key, when either is set

Skillshare migrates its older `registry.yaml` and the `.skillshare-meta.json` files beside each skill into `.metadata.json` the next time it runs. If agentx finds nothing to adopt, run a Skillshare command such as `skillshare list` first.

If a record file is unreadable JSON, or a configuration file is unreadable YAML, agentx stops. Fix the file or move it aside.

agentx skips an entry that is not an object or names no source. If one field has the wrong type of value, agentx warns you, drops that field and reads the rest of the entry. A skill both tools recorded is adopted from the Vercel skills CLI's record, with a warning.
