# Adopt makes an unmanaged skill one of the user's own skills, and fork no longer accepts one

`agentx adopt` makes an unmanaged skill that no other tool recorded one of the user's own skills, with its files as they are. It is a fork in the skill's place with nothing to fork from: a branch of its own in the account repo, `skills/<name>`, whose first commit holds the skill as it is and carries a new fork id, the skill's directory moved into that branch's worktree, and the library symlink to it. Nothing is fetched, and the skill has no upstream. The skill is looked for in the library first: an entry no branch records is adopted in its place, and every placement is left as it is, since placements name the library path. When the library holds no skill of that name, the skill is a real directory in an agent client's own skills directory: it moves into the library, and a symlink to the library takes its place, as a placement, except in the directory of a universal client, which reads the library and needs none. An identical directory of that name in another agent configuration is replaced the same way, and directories that differ refuse the adoption, since only one of them can become the skill. Either way the directory is moved, in one journaled mutation.

`agentx skill fork` no longer accepts an unmanaged skill, in its place or under a new name: it refuses, and names the adopt command. A fork is made of a skill agentx manages or a plugin provides, and adopt is the one command for a skill agentx does not manage yet, whether or not another tool recorded it. The hints that sent an unmanaged skill to fork, those of a publish, a history, a diff with `--commit`, a rename, a placement on the cloud machine and an install over a name the library holds, send it to adopt.

A skill another tool recorded is adopted the same way when its record names nowhere agentx can install it from: a source that is no git repository, a repository Skillshare tracks as a whole, no source agentx can read, or a path that is not a directory of a repository. With nothing to install it from, such a skill is as unmanaged as one no tool recorded, and the folder this machine holds of it becomes one of the user's own skills. Every form of the command does this, `--skill`, `--all` and a run that names a tool. There is one kind of skill that is ready to adopt, and its record decides how it is adopted: no flag does, and neither does the way the command was called. A record that names a source is always installed from it, as [ADR 0012](0012-adopt-installs-from-the-source-and-replaces-what-the-other-tool-left.md) decided, and what the other tool left gives way to that version. A record whose name is already one of the user's own skills is managed, and no run acts on it. This amends ADR 0012, which kept an edit by forking the skill before adopting it: the directory the other tool left is unmanaged, so that fork is now refused.

The preview, `agentx adopt` with no flag, lists every unmanaged skill of the machine, the ones no tool recorded included: by name under `Ready to adopt` the ones a run would adopt, and under `Cannot adopt` the others, each with a reason in plain words that says what to do. `agentx adopt --all` adopts everything under `Ready to adopt`, lists the skills it could not adopt under `Could not adopt`, each with the same plain reason, and exits 0: the user asked for whatever can be adopted, and the preview said which skills cannot be and what to do about each. A real failure still fails the run, with its own exit code: a source that cannot be reached, an install that fails, the lock another command holds. `agentx adopt --skill <name>` for a skill that cannot be adopted fails with exit code 6, a message and a hint, since the user asked for that skill. Given the name of a tool, the preview and `--all` cover that tool's records alone. A skill no tool recorded has no `adoption` event, which is one record of another tool, in a preview or in a run: adopting it reports the skill as the library now holds it.

## Considered and rejected

Keeping `skill fork` for unmanaged skills beside the new adopt: two commands would do one job, every hint would have to choose between them, and the user would have to know whether another tool recorded a skill before knowing which to run. Fork also only ever reached a library entry, never a directory in an agent client's own skills directory. An `adoption` event for a skill no tool recorded: the event is one record, with the tool and the file it was read from, so a skill without a record would need a change to the output schema, for a list a program already reads from the inventory. The preview's text lists such skills and its summary counts them. Copying the directory out of the agent client's skills directory instead of moving it: the client would keep reading its own copy, which agentx does not manage, beside the adopted skill, and an edit made there would never reach the skill; a move leaves one copy, and a symlink where the client looks for it. A flag to keep a recorded skill's files, adopting it as it is where its record could install it: one skill would have two outcomes, a skill of its source that agentx updates or one of the user's own with no upstream, chosen by a flag the user has to know of before the first run, and a wrong choice is not undone by running the command again. The record decides instead, and only a skill there is nothing to install from is adopted with its files as they are. A group of its own in the preview for those skills, apart from `Ready to adopt` and with a word of its own for adopting them: the user would have to learn a second word for adopting, and which command covers which group, for a difference that changes nothing they do next. Adopting such a skill only when `--skill` names it, while `--all` and a run that names a tool refuse it: `--all` would leave behind skills the preview calls ready, and end in a failure over a skill nothing is wrong with. Failing `--all` over a skill that cannot be adopted: the preview already says so and what to do, so the run would end in a failure the user was told of beforehand, every run after it would fail the same way until the user moved that skill, and a script could not tell it from a source that could not be reached.

## Consequences

A skill adopted out of an agent client's own skills directory becomes visible to every universal client, since they read the library, where before only that client saw it. No other agent configuration gets a placement by the adoption; `agentx skill place` makes them.

A user who wants to keep an edit made to a recorded skill agentx can install has to copy it by hand before adopting: the directory copied under another name is an unmanaged skill, which `agentx adopt` adopts with its files as they are, and the adoption of the recorded skill then replaces the original with the version its source holds.

`agentx adopt --all` changes skills no tool installed: every folder the preview lists under `Ready to adopt` becomes one of the user's own skills, and one in an agent client's own skills directory moves into the library. A skill adopted with its files as they are has no upstream, so it gets no updates from the place the other tool installed it from.

Once a recorded skill is adopted with its files as they are, the other tool's record stays, since agentx never writes that tool's files. Every later preview lists the skill under `Already managed by agentx`, and no run acts on it. A skill there is nothing to install from that the library holds as a symlink, as Skillshare leaves one, is listed under `Cannot adopt`: agentx adopts folders only, and the user moves the folder the link leads to into the library first.

A folder that holds a `.git` of its own is listed under `Cannot adopt`: moved into a worktree, it would take that repository with it, and git would find that repository and not the skill's branch. The user moves the `.git` out first.

`agentx adopt --all` exits 0 while skills it could not adopt are left. A script that needs to know reads the `log` warnings, one per such skill, or the `refused` adoption events of the recorded ones.

An unmanaged skill whose name breaks the Agent Skills name grammar is listed under `Cannot adopt`: adopt has no flag to give it another name, so the user renames the directory by hand first. `agentx skill fork <name> --name <new>` used to do that for a library entry.

An adoption out of an agent client's own skills directory that is interrupted after the directory moved leaves that client without the skill until the journal is recovered, which the next agentx command that changes anything does.
