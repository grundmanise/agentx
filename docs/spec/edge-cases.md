# Edge cases agentx does not handle specially

agentx is built for realistic skills: folders of Markdown and text files, maybe scripts, images and small subfolders. The cases below get no handling of their own: agentx leaves them to git's own behaviour or fails with a generic error, and loses nothing.

- A skill file with lines of its own that look like conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`): a conflicting `skill update` leaves git's markers at git's default size in the pending merge's worktree, so such a line and a marker look alike there. agentx never reads the markers.
- A file that conflicts for a reason other than its lines, such as a binary file, a file executable on one side only, a symlink meeting a file or a file moved to two places: `skill update` lists it with the words `git status` uses for the versions it has, `both modified` or `added by us` say, and nothing more. `git status` in the worktree says the rest.
- A tracked file or folder of a managed skill whose permissions were changed, a file made `0600` say: `skill update` lays the new version out with `0644`, or `0755` for an executable file and for a folder, less the umask, as `skill revert` does. Files git ignores keep their mode.
- A clean or resolved merge that holds two paths differing only in case, a `readme.md` you added and a `README.md` the update adds, on a file system that ignores case, as macOS and Windows do by default: `skill update` fails with the library error, exit code 6, and changes nothing. Rename the file, then update again.
- An import branch an earlier agentx stored in an older form, under a library directory that holds exactly that version: `skill update` merges it as it merges an edited skill. The files it lays out are the same, and the result says `merged its edits cleanly`.
- A new version that cannot be written to disk, a file name longer than the file system allows say, in `skill update --all`: the whole run fails with the library error before a journal is written, and no skill is updated.
- A skill with a merge pending that a check made before the lock answers for first: `skill revert` of a skill whose library directory already holds its base version says so and exits 0, and `skill update` of a skill whose source was removed, or that the last check found removed upstream, gives that answer rather than applying the merge or listing what is left of it. `skill revert` and `skill remove` read the pending merge under the lock only, and nothing is changed either way. Add the source again, or give the merge up with `skill update <name> --abort`.
- The registration of a pending merge's worktree unlocked by hand with `git worktree unlock`, whose directory is gone: the next command that changes anything no longer removes it; `git worktree prune` does.
- An agentx home moved elsewhere while a merge is pending: git records the worktree by its absolute path, so the moved worktree no longer finds the account repo, and `skill update <name>` fails with git's error, exit code 8, every time. Another command that changes anything removes the leftover; `skill update <name> --abort` does too, then says no merge is pending. Update again afterwards to leave the merge pending anew.
- A library directory edited while its merge was pending, by any tool: `skill update` does not merge the edit into the resolved merge. It refuses with exit code 6 and keeps the worktree; `skill update <name> --abort` and then `skill update <name>` merge the edit afresh.
- A pending merge given up with `skill update <name> --abort` while another `skill update <name>` is already applying it: the update applies what was resolved, as though it had finished before the `--abort`.
- A pending merge with no merge in progress in its worktree, given up there with `git merge --abort`, left half set up by an update that was killed, or with a commit you made on top of the merge commit: `skill update` reports it pending with the files still unmerged, often none, exit code 4, until `skill update <name> --abort` gives it up.
- A pending merge resolved to a version with no `SKILL.md`: `skill update` applies it as resolved and then fails with `the library holds no <name> after updating it`, exit code 10. The library directory keeps every other file, and `skill list` names the way out.
