# CLI contract

Status: accepted, 2026-09-18. Implements the output contract in ADR 0001 and the machine state layout in ADR 0004. The desktop app, scripts and tests depend on this document; change it together with the CLI.

## Invocation

`agentx [--json] [--verbose] [--color on|off] <command> [arguments]`. The three global flags are accepted before or after the command. `--json` switches stdout to newline-delimited JSON events. `--verbose` raises the log level on stderr to debug. `--color` decides whether text output carries ANSI colour, see [Streams](#streams); any other value is a usage error. `agentx help`, `--help`, `-h` and a bare `agentx` print usage and exit 0; the usage text goes to stdout, or to stderr in JSON mode. A bare `agentx --json` is a usage error instead: a script that omits the command has made a mistake.

The CLI reads its environment once, at startup, from the variables below. Beyond them, `PATH` locates git and the command of a local MCP server, and the [handshake](#handshake) hands the environment on to the servers it starts.

| Variable | Meaning | Default |
|---|---|---|
| `AGENTX_HOME` | agentx home | `$HOME/.agentx` |
| `AGENTX_LIBRARY` | the library | `$HOME/.agents/skills` |
| `HOME` | the user's home; agent client paths derive from it | required |
| `XDG_CONFIG_HOME` | where agent clients keep user-scope configuration | `$HOME/.config` |
| `XDG_STATE_HOME` | where the vercel skills CLI keeps the lock file [`agentx adopt`](#adoption) reads | unset; the `.agents` location below is then the one that tool writes |
| `AGENTX_PLATFORM_ID` | the platform id the machine id is derived from; set it empty to declare that the machine has none | the operating system's platform id, see [Machine identity](#machine-identity) |
| `AGENTX_HOSTNAME` | the default machine label | the operating system's hostname |
| `AGENTX_INSTANCE_ID` | the `instance_id` carried by snapshots, so a script can fix it | a fresh random id per process |
| `AGENTX_HANDSHAKE_TIMEOUT` | the budget of one MCP handshake, a duration such as `500ms` | `10s` |

## Streams

Without `--json`, stdout carries aligned text and stderr carries log lines as `level: message`, with `error: <message>` and `hint: <fix>` for a failure. A `warning:` can have a second line right under it, indented by two spaces, that says what to do (the warning for a kept copy under **Placements** does); with `--json` it is still one `log` event, whose message is the two lines joined by `; `. A table pads every column to its widest cell with two spaces between columns and nothing after the last cell. A row that reports a state starts with a glyph: `✓` ok, `!` warning, `✗` failure, `•` information. A command that changes something confirms it on one line starting with `✓`; the wording is the command's own.

Text output is coloured per stream when that stream is a terminal, the `NO_COLOR` variable is not set (see no-color.org) and `TERM` is not `dumb`; `--color on` colours a pipe too, and `--color off` colours nothing. Colour is added by SGR escape sequences around the text and changes nothing else: stripping the sequences gives the exact text a pipe receives, alignment included. JSON output is never coloured, whatever `--color` says. The palette has one meaning per colour: bold for a heading or the name that starts a row, cyan for the key of a key-value row and for a command or flag name, dim for secondary detail, green for ok and enabled, yellow for a warning, a hint and disabled, bold red for a failure and an error, blue for information, magenta for a `(plugin <name>)` marker, cyan for a count such as `12 tools`.

Text agentx did not write is sanitised before it is printed: every control character becomes a space, runs of spaces become one and the leading and trailing ones are dropped. That is a skill's name and description, which the repository a source was added from supplies; the name of a directory in the library or under a client's configuration, which whoever made the directory chose; the command line, the URL and the version a configuration file or a plugin manifest declares; and whatever agentx relays of what something else said, such as the stderr of a git it ran, which carries the messages a server sent it. A control character is one of the 65 characters Unicode names as such: the C0 controls `U+0000` to `U+001F`, `DEL` at `U+007F`, and the C1 controls `U+0080` to `U+009F`, which a terminal obeys as readily as the C0 ones. Nothing above `U+00FF` is covered: a format character such as a bidirectional override or a zero-width joiner is printed as it is, being what several writing systems are spelled with and what an emoji sequence is joined with. A value carrying a newline therefore cannot break the one row per item a listing prints, a tab cannot disturb a column, a carriage return cannot overwrite the line already printed, and no escape sequence reaches the terminal, whatever `--color` says. Nothing is parsed: agentx does not recognise an escape sequence and strip it whole, since a parser that misjudged one sequence's end would let the rest through, while a rule that admits no control character at all cannot; what a sequence leaves behind once its `ESC` is a space, the `[31m` of a red, prints as the ordinary text it is.

A diff is printed rather than sanitised, being text a reader reads for its layout: `agentx skill diff` prints the lines git wrote as they are, a file's own bytes included, a byte that is not valid UTF-8 among them, with every control character but the tab turned into a space of its own. So is a byte from `0x80` to `0x9F` that is no part of a UTF-8 character, which a terminal set to 8-bit controls reads as a C1 control, `0x9B` being the one-byte form of the escape that starts a sequence; every other byte that is not valid UTF-8 is printed as it is. No escape sequence reaches the terminal, and every space and every tab of an indentation stays where it was. Its `diff` events carry the patch git wrote, and the path, as JSON strings, and every string of an event is UTF-8: a byte that is not valid UTF-8 arrives as `U+FFFD`, as it would in any other event. The `patch` of a file that is not UTF-8 text, and the `path` of a file whose name is not UTF-8, are therefore there to be shown and cannot be applied byte for byte.

A path is quoted rather than sanitised, being text a reader copies: a space where a control character was names nothing on disk and says nothing about why. A path carrying one is printed whole in double quotes, with `\a`, `\b`, `\t`, `\n`, `\v`, `\f`, `\r`, `\"` and `\\` for the bytes that have a letter of their own and `\NNN` in octal for the rest, which is what git prints for such a path under `core.quotePath` and what a reader already knows from `git status`. A path carrying no control character is printed as it is, non-ASCII included.

Every line agentx puts on stderr (`warning:` and the line under it, `hint:`, `error:` and the hint under it, `debug:`) is sanitised as it is written, whoever composed it: a message is plain text by then, agentx painting only the word that starts it, so one rule at the one exit covers every command that relays what something else said. A value that goes into a table cell on stdout is sanitised where the cell is built instead, a cell being free to carry the sequences agentx painted it with. Either way it happens before anything is painted, so the rule above still holds: stripping the SGR sequences agentx adds gives the exact text a pipe receives. JSON output is not sanitised, its values being escaped already, so a consumer reads what the source wrote: a `source_skill` event carries the name and the description as the `SKILL.md` frontmatter holds them, byte for byte, which is what lets whoever reads the events show the state of the files on this machine.

With `--json`, stdout carries only events, one JSON object per line, and nothing else. Stderr carries log events in the same envelope. A consumer reads the exit code before trusting either stream.

## Event envelope

Every event is one JSON object with at least:

| Field | Type | Meaning |
|---|---|---|
| `type` | string | the event type |
| `schema_version` | integer | the output schema version, currently `1` |

`schema_version` changes when an event changes incompatibly. A consumer refuses a CLI whose schema version it does not know. A field added to an event, and a value added to a field this document says will gain more, are not such a change and leave the version where it is: a consumer ignores a field it does not know, and shows such a value it does not know as it is written.

## Event types

Every run emits exactly one `result` as its last stdout event, after any `error`.

| Field | Type | Meaning |
|---|---|---|
| `cli_version` | string | the CLI version, `dev` for an unreleased build |

`settings`, emitted by every `agentx config` command and, as its first event, by `agentx import`:

| Field | Type | Meaning |
|---|---|---|
| `settings` | object | the machine settings as they now are, in the shape of the settings file below, with `label` filled in from the hostname when it is not set |

`machine`, emitted by every `agentx machine` command:

| Field | Type | Meaning |
|---|---|---|
| `id` | string | the machine id, 32 lowercase hex characters |
| `label` | string | the machine label |
| `derivation` | string | `platform` when the id is derived from the platform id, `random` when it comes from `machine.json` |

`source`, emitted by every `agentx source` command, one per source (see [Sources](#sources)), and by `agentx skill add` for the source it installs from:

| Field | Type | Meaning |
|---|---|---|
| `id` | string | the source id, 16 lowercase hex characters |
| `url` | string | the canonical URL |
| `alias` | string | a second URL mapped onto the canonical one; absent until aliases exist |
| `pin` | string | the ref the source is pinned to; absent when it follows the remote's default branch |
| `subpath` | string | the directory the command's listing was scoped to; absent for the whole repository, never stored |
| `last_fetched` | string | when the source was last fetched, RFC 3339 in UTC; absent from the event of `source remove` |
| `commit` | string | the fetched commit; absent when the account repo holds no ref for the source |
| `previous_commit` | string | what the source ref held before this fetch; absent when the fetch did not move it and when the source is new |
| `skills` | integer | how many skills the listing found; present after `add`, `fetch`, `skills` and `skill add`, absent from `list` and `remove` |

`source_skill`, emitted by `agentx source skills`, one per installable skill, after the `source` event, sorted by `subpath`:

| Field | Type | Meaning |
|---|---|---|
| `source` | string | the source id |
| `subpath` | string | the skill directory from the repository root, `""` when the root itself is the skill |
| `name` | string | the frontmatter `name`, else the directory name (the repository name for the root) |
| `description` | string | the frontmatter `description`, `""` when it has none |
| `tree` | string | the tree id of the skill directory at the fetched commit |

`progress`, emitted by a command that does one thing several times, one event per step as that step ends:

| Field | Type | Meaning |
|---|---|---|
| `phase` | string | what the step did, one word per kind of step the command has: `fetch` for one source of `agentx source fetch` and for one source `agentx adopt` has to add; `blobs`, `import` and `install` for one skill of `agentx skill add`; `place` for one skill of `agentx config enable --place-all`; `adopt` for one skill of `agentx adopt`; and `rescan` for the reading of the affected configurations that ends such a run |
| `subject` | string | what the step was about: the source's canonical URL for a fetch, the skill's library name for a step of an install; absent for a step that covers the run as a whole, such as the rescan |
| `current` | integer | how many steps have ended, this one included, so that one run counts from 1 to `total` |
| `total` | integer | how many steps the run has in all; absent when the run does not know that in advance. A run that gives up on part of its work takes the steps it will no longer run out of `total`, so a run that ends still emits a last event whose `current` is its `total` |

A step is reported when it ends rather than when it starts, so that `current` is the count a progress bar needs and a run emits one event per step however it schedules them. Steps taken in parallel end in the order the network decides, so the order of the subjects is not fixed and is not the order the run reports its results in; each event says on its own what it covers, which is what a consumer reads. The event carries no outcome: a step that failed is a `log` warning, and the `error` and `result` events name what failed.

`library_skill`, emitted by `agentx skill list`, one per directory of the library sorted by name; by `agentx skill add`, one per skill it installed; by `agentx skill place`, one for the skill it placed; by `agentx skill remove --from <configuration>`, one for the skill whose placements it took away, and none at all when the skill left the library, as it does with `--from universal`; by `agentx skill revert`, one for the skill it reverted; and by `agentx config enable --place-all`, one per directory of the library sorted by name. Everywhere but `skill list` and `skill revert` its `placements` are those the rescan found in the configurations that command covered, so a universal client the command did not cover, a disabled one or one `--to` left out, is not among them; `universal` names every universal client, whichever command emits the event. A [snapshot](#snapshot) carries the same object, without `type` and `schema_version`, for every skill of the library under `library`, so the desktop app and a script are told the same thing about a skill:

| Field | Type | Meaning |
|---|---|---|
| `name` | string | the library directory name, which is also the name of its branch in the account repo |
| `kind` | string | `managed` for a skill with an import branch, `fork` for one with a branch in the fork namespace, `unmanaged` for one with neither |
| `source` | string | the canonical URL of its upstream, from the lineage trailers; absent when the skill has none |
| `subpath` | string | the skill's directory in that source, `""` for its root; absent with `source` |
| `upstream_commit` | string | the upstream commit of the version: the last commit of the source that touched the skill's directory when it was read; absent with `source` |
| `base_hash` | string | the content hash of the base version, from the import commit's trailer; absent with `source` |
| `content_hash` | string | the content hash of what the library directory holds now |
| `state` | string | `current` when the library directory holds exactly its base version, `modified` when it was edited since, by any tool; present for a managed skill alone, since a fork's base is decided by its own history, which this command does not read. The two are told apart by tree id, the one way agentx compares a directory with a base version: the directory is read in process as git would record it, every entry with `lstat` and never followed, a regular file as a blob of mode `100644`, or `100755` when its owner may execute it, a symlink as a blob of mode `120000` holding its target, a directory as a tree and an empty one left out, in git's order and with git's object headers, nothing ignored and nothing filtered; its tree id, wrapped under the upstream's own directory name the way the [import commit](#skills) wraps it, is compared with the tree of the import commit the branch points at, which the one `for-each-ref` that reads the lineage reads as well, so the comparison runs no git of its own. A directory holding something git cannot record, a `.git` component in any case or anything that is neither a file, a directory nor a symlink, and one that cannot be read whole, is `modified`. A mode and a link are content: a file made executable, a file replaced by a symlink to the same bytes and a symlink leading out of the skill are edits, which `content_hash` does not see, since it reads neither modes nor links out of the skill; `content_hash` and `base_hash` stay the names of the two versions and decide nothing here. It is what the base version can tell on its own: whether an upstream moved is not computed here, and every other way the skill has drifted is in `drift` |
| `drift` | array of strings | the drift states the skill is in beside its `state`, sorted; absent when it is in none, and always for a fork and an unmanaged skill. `displaced` and `missing` say what the placements are, read at each configuration's own place, `<the client's own skills directory>/<name>`, and nowhere else, for every enabled configuration whose client does not read the library: `displaced` when one holds a real directory where agentx keeps a symlink, which is what an installer that copies over links leaves, or the symlink naming the library directory where `copy_mode` records a copy; `missing` when one holds nothing at all, whether the skill was never placed there, `--to` having left it out, or its placement went, by `--from` or by hand. A client that sees the skill through another client's skills directory, as Cursor reads Claude Code's, is still missing it. A disabled configuration and a universal client are never either: the one is a configuration the user chose not to place into, and the other's placement is the library entry itself. A symlink of the user's to anywhere else takes the place, and so does a copy whose content is not the library's, which is still the copy (see **Placements** under [Skills](#skills)), and anything else at the path: the skill is not missing there, and nothing agentx keeps was displaced. Both are information: they never fail a command and change no exit code. The third is `source removed`, when the canonical URL its `Agentx-Source` trailer names is the `url` of no source entry in the [machine settings](#machine-settings), because the source was removed with `source remove` or was never added on this machine. It is derived on every read from the lineage and the settings and never written anywhere, and a source whose entry is there and whose ref the account repo does not hold is not removed: that is a source not fetched, which is what an import leaves. The coordinates stay as the lineage has them, since they are still where the skill came from and what adding the source again needs. The drift states are a list beside `state` rather than more values of it because each answers a question of its own and any of them can hold together with `current` or `modified` and with one another: a skill edited by hand whose source was then removed is `modified` and `source removed`, and one word would hide the other. The drift states still to come, such as an upstream that no longer holds the skill, join this list. A fork is not `source removed` when the source of its third-party upstream goes: the source that matters to a fork is the account remote it is published to, not the upstream it merges later versions from. An unmanaged skill has no source at all. Every drift state is derived on every read; [serve](#serve) emits a `drift` event when one changes. A managed branch whose library directory is gone has no entry, and so no drift at all: a warning names it instead, see **Listing** under [Skills](#skills) |
| `placements` | array | one object per way a configuration sees the skill, sorted by `configuration` then `path`: `configuration`, `path`, `mode` (`symlink`, `copy`, or `library` for a client that reads the library directly) and `kind` (what is on disk now, the `kind` of the occurrence in a snapshot, or `library` for the library entry itself) |
| `universal` | array of strings | the id of every universal client detected, by the rescan of the command that emits the event or by the scan a snapshot comes from, a configuration whose client reads the library directly, `reads_library` in a snapshot, sorted by id: each one sees the skill through the library entry whatever its enabled state and whatever `--to` named, so it is listed whether or not a command placed into it; `[]` when none is detected, a client that is not installed seeing nothing |

`diff`, emitted by `agentx skill diff`, one per file of the skill that differs between the two versions it compares, sorted by path (see **Comparing with the base** under [Skills](#skills)):

| Field | Type | Meaning |
|---|---|---|
| `name` | string | the skill's library name |
| `path` | string | the file's path relative to the skill's directory, with `/` as the separator, as the tree holds it; never inside the upstream's directory name the import tree wraps the skill in. A byte of the name that is not valid UTF-8 is `U+FFFD`, see [Streams](#streams) |
| `status` | string | what the library did to the file against the base: `added`, `modified` or `deleted`; a change of mode or of type, a file turned into a symlink or back, is `modified` |
| `patch` | string | the unified diff git wrote for the file, from its `diff --git a/<path> b/<path>` line to its last line, each line ending in a newline; a change of type is the two diffs git writes for it, the old content deleted and the new one added. A byte that is not valid UTF-8 is `U+FFFD`, so the patch of a file that is not UTF-8 text is for display, see [Streams](#streams) |

| Field | Type | Meaning |
|---|---|---|
| `path` | string | the file the document was written to, as the argument named it |
| `skills` | integer | how many lineage records it holds |

| `upstream_commit` | string | the commit the version was read from; absent with `source` |
| `base_hash` | string | the content hash of the base version the branch records; absent with `source` |

|---|---|---|
| `ok` | boolean | whether the command succeeded; the exit code is 0 exactly when it is `true` |

| Field | Type | Meaning |

`snapshot`, emitted by `agentx scan`, is described under [Snapshot](#snapshot).

`configuration`, `mcp_server`, `plugin` and `skill` are node types carried inside `snapshot` and no command emits them as events of their own; the `skill` node is one content version found anywhere on the machine with its occurrences, and no event carries it. The entries of a snapshot's `library` are not nodes: each is a `library_skill` without its envelope. `doctor` is described under [Doctor](#doctor), `adoption` under [Adoption](#adoption), and `refresh_complete`, `search` and `drift` under [Serve](#serve). The types `reconcile`, `update_available` and `conflict` are named for later commands and not emitted yet; `operation` and `fleet` are reserved and never emitted.

## Exit codes

| Exit | Code | Meaning |
|---|---|---|
| 0 | `ok` | success |
| 1 | `usage` | a usage error: unknown command, bad flag, missing argument or a required environment variable not set |
| 2 | `git` | git is missing or older than 2.40 |
| 3 | `source` | a source is unreachable or authentication failed |
| 4 | `pending_merge` | a pending merge blocks the action |
| 5 | `not_found` | a skill, source or configuration was not found |
| 6 | `refused` | a collision or an unmet precondition |
| 7 | `locked` | another agentx command holds the lock |
| 8 | `account_repo` | the account repo is unusable: missing, corrupt, or a repository format this git cannot read |
| 9 | `interrupted` | a stop signal ended the run before it finished, see [Stopping a run](#stopping-a-run) |
| 10 | `internal` | an internal error, including a settings file or a vercel skills lock file agentx cannot read |

In JSON mode the `error` event carries the code as its `code` field.

## Stopping a run

`SIGINT` and `SIGTERM` stop a run. The first one cancels it: every git child of the run is killed, the command unwinds through its own error path, and the run reports `interrupted` with exit code 9, an `error` event and the terminating `result` like any other failure, rather than dying silently where it stood. That answer stands in for whatever the command was about to report, since a run whose git was killed reports how it died rather than what was wrong, so the hint sends the reader to `agentx doctor`, which names every kind of state a stop can leave (an unfinished [mutation journal](#mutation-journal), a remote no source names, the staging refs of an install), each with its own repair. A second signal of either kind restores that signal's default and raises it again, so a run that does not stop is killed exactly as it was before there was a handler; that is the crash the [mutation journal](#mutation-journal) is built for, and nothing about the graceful stop replaces it. A signal the process was started with ignored is left ignored, so a job a shell runs in the background, which inherits `SIGINT` ignored, is not stopped by a Ctrl-C meant for the job in the foreground.

agentx never cuts a mutation short itself. The ref steps of a mutation journal, and of the recovery a later command runs before its own work, run on a context the cancellation is taken off: by the time they reach git the journal that describes them is on disk, so giving up would leave a half-applied journal for the next command and save nothing. Everything else the run does keeps the cancellation, so a stop before the journal exists gives up at once and leaves nothing behind. An install that had already written its import commits also takes its staging refs away on that same context, so a stop does not leave the refs [Doctor](#doctor) reports as `staged_imports`.

A signal sent to the whole process group is the one case that cannot cover, and it is not meant to. A terminal's Ctrl-C signals the whole foreground process group, a supervisor may signal the group rather than the process it started, and the desktop app cancels a run by killing its whole process tree ([ADR 0001](../adr/0001-go-cli-owns-machine-and-account-tauri-renders.md)). In each of these the git of a ref step receives the signal directly and dies whatever context agentx ran it on. Nothing is lost by that. The ref updates of a journal are one `update-ref` transaction, which commits or does not, the journal stays on disk, the next command that takes the lock finishes it, and the run still reports the stop with exit code 9. It is the crash boundary the journal is built for, reached by a different route. A signal sent to the agentx process alone, such as one from a supervisor that signals only the process it started, is the case the paragraph above covers whole.

A run that was stopped but still finished everything it was asked to do exits 0 with its ordinary output: the signal arrived after the last step that could fail and changed nothing, and a run that did the work reports that it did. `agentx serve` ends on a cancelled context by design and exits 0 as it always did.

## Agentx home

Everything the CLI keeps on the machine lives under agentx home. Durable entries survive a reinstall when the directory is retained; transient entries coordinate running commands; derived entries are rebuilt from what the machine already has.

```
~/.agentx/
  account.git/        durable   bare account repo: skills/<name> forks, managed/<name> import branches,
                                refs/agentx/merge/<name> pending merges, refs/agentx/candidate/<name>
                                update candidates, refs/agentx/sources/<id> the last fetched state of each
                                source, refs/agentx/fetching/<id> where a fetch of that source stages until
                                it is whole (see Sources), refs/agentx/importing/<run>/<n> where the import
                                commits of one skill add wait until its journal points the branches at them
                                (see Skills)
  worktrees/<name>/   durable   one linked worktree per placed fork
  settings.json       durable   machine settings
  mutations/<id>.json durable   local mutation journal, kept until completion or recovery; the content it
                                stages waits in mutations/<id>.staged next to it, and a library directory
                                or placement it stages or retains waits in a hidden directory beside that
                                live path (see Mutation journal)
  sync.json           durable   fleet upload protocol metadata; reserved, nothing writes it today
  ops/<ulid>.json     durable   operation records; reserved, nothing writes them today
  version             transient mutation counter, rewritten last by every mutating command
  lock                transient advisory lock: shared for local scans, exclusive for mutations and recovery
  serve.lock          transient advisory lock held by the one serve child of this home for its lifetime
  machine.json        derived   the machine id, only where no platform identity exists
  handshakes.json     derived   last MCP signature per server
```

No agent client reads anything in agentx home except the fork worktrees, through symlinks from the library. There is no logs directory: logs go to stderr. Temporary worktrees for editor sessions live in the operating system's temporary directory.

## Machine settings

`settings.json` in agentx home holds what only this machine decides. It is read whole and written by temp file, fsync and rename while the lock is held. A missing file means defaults. An unreadable file is exit code 10 with a hint naming the path.

`agentx config list` prints every setting, `agentx config get <key>` one, and `agentx config set <key> <value>` changes `label`, `auto_push` or `accept_operations`; the booleans take `true` or `false`. A label is one non-empty line of at most 256 bytes carrying no control character, which is the rule every route to it is held to: `config set label`, `machine rename` and the label an import restores. An unknown key, a key that `config set` cannot change, or an invalid value is exit code 1 with a hint listing the keys. Without `--json`, `list` prints a `key  value` table, showing an empty value as `(none)`, `get` prints the bare value, and `set`, `enable` and `disable` print one confirmation line: `✓ <key> is now <value>`, `✓ <id> is now enabled` or `✓ <id> is now disabled`.

`agentx config disable <id>` adds a configuration id to `disabled_configurations` and `agentx config enable <id>` removes it; both are mutations, both are no-ops when the list already has the wanted state, and both emit the `settings` event. The id must name a detected configuration (see [Snapshot](#snapshot)), else exit code 5 with a hint listing the detected ids. A detected configuration is enabled unless it is listed, so every configuration is enabled on first detection without a write.

`agentx config enable <id> --place-all` also places every skill the library holds into that configuration, as [`agentx skill place`](#skills) would one at a time without `--copy`, so a configuration `copy_mode` records for a skill gets a copy of it and every other placement is a symlink; without the flag, enabling only decides where later installs go and places nothing. `--place-all` belongs to `enable` alone: `config disable --place-all` is exit code 1. The settings write and every placement it implies are one journaled mutation, since they are one thing the user asked for and an interrupted run may not leave a configuration enabled with half the library in it: the next command finishes that journal rather than undoing it. A placement the run skips is another matter and does leave part of the library placed, which the output and the `result` say. A placement path holding something agentx did not put there is left alone and skipped exactly as it is during an install: what is refused is a placement and not a skill, so the run still succeeds, the other skills land, the path is one `warning:` line naming it and the `result` counts it. A copy `copy_mode` records for the configuration that does not hold the library's version is kept and skipped the same way, with the two-line warning an install gives it, whose second line names the commands that replace it with the library version. The settings event comes first, then one `progress` of phase `place` per library skill, then the `rescan`, `total` being `<skills in the library> + 1`, then one `library_skill` event per library skill in name order with the placements the rescan found in this configuration. A configuration whose client reads the library has nothing to place: it already sees every library skill, and the run says so rather than making a second entry, in the output and in the `result` both, neither of which reports a placement it did not make.

```json
{
  "schema_version": 1,
  "label": "my-laptop",
  "auto_push": false,
  "accept_operations": false,
  "disabled_configurations": ["windsurf"],
  "sources": [
    {
      "url": "https://github.com/example/skills",
      "alias": "https://github.com/example/skills-old",
      "pin": "v1.2.0",
      "last_fetched": "2026-09-18T10:00:00Z"
    }
  ],
  "copy_mode": {
    "my-skill": ["cursor"]
  }
}
```

| Key | Meaning |
|---|---|
| `schema_version` | the settings schema version, currently `1` |
| `label` | the machine label; absent until set with `config set label` or `machine rename`, and reported as the hostname meanwhile |
| `auto_push` | whether published forks are pushed automatically |
| `accept_operations` | reserved; whether this machine executes operations queued for it |
| `disabled_configurations` | configuration ids the user took out of the default set for explicit placements, sorted; every other detected configuration is enabled |
| `sources` | each source by canonical `url`, sorted by it, with optional `alias` (a second URL mapped to the canonical one; reserved, nothing sets it), optional `pin` (the ref the source is held at, absent when it follows the remote's default branch) and `last_fetched` (RFC 3339 in UTC); written by `source add`, `source remove` and `source fetch`, which rewrites `last_fetched` alone, and by `skill add` when it adds or fetches the source it installs from, as `source add` does, see [Sources](#sources) |
| `copy_mode` | skill directory name to the configuration ids that receive a copy instead of a symlink, sorted; written by `agentx skill add --copy` and `agentx skill place --copy`, one write per run, and by `agentx skill remove`, which takes out the configurations it no longer places the skill in, whether it deleted a placement there or found none, and the whole entry when the skill leaves the machine. A skill with no copy anywhere leaves no entry behind |

Git config in the account repo holds only what git owns: remotes and tracking branches.

## Machine identity

The machine id names one computer across reinstalls. It is derived, in this order:

1. When `machine.json` exists in agentx home, its `id` is the machine id and the derivation is `random`. The file is `{"id": "<32 lowercase hex characters>"}`.
2. Otherwise, when a platform id exists, the machine id is HMAC-SHA256 with the key `agentx-machine-id/v1` over the message `<platform id> LF <uid>`, where `LF` is one newline byte and `<uid>` is the numeric user id in decimal, rendered as the first 32 lowercase hex characters of the MAC. The derivation is `platform`. The platform id is `AGENTX_PLATFORM_ID` when the variable is set, else the content of `/etc/machine-id` without surrounding whitespace on Linux, else `IOPlatformUUID` from `ioreg -rd1 -c IOPlatformExpertDevice` on macOS.
3. Otherwise 16 random bytes are generated once, under the lock, stored as hex in `machine.json`, and used from then on as in 1.

`agentx machine` prints the id, the label and the derivation. `agentx machine rename <label>` sets the label in the settings file. `agentx machine reset-id` writes a new random id to `machine.json`; from then on the id is random even where a platform id exists, until the file is deleted. Without `--json`, `machine` prints a `key  value` table with the rows `Machine id`, `Label` and `Derivation`, and the two mutations print one confirmation line: `✓ machine label is now <label>` or `✓ machine id is now <id>`.

## Lock and version file

Every command that changes agentx home takes an exclusive advisory `flock` on `lock` in agentx home without waiting, recovers any unfinished [mutation journal](#mutation-journal), does its writes through a journal of its own, rewrites `version` as its last step and releases the lock. `version` holds one decimal integer and a newline, incremented on every successful mutation (a missing file counts as 0); it is a change signal for watchers, not an ordering of snapshots. A command that finds the lock held exits with code 7 and a hint naming the lock file after at most 50 ms of retrying; it never waits for the holder. The one exception is a **take-back**: a command undoing, under a later hold, a write an earlier hold of its own already made. Giving up there would leave that write behind for good, since the lock is exactly what the command needs to clean up after itself, so a take-back waits for the holder for up to five seconds before it gives up – long enough for a queue of ordinary mutations, each of which holds the lock for one file write, and short enough that a lost lock never becomes a hang. A take-back leaves `version` untouched, like any step whose change nothing watching agentx home ever saw. While it holds the exclusive lock, a command keeps its process id in the lock file, so `agentx doctor` can name the holder. A failed mutation leaves `version` untouched. `agentx scan` holds a shared `flock` on the same file while it reads settings, the lineage and the filesystem, retrying for up to one second while a mutation holds the exclusive lock and exiting with code 7 after that; it never writes `version`. With `--handshake` it releases the shared lock before it starts or connects to any server, and writes `handshakes.json` afterwards under the exclusive lock, again without touching `version`. Other reading commands do not take the lock, except for the one write that stores a random machine id; that write does not touch `version`. Taking either lock creates agentx home and its `mutations` and `ops` directories when they are missing; nothing writes into `ops` yet.

## Mutation journal

Every replacement of a state file in agentx home is journaled, so that a process stopped at any point leaves either the old file or the new one and a later command can tell which and finish the job. This covers `settings.json` (`config set`, `config enable`, `config disable`, `machine rename`, `source add`, `source fetch`, `source remove`, `import`), `machine.json` (`machine reset-id`, and the first command that stores a random machine id) and `handshakes.json` (`scan --handshake`). `version` is a signal, not state, and is rewritten atomically without a journal. Creating the account repo is not journaled: it builds the repository in a temporary directory and renames it into place.

An install changes more than state files: a lineage ref per skill, a library directory per skill and the placements that point at them. A removal and a later placement change the same kinds of thing the other way, and a revert replaces a library directory and the copies that held it. Those are journaled as `steps` in the same journal, one journal however many skills the run touches, each decided from the live state and safe to repeat, so that one interrupted run is finished rather than half undone. The `ref` steps go all together, first when the journal creates or moves them and last, after the state files, when every one of them deletes: a ref a journal writes can be written again from the journal, and one it deletes cannot be brought back once the journal is gone, so the deletions run only after everything that could still refuse has not. Between them go the path steps in the order they are recorded, then the state files. A removal that is refused therefore still has the skill's lineage, and abandoning its journal leaves a managed skill managed rather than turning it into an unmanaged one. A journal's refs of one repository are read in one call and moved in one transaction, so that a journal never holds some of its branches written and others not, and an install of thirty skills is two git processes for its refs rather than sixty. A step is `ref` (point a ref at a commit, with an expected old value, empty for a ref that must not exist yet; a `new` that is empty deletes the ref instead, still with the value it is expected to hold, so that a branch something else moved is refused rather than dropped; an `old` and a `new` that are the same commit move nothing and hold the journal to that commit, so that recovery finishes a change made for a version only while the branch still names it), `publish` (rename a staged directory into place), `link` (create a symlink placement) or `remove` (take a path out of the way, retaining what it held). Content a step stages or retains lives in a hidden directory beside the live path, `.agentx-staged-<id>-<n>` and `.agentx-retained-<id>-<n>`, not under agentx home: the rename that publishes or displaces it then stays on one filesystem, and discovery skips hidden entries, so no agent client sees a half-written skill. Retained content is dropped only once every live path holds its new state and it still hashes to what the journal captured; content that changed meanwhile is kept and named, as a `warning:` line on stderr giving both the live path and the hidden directory the content was kept in, since nothing else will ever mention it. A step whose live path already holds its new state does nothing and removes what it staged, since no later step will publish it and no journal will name it again: two configurations sharing one skills directory plan two publishes of one path, and the second of them is that step. A staging directory left by a process that stopped before its journal existed is swept by the next install, under the lock and after recovery; retained content is never swept. A command that refuses after staging content and before its journal exists removes what it staged, for the same reason: no journal names it, so the sweep of a later install into those same directories would be the only thing that ever could, and a copy staged in a client directory no later install targets would stay for good.

The journal cannot run git, so a command that mutates agentx home hands it what its `ref` steps need: reading the value of every ref it names, and moving them all in one transaction with their expected old values. Every command that writes has git, since git is the startup gate for all of them.

Under the exclusive lock the command writes the new content to `mutations/<id>.staged`, then the journal `mutations/<id>.json`, each by temp file, fsync, rename and directory fsync. Only then does it apply the steps, rename the staged files over the live files, rewrite the journal with `progress` `applied` and remove it. `<id>` is the Unix time in nanoseconds, `-` and four random bytes in hex, so journals sort oldest first. The journal is one JSON object:

| Field | Meaning |
|---|---|
| `progress` | `staged` until every live file is replaced, then `applied` |
| `replace` | the live files the mutation replaces, one entry each |
| `replace[].path` | the live file's absolute path |
| `replace[].old` | SHA-256 hex of the live file before the mutation, or `absent` when there was no file |
| `replace[].new` | SHA-256 hex of the staged content |
| `replace[].staged` | the staged file, next to the journal |
| `steps` | the changes outside the state files, in the order they are recorded, `ref` steps being applied before the rest; absent when the mutation has none |
| `steps[].kind` | `ref`, `publish`, `link` or `remove` |
| `steps[].path` | the live path of a `publish`, `link` or `remove` |
| `steps[].git_dir`, `steps[].ref` | the repository and ref of a `ref` step |
| `steps[].old` | what the step expects to find: for a path `absent`, `link:<target>`, `dir:<fingerprint>` or `other`; for a ref its object id, empty for a ref that must not exist |
| `steps[].new` | what the step leaves behind, in the same words; empty on a `ref` step deletes that ref |
| `steps[].staged` | the directory a `publish` renames into place |
| `steps[].retained` | where a `remove` keeps the content it displaced |

The fingerprint of a directory is SHA-256 over every entry below it in bytewise order of its relative path: the path, `NUL`, a kind and a length, `NUL`, then the file's bytes or the symlink's target. It is not the [content hash](#content-hash), which names a version of a skill: it names the bytes on disk, so that a directory rewritten by hand is never mistaken for the one the mutation captured.

Recovery runs under the exclusive lock and decides from what the live path holds, not from `progress`, since a process can stop after a write and before recording it. A step whose live path holds its `new` state is done; one that holds `old` is applied; one that holds neither was changed by something else, and both versions are kept: the journal stays and the command fails with exit code 6 (`refused`) naming the path. A live file whose hash is `new` is done: the journal, and a staged file still present, are removed and `version` is not bumped. A live file whose hash is `old` while the staged file hashes to `new` gets the staged file renamed over it, which bumps `version` once. A live file that matches neither was changed meanwhile: nothing is touched, the file, the staged content and the journal all stay, and the command fails with exit code 6 (`refused`) and a message that says `recovery required` and names the file and the journal, with a hint to restore the file's previous content and rerun, or to move the journal aside to keep the file as it is. A `.json` file under `mutations/` that is not a journal, or one whose staged file is missing or does not hash to `new`, is refused the same way. A step that cannot be applied at all, a directory that cannot be written or a path something else took, leaves the journal where it is and is exit code 6 (`refused`) with a message that says `recovery required` and names the step, its path and the journal: from the moment the journal exists every command recovers it before its own work, so a raw input or output message here would become every command's answer, with nothing in it to act on. A `ref` step whose repository git cannot read is exit code 8 (`account_repo`) instead, wherever it surfaces, since a journal reaches the account repo long after the command that wrote it is gone. A `publish` step whose staging directory is gone is decided from the live path: one still holding what the step expected lost its staged content, and one holding anything else changed after the publish renamed the content into place, which is what the refusal then names – the staging directory is supposed to be gone by then. A journal that replaces a directory records two steps at one path, a `remove` that takes the old content out of the way and a `publish` or a `link` that fills the path again: a path step whose path already holds what a later step of the same journal leaves there is done, since the path moved on past it, and a process stopped after both steps is finished rather than refused. Recovery never repeats a completed step, so it can run any number of times. Journals are recovered oldest first and recovery stops at the first refusal. A `.staged` file without a journal, left by a process that stopped between the two writes, is removed once every journal is recovered.

A process that stops after the rename and before it rewrites `version`, like a recovery that finds the live file already new, leaves the new file in place without a `version` bump. That is a missed signal, not a lost change: `agentx serve` still rescans, since the file lives in agentx home, which it watches, and every other command reads the file fresh.

Every mutating command recovers before its own change, under the lock it already holds; a refused recovery refuses the command. `agentx scan` and every scan of `agentx serve` look for journals under the shared lock and, when one exists, release it, recover under the exclusive lock (waiting for a mutation in progress the way they wait for the shared lock), release that and start their reads over, so no inventory is composed from a half-applied change. A refused recovery is exit code 6 for `agentx scan` and for the initial scan of `agentx serve`; for a later scan of `agentx serve` it is a `log` warning on stderr and a `refresh_complete` with `ok: false` and the message in `error` for every pending refresh, while the last snapshot stays in force until the journal is resolved. `agentx doctor` reports unfinished journals in its `mutations` row and recovers nothing. Reading commands such as `config get` and `machine` neither check for journals nor recover.

## Content hash

The content hash identifies one version of a skill by its content. It is SHA-256 over the following byte sequence, where `NUL` is one zero byte:

1. the frontmatter `name`, then `NUL`;
2. the frontmatter `description`, then `NUL`;
3. for every regular file under the skill directory, in bytewise order of its relative path with `/` as the separator: the relative path, `NUL`, the byte length in decimal, `NUL`, the file bytes.

The frontmatter is the `---` block at the top of `SKILL.md`, read as YAML: `name` and `description` are taken from it in any scalar form the standard allows, a plain value, a quoted one, a literal or folded block, or a plain value continued on the indented lines below its key, with surrounding whitespace trimmed; a number or a boolean written without quotes contributes the text the file holds rather than the decoded value rendered back, so `007`, `1.50` and `True` hash as they are written and not as `7`, `1.5` and `true`; a key whose value is a mapping or a sequence contributes nothing, so a nested block such as `metadata` is skipped; and a block that is not valid YAML, an unclosed one and a duplicate key included, is unparsable. A `SKILL.md` comes from any repository a user adds, so a block longer than 65536 bytes, or one opening more than 256 lists or mappings, is refused unread: the parser builds its whole tree before it can report anything, and a block that nests far enough costs memory faster than bytes, which ends the process rather than raising an error. Published blocks run to a few hundred bytes. A missing name or description contributes empty bytes; a missing or unparsable frontmatter counts as both missing, even though the skill is then named after its directory. A symlink inside the skill is followed when it resolves inside the skill directory and skipped with a warning otherwise: a file symlink contributes the target's bytes under the symlink's path, a directory symlink is walked under the symlink's path, and a directory symlink that points back at a directory being walked is a loop, skipped with a warning. File modes and times do not contribute. The hash is rendered as bare lowercase hex wherever a field carries one.

Two hashes of a skill are worth telling apart – what is on this machine now, and the version it was recorded from – and each has one name, in every event and every document that carries it. `content_hash` is always the first: the content hash of a version found on this machine, which is the version a scan read from disk, or what a library directory holds at the moment the command read it. `base_hash` is always the second: the content hash of a skill's [base version](#skills), the one its import commit records in its `Agentx-Content-Hash` trailer, whatever machine that commit was written on. Something that knows both carries both, under those two names; something that knows only the recorded version carries `base_hash` alone. No field means one of them in one place and the other in another, so a consumer never has to know which command emitted a field to know which hash it holds.

## Snapshot

`agentx scan` inventories the machine and emits one `snapshot` event: every detected agent configuration, every skill each one can see, every MCP server each one declares and every plugin each one has installed, with the skills and servers a plugin provides, and every skill of the library with what agentx knows of it. It writes nothing and never starts or connects to a server unless `--handshake` is given. Two scans of an unchanged machine produce byte-identical events when `instance_id` is fixed.

`agentx scan --project <path>` adds the project-scope skills found under `<path>` in each detected configuration's project skills directories, read-only; `<path>` must exist, else exit code 5. `agentx scan --configuration <id>` names the configuration that changed; the id must be detected, else exit code 5 with a hint listing the detected ids, and the whole machine is scanned regardless, since a one-shot command has no earlier snapshot to reuse.

Without `--json`, the output starts with one summary line counting the machine, `<n> configurations, <n> skills, <n> servers, <n> plugins detected` (`1 skill`), counting skills, servers and plugins as the snapshot does, once each however many occurrences; then one section per configuration, each preceded by a blank line and headed `<name> (<id>)  <path>  enabled|disabled` and, when the configuration has any, `  <n> skills, <n> servers, <n> plugins` (`1 skill`, leaving out a count of zero, counting the skill and server occurrences of this configuration), followed by up to three labelled blocks, each present only when it has rows: `skills:` with one line per occurrence (skill name, kind, scope and placement path, followed by ` -> <resolved path>` for a symlink and by `  (plugin <name>)` for a placement inside a plugin; the name is sanitised and the two paths are quoted as [Streams](#streams) prescribes, a skill's frontmatter and the names of the directories it sits in being text agentx did not write); `servers:` with one line per server (name, transport, then the command line or the URL, both sanitised as [Streams](#streams) prescribes since a configuration file declares them, with `  (plugin <name>)` for a server a plugin provides, then `<n> tools` (`1 tool`) for a server with a signature, counting its tools, prompts, resources and resource templates together, ending with `(disabled)` for a server its client records as turned off); and `plugins:` with one `name  version` line per plugin, followed by what the plugin provides in this configuration as `<n> skills, <n> servers` (`1 skill`, leaving out a count of zero, nothing when both are zero), ending with `(disabled)` for a plugin its client records as disabled. The block labels are indented two spaces and their rows four; rows are sorted by name. A configuration with no rows at all says `no skills, servers or plugins`. With no configuration detected the output is `No agent configurations detected.` and a hint line instead. Environment and header values are never printed. Warnings go to stderr as `warning: <message>`.

| `scan_counter` | integer | `1` for a one-shot scan |
| `machine` | object | `id`, the machine id, and `label` |
| `configurations` | array | the detected configurations, sorted by `id` |
| `skills` | array | the skill nodes, sorted by `physical_id` |

A managed skill whose import branch the account repo holds but whose library directory is gone is not listed, and so has no `state` and no `drift`: it is named in `warnings` instead, one per skill, as `agentx skill list` names it (see **Listing** under [Skills](#skills)) |
| `mcp_servers` | array | the MCP server nodes, sorted by `physical_id` |
| `plugins` | array | the plugin nodes, sorted by `physical_id` |
| `edges` | array | `{"from", "to"}` pairs of node ids, sorted by `from` then `to`: the machine id to each configuration; each configuration to each skill it sees, each server it declares and each plugin it has installed; each plugin to each skill and server it provides |

| `enabled` | boolean | `false` when the client records this declaration as turned off: a Codex declaration with `enabled = false`, a Codex plugin server turned off by its overlay, every server of a Codex plugin with `enabled = false` (see below), a Gemini CLI server listed in `mcp.excluded` of `~/.gemini/settings.json`, left out of a non-empty `mcp.allowed` there, or recorded as `{"enabled": false}` under its lowercased name in `~/.gemini/mcp-server-enablement.json`, and a Copilot CLI server listed in `disabledMcpServers` of `~/.copilot/settings.json`. Claude Code, Cursor and Windsurf keep that state per project or inside the app, and it is not read; absent from every other occurrence, including one the client records as on. A turned-off declaration is still declared and still merges into its server node by identity, and is never handshaken |

A plugin node is one plugin bundle installed in one configuration, in one version:

| Field | Type | Meaning |
|---|---|---|
| `physical_id`, `logical_id` | string | see below |
| `name` | string | the plugin name |
| `marketplace` | string | where the plugin was installed from: the marketplace name for Claude Code and Codex, the marketplace directory name for a cached Cursor plugin (`cursor-public` is the official marketplace), the recorded install source for a Gemini CLI extension; empty for a Cursor plugin under `plugins/local` and whenever the client records none |
| `version` | string | the installed version, or empty when the client records none |
| `configuration` | string | the configuration id |
| `path` | string | the plugin's directory |
| `enabled` | boolean | whether the client has the plugin enabled; present only when the client records that state on disk, which today is Codex for a plugin with a `config.toml` table; absent for every other plugin, which is installed but not known to be enabled or disabled |

Server discovery reads these user-scope files, each parsed as a map of server name to declaration under its top-level key, ignoring unknown keys; a declaration that is not an object or has neither a command nor a URL is ignored; a missing file declares nothing; a file that cannot be read or parsed is one warning naming the file, never its content, and the scan continues:

| Configuration | File | Format |
|---|---|---|
| `claude-code` | `~/.claude.json` | JSON, `mcpServers` |
| `codex` | `~/.codex/config.toml` | TOML, `[mcp_servers.<name>]` tables with `command`, `args`, `env`, `cwd`, `url`, `http_headers`, `env_http_headers`, `bearer_token_env_var` and `enabled` |
| `cursor` | `~/.cursor/mcp.json` | JSON, `mcpServers` |
| `gemini-cli` | `~/.gemini/settings.json` | JSON, `mcpServers`, with `url` an SSE endpoint and `httpUrl` a streamable HTTP one; `mcp.excluded` and `mcp.allowed` turn servers off |
| `windsurf` | `~/.codeium/windsurf/mcp_config.json` | JSON, `mcpServers`, with `url` or `serverUrl` |
| `github-copilot` | `~/.copilot/mcp-config.json` | JSON, `mcpServers`; `disabledMcpServers` in `~/.copilot/settings.json` turns servers off |

In the JSON files a declaration holds `command`, `args`, `env` and an optional `cwd` for a local server, `url` (or the client's variant) and `headers` for a remote one, and an optional `type` or `transport`. Every other configuration contributes skills only.

The library is read with the rest of the scan, under the same shared lock, so that no entry pairs a library directory with lineage from either side of a mutation: its directories as a client that reads the library reads them, through the same reads, so a skill is hashed once however many ways the scan reaches it and what cannot be read in the library is one of the snapshot's warnings; the lineage branches in one `for-each-ref` over `refs/heads/managed/` and `refs/heads/skills/`, after the `rev-parse` that checks the account repo; and the sources of the settings, which decide `drift`. A machine without an account repo spawns no git for it and lists every library skill as unmanaged. An account repo git cannot read does not fail the scan, since nothing else in the snapshot is read from it: `library` is `[]`, rather than every skill listed as unmanaged, which would not be true, and one warning, `<what skill list fails with>; the library is not listed, run 'agentx doctor' and check the account repo it names`, names the account repo and git's error, while the rest of the snapshot is what it would have been; a later scan that can read the repo again lists the library, and under [serve](#serve) that is a changed snapshot. The warning sends the reader to the account repo as well as to doctor because git's error is the diagnosis: doctor checks that the repo opens, and a repo that opens can still hold a branch git cannot read, one whose commit is missing for instance. `skill list`, which reports nothing but the library, is exit code 8 on the same repo. A skill of the library is also a skill node wherever a client sees it: the node is the content a client sees, the entry what agentx knows of the directory. Without `--json` the library is not printed, [`agentx skill list`](#skills) printing it, and its lineage is not read: a text scan, and every scan of a text serve, spawn no git for the library's lineage and cannot fail on the account repo, though a long-running serve still reads the source refs for its source index after each scan, as [Serve](#serve) describes. Its directories are read all the same, so a scan warns about the same library directories in both modes.

### Handshake

`agentx scan --handshake` starts or connects to every declared server after the local reads, outside the lock, at most four at a time, and lists what each exposes. Each server has a budget of ten seconds; `AGENTX_HANDSHAKE_TIMEOUT`, a duration such as `500ms`, replaces it for tests and diagnosis. A declaration its client has turned off (`enabled: false` on its occurrence) is never started or connected to, and keeps its stored signature. A server on the `stdio` transport is started as its command and arguments in its declared `cwd`, a relative one resolved against the plugin's directory for a plugin's server and otherwise against the directory `agentx` runs in, as each client resolves it against its own; without one, it starts in the directory `agentx` runs in, or, for a server of a Codex plugin in the Agent Plugins format, in the plugin's directory; a command with a `/` resolves against that working directory, a bare one is looked up on the `PATH` of the `agentx` process. It runs with the environment of the `agentx` process plus the variables the declaration sets, and its standard error goes to the null device; when the handshake is over its standard input is closed, a server still running a second later receives `SIGTERM`, and one still running a second after that is killed. A remote server receives the declared headers; for Codex, an `env_http_headers` value is read from the environment of the `agentx` process, and a `bearer_token_env_var` that environment sets becomes `Authorization: Bearer <value>` (listed in `header_keys`; unset, no `Authorization` is sent). A server on `streamable-http` receives JSON-RPC by `POST` to its URL, `Accept: application/json, text/event-stream`, and answers either as JSON or as an event stream; the `Mcp-Session-Id` the server assigns is echoed and released with `DELETE` at the end. A remote server is reached through the proxy the environment of the `agentx` process names (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY`), the one place a handshake reads that environment directly. The exchange is `initialize` with protocol version `2025-11-25`, the last MCP revision that opens with an `initialize` handshake (the server's answer is accepted whatever version it names; a server that implements only the `2026-07-28` revision or later, which carries the version on every request instead, rejects `initialize` and is one warning), `notifications/initialized`, then `tools/list`, `prompts/list`, `resources/list` and `resources/templates/list`, each only when the initialize result declares its capability, following `nextCursor` until the last page. A method the server reports as unknown (JSON-RPC error `-32601`) contributes nothing.

Before a declaration is handshaken, the placeholders in its command, arguments, environment values, `cwd`, URL and header values are expanded from the environment of the `agentx` process the way its client expands them. The expansion serves the handshake alone: the snapshot records every value as written, so a server's identity never depends on the environment, and no expanded value is printed or stored. A default applies only when the variable is unset; a variable set to the empty string gives the empty string.

| Configuration | Placeholders | An unset variable |
|---|---|---|
| `claude-code` | `${VAR}`, `${VAR:-default}` | stays as written. In a remote server's URL and headers, the variables Claude Code treats as credentials are empty whether set or not, a default notwithstanding: the list of Claude Code 2.1.278 (such as `AWS_SECRET_ACCESS_KEY`, `NPM_TOKEN`, `HTTPS_PROXY` and any `OTEL_*`), matched without regard to case and with an `INPUT_` prefix, any `*_BASE_URL` whose value embeds credentials, and, beyond that list, every `ANTHROPIC_*` and `CLAUDE_*` variable, so that one a later Claude Code protects stays withheld while the list lags. With `--verbose`, a debug line names the variables withheld from each server, never their values |
| `cursor` | `${env:NAME}`, `${userHome}`, `${pathSeparator}`, `${/}` | stays as written, and so do `${workspaceFolder}` and `${workspaceFolderBasename}`, a user-scope declaration having no workspace |
| `gemini-cli` | `$VAR`, `${VAR}`, `${VAR:-default}` | stays as written, except in an environment value or a header, where it is empty |
| `windsurf` | `${env:NAME}`, and `${file:/path}` for the file's contents, trimmed | is empty; a file that cannot be read stays as written |
| `github-copilot` | `$VAR`, `${VAR}`, `${VAR:-default}`, and `~` at the start of `cwd` for the home directory | stays as written |
| `codex` | none; the environment enters through `env_http_headers` and `bearer_token_env_var` | |

A server on `sse` speaks the legacy HTTP+SSE transport of protocol revision `2024-11-05`. A `GET` to its URL with the declared headers and `Accept: text/event-stream` opens an event stream whose first `endpoint` event names, relative to the URL, where each JSON-RPC message is `POST`ed with the same headers; the answers arrive on the stream as `message` events. An endpoint on another scheme or host than the URL is refused before anything is sent to it, since the declared headers would follow. The stream is closed at the end. A `streamable-http` server whose opening `POST` is refused with HTTP 400, 404 or 405 and a body that is not a JSON-RPC error (which is how a current server refuses a method) is tried once more on this transport at the same URL, as the protocol's backwards compatibility asks; when that URL opens no event stream, the original refusal is the failure. No other URL is ever tried: a handshake reaches the server where its client does.

A server that cannot be started, exits, answers something that is not JSON-RPC, refuses a method with any other error or runs out of its budget is one warning, `<config file>: server <name>: <reason>`, that never carries an environment or header value; the scan continues and the server keeps its stored signature, or `none`. The exit code stays 0.

The occurrence of a failed declaration carries `handshake_error`: `message` is the reason of the warning, `hint` is what the user can do about it, and `reason` is one of:

| `reason` | When |
|---|---|
| `unauthorized` | the server answered HTTP 401 or 403. The handshake sends only the declared headers and never the sign-in an agent client holds, so a server behind OAuth always fails this way; the hint says so, or, for a Codex `bearer_token_env_var`, to set or renew that variable, or, when the declaration sets headers, that they were refused |
| `unreachable` | the connection failed, or the server answered HTTP 404 or 410 without a JSON-RPC error |
| `not_found` | the command of a local server does not exist |
| `timeout` | the budget ran out |
| `failed` | everything else: the server exited, answered something that is not JSON-RPC, another HTTP status or a JSON-RPC error, or its event stream named an endpoint on another origin |

In human output the server's row ends with the failure in words (`needs sign-in`, `unreachable`, `command not found`, `timed out`, `handshake failed`), after the tool count of a stored signature, and stderr closes with one `hint:` line per distinct hint, after the warnings.

Every item is serialised as its kind, name, description, input schema and output schema joined by `NUL`, the schemas as canonical JSON (object keys sorted, no whitespace, numbers as written, only the escapes JSON requires) and empty for anything but a tool or an absent schema. Items are sorted by kind, then name, then serialisation. The signature is SHA-256 over the serialisations joined by `NUL`, rendered as 64 lowercase hex characters; a server that exposes nothing has the signature of the empty list. A tool's hash is SHA-256 over its own serialisation, and its `id` is the identity `tool` over the server's logical id and that hash, so a tool that is byte-identical in two versions of one server is one node.

After the handshakes, the signatures taken are written to `handshakes.json` in agentx home under the exclusive lock, replacing the entry of each server handshaken and keeping every other: `{"<server logical id>": {"signature": "<hex>", "tools": [...], "at": "<RFC 3339>"}}`, `tools` as on the node. The file is derived state, so `version` is not rewritten: no other consumer needs to rescan for it. When one scan handshakes two declarations of one logical server that answer differently, each declaration gets its own node, and the file keeps the declaration last in scan order. A scan without `--handshake` reads the file and gives every declaration of a listed server the stored `signature`, `signature_at` and `tools`; a file that cannot be parsed is a warning and counts as empty.

Plugin discovery reads, per configuration:

| Configuration | Install records | Plugin directories | Manifest |
|---|---|---|---|

| `codex` | the `[plugins."<name>@<marketplace>"]` tables of `~/.codex/config.toml`, each with `enabled` (`true` when absent) | `~/.codex/plugins/cache/<marketplace>/<name>/<version>/`; the active version is `local` when present, else the highest by semver, compared as strings where either name is not a semver | `plugin.json` at the root when its `$schema` starts with `https://agent-plugins.org/schemas/`, else the first of `.codex-plugin/plugin.json`, `.claude-plugin/plugin.json` and `.cursor-plugin/plugin.json` |

Every other configuration reports no plugins. For every client, a manifest or server file that cannot be parsed is one warning naming the file, never its content, and the plugin is still reported with what its directory gives; a missing file is silent. Claude Code: a record without an `installPath` or whose directory does not exist is a warning; skills are under `skills` and servers in `.mcp.json` at the root, in the `mcpServers` JSON format, with `${CLAUDE_PLUGIN_ROOT}` replaced by the plugin directory in the command, the arguments, the environment values and `cwd`.

Codex: the name and marketplace are the two halves of the `config.toml` key, split on its last `@`; a key without both halves is a warning, and a key whose plugin directory does not exist is a warning naming that directory. A plugin directory without a key, which is how a plugin installed through the account appears, is reported without an `enabled` field. The version is the manifest's `version`, else the version directory name. Skills are the manifest's `skills` paths (one string or a list, each starting with `./` and staying inside the plugin, else a warning naming the path), else `skills`. A plugin without a manifest is named after its directory. Skills are in the manifest's `skills` paths (one or a list, each relative, with or without a leading `./` as Cursor's own marketplace plugins omit it, and staying inside the plugin, else a warning naming the path; a path holding a `SKILL.md` is that one skill, another is a skills directory), else under `skills`; servers are the manifest's `mcpServers` object, with the manifest as the `config_file`, else the file the manifest names, else `mcp.json`, else `.mcp.json`, in the `mcpServers` JSON format, with `${CURSOR_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_ROOT}` replaced by the plugin directory in the command, the arguments, the environment values and `cwd`. Discovery: inside each skills directory a client reads, every child directory, or symlink to one, that holds a `SKILL.md` is a skill; hidden entries and `node_modules` are skipped; a broken symlink is a warning naming the link, and several in one directory are one warning naming the directory, their count and their names. A client's user-scope skills directories are its own, other clients' directories it reads (Cursor reads the Claude Code and Codex directories) and the library for clients that read it directly (Codex and Gemini CLI), which yields an occurrence with the library path as placement path whatever the enabled state. Each directory is canonicalised once and each skill is hashed once per scan.

Identities are SHA-256 over the type name and its inputs, each input preceded by one `NUL` byte, rendered as `<type>:<lowercase hex>`. Paths under the user's home are hashed with the home replaced by `~`, so an identity does not depend on where the home directory is. Every identity but a skill's, a plugin's and a remote or package server's logical one includes the machine id; since the platform-derived id also covers the user id, a snapshot that must compare across users or machines, such as the CLI's own golden files, pins the id with `machine.json`.

## Git

The CLI runs the system git as a subprocess and never embeds a git implementation. Git is located through `PATH` of the environment the CLI was given. The floor is git 2.40, compared by numeric version components, so 2.4 and 2.39 are rejected and 2.100 is accepted. Before any command other than `version`, `doctor` and `help` runs, the CLI runs `git --version` once; a missing or too-old git is exit code 2 with a hint naming the distribution package where known, before the command does anything. `version` and `doctor` stay available to report the problem.

Every git call names its repository with `--git-dir` explicitly, captures stdout and stderr, and logs the command line and stderr at debug level. Git runs in one of two environments, built from the CLI's own environment:

- Isolated, for every command that writes objects or merges, and for every local read of the account repo: `GIT_CONFIG_GLOBAL` points at `/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, every `GIT_*` variable of the user's is dropped, author and committer are fixed to `agentx <agentx@localhost>` at `946684800 +0000`, `GIT_NO_LAZY_FETCH=1` forbids fetching a missing object one at a time (git 2.45 and newer honour it; older gits ignore it), and `core.autocrlf=false`, `commit.gpgsign=false` and `core.hooksPath=/dev/null` are passed with `-c`. A commit made this way has the same id on every machine whatever the user's git configuration, and nothing in this environment touches the network.
- User, for network commands, today the fetches of `source add` and `source fetch`: the CLI's environment as is, so credential helpers, SSH configuration and URL rewrites (`url.<base>.insteadOf`) apply. agentx never stores git credentials.

An isolated call may name its own author and committer dates, which is how the [import commit](#skills) takes the upstream committer's time; everything else the isolated environment fixes still holds. A command that has several read-only calls to make that do not depend on each other runs them at once through the git runner, at most four at a time, the bound the fetches of a source and the handshakes of a scan keep: the calls come back in the order they were given, the first failure by that order is the error, and the number of processes is the same as running them one after another. Only reads run this way; every write of an object or a ref is made by one call at a time under the lock. `agentx skill diff` writes the blobs and trees of the directory it compares, which no ref ever holds, without taking the lock: git writes an object whole or not at all, and an object written twice is the same object.

In the serve child every git call additionally has `GIT_TERMINAL_PROMPT=0`, `-o BatchMode=yes` appended to the SSH command and `GIT_ASKPASS=/bin/false`, so a prompt becomes an error rather than a hang.

## Doctor

`agentx doctor` checks whether this machine can run agentx and reports one row per check, in this order. It only reads: it creates neither agentx home, nor the lock file, nor the account repo, and its git probes run in a throwaway repository in the temporary directory.

| Check | Statuses | What it means |
|---|---|---|
| `git` | `ok`, `fail` | git is in `PATH` and 2.40 or newer; the detail names the version |
| `fork_merges` | `ok`, `fail` | upstream changes can be merged into forks: `git merge-tree --write-tree --merge-base=<base> <ours> <theirs>` merges two branches of a throwaway repository in the temporary directory, made with deterministic commits |
| `commit_identity` | `ok`, `fail` | commits get the same id on every machine: the isolated environment gives a fixed input the known commit id `5d75017e77f5413f4337ef776244b8d8dc77ca90`; the failure detail names both ids |
| `home` | `ok`, `fail` | agentx home is writable, or does not exist yet; the first scan creates it |
| `lock` | `ok`, `warn` | the lock is free, a missing lock file included, or held by another agentx command; the detail names the holder's process id |
| `mutations` | `ok`, `warn`, `fail` | no [mutation journal](#mutation-journal) is unfinished; a warning names the count and the oldest journal, and the hint says how to recover; doctor recovers nothing itself; `fail` when the directory cannot be read |
| `settings` | `ok`, `fail` | `settings.json` parses, or does not exist yet; the detail and hint name the path |
| `account_repo` | `ok`, `fail` | the account repo opens, or does not exist yet |
| `source_remotes` | `ok`, `warn`, `fail` | every source remote of the account repo is a source the settings name (see [Sources](#sources)); a warning names the count and each remote by the canonical URL it records, or by its source id for a URL agentx would not have written, and the hint gives the same two repairs a failed take-back gives, `agentx source add <url>` or `agentx source remove <id>`, so that the two report one thing once; `fail` when the settings do not parse, with a hint that names the settings file. An add that fails takes its own remote back, so what this row names is what no take-back covers: a run killed outright, and a take-back an unrecoverable journal refused. The other direction, an entry whose remote is gone, is not a row: every command that uses the remote names it as missing and `source fetch` writes it back. Reported, never repaired: doctor holds no lock. Emitted only when the `account_repo` row is `ok` and the repo exists |
| `staged_imports` | `ok`, `warn`, `fail` | no `refs/agentx/importing/<run>/<n>` is left behind; a warning names the count of refs, the count of runs they belong to and the first ref, and the hint is the `git update-ref -d` that removes one. An install killed between its fast-import and the journal that publishes the commits leaves them, and they pin the objects they name. Reported, never swept: the staging refs of a run still fetching are indistinguishable from these (no lock is held while either exists and the run id says nothing about which), so a sweep would have to guess, and a wrong guess takes the objects a live install is about to publish. Emitted only when the `account_repo` row is `ok` and the repo exists |
| `library` | `ok`, `fail` | the library is a writable directory, or does not exist yet; the first install creates it |
| `client:<slug>` | `info` | one row per detected agent configuration, sorted by slug; the detail is `<name>: <configuration directory>` |
| `clients` | `info`, `warn` | `<n> of <m> registered clients detected`, where `m` is the size of the client registry; `warn` with a hint when nothing is detected |

`doctor`, one event per check:

| Field | Type | Meaning |
|---|---|---|
| `check` | string | the check name from the table above |
| `status` | string | `ok`, `warn`, `fail` or `info` |
| `detail` | string | what was found, naming the version, path or error involved |
| `hint` | string | how to fix it; absent when there is nothing to suggest |

Without `--json` the rows print in three titled sections, `System` (`git`, `fork_merges`, `commit_identity`, `home`), `App` (`lock`, `mutations`, `settings`, `account_repo`, `source_remotes`, `staged_imports`, `library`) and `Clients` (every `client:<slug>` row; the `clients` detail is shown after the section title rather than as a row), each row indented as `<glyph> <check>  <status>  <detail>`, the glyph being `✓` for `ok`, `!` for `warn`, `✗` for `fail` and `•` for `info`, with the columns aligned across sections. After the sections, a blank line and either `✓ No issues detected` or an `<n> issues` block (`1 issue`) listing every `warn` and `fail` row again as `<glyph> <check>  <detail>`, with its `hint` on the next line as `hint: <hint>` aligned under the detail. Exit code 2 when git is missing or too old; the run stops after the `git` row, since nothing else can be checked. Exit code 8 when the account repo is unusable, after every row. Otherwise 0, warnings included. The `result` event carries `ok: false` exactly when the exit code is non-zero.

## Account repo

The account repo is `account.git` in agentx home, a bare repository. It is created on first use, under the lock, by the first command that opens it: `agentx source add`, or `agentx skill add` when it adds the source it installs from. Its creation bumps `version` like any mutation. On a fresh machine it does not exist and `agentx doctor` reports that. Creation runs `git init --bare` in the isolated environment and sets `gc.auto=0` (maintenance runs on the serve child's timer, never inside a command), `core.logAllRefUpdates=true` (reflogs, which a bare repository lacks by default), `merge.conflictStyle=zdiff3` and, on git 2.48 or newer, `worktree.useRelativePaths=true`. The repository is renamed into place only once every step succeeded. A present `account.git` that is not a bare repository git can read is exit code 8 with a hint naming the path.

Git config in the account repo holds only what git owns: the remotes of [Sources](#sources), and later tracking branches.

## Sources

A source is a git repository added by URL, from which skills are installed. `agentx source add <url>` fetches it, `agentx source fetch [<url|id>]... [--all]` fetches sources that are already added, `agentx source list` lists the sources of this machine, `agentx source skills <url|id>` lists the installable skills of a fetched source, and `agentx source remove <url|id>` deletes one. `add`, `fetch` and `remove` are mutations; `list` and `skills` read and never touch the network.

**URL forms.** `source add` and every `<url>` argument accept, with an optional `#<ref>` fragment on each: `owner/repo` and `owner/repo/<subpath>`, which resolve to GitHub; `https://github.com/owner/repo`, with or without `.git` or a trailing slash, followed by an optional `/<subpath>` or `/tree/<ref>/<subpath>`; a GitLab URL, `https://gitlab.com/group/subgroup/repo`, with an optional `/-/tree/<ref>/<subpath>`; the SSH shorthand `git@host:path` and `ssh://` and `git://` URLs; any `https://` or `http://` host; and `file://<path>`. Everything else, a GitHub `blob`, `pull` or other page URL included, is exit code 1 with a hint listing the forms. The result is the canonical URL, an optional subpath and an optional ref. The canonical URL is the source's identity: the scheme and host in lower case, the host without a trailing dot and without a port that is the scheme's default, an IP address host in one spelling and bracketed, `.git` and a trailing slash dropped, `git@host:path` written as `ssh://git@host/path`, the path's percent escapes kept as escapes, and a `file://` path cleaned but otherwise as it is on disk. The canonical URL of anything accepted parses back to itself, to the same id, and to the repository alone with no subpath and no ref: it is printed by `source list` and read back by `source remove` and `source skills`, so a form that did not round trip would name a different source than the one it came from. A pin must be a ref git accepts, which is what `git check-ref-format` allows for a one-level name, or a commit id; a name git would refuse is exit code 1 here rather than a fetch failure later. On GitHub the repository is `owner/repo` and what follows is the subpath; elsewhere the repository path ends at `/-/` or at the first segment named `*.git`, and what follows is the subpath, so `https://git.example.com/team/repo.git/skills` and `file:///srv/skills.git/tools` name a subpath and `https://git.example.com/team/repo/skills` is the repository `team/repo/skills`. The ref of a tree URL is the pin; a fragment naming a different ref is exit code 1. A ref must be a name git accepts for a branch or tag, or a commit id. The subpath scopes what the command lists and is never stored. Once its percent escapes are decoded it is held to the rule a path in a source's tree is held to (see [Skills](#skills)): a subpath with an empty, `.`, `..` or `.git` component, the last in any case, or holding a backslash or a NUL is exit code 1, however it was escaped, so `skills%2F..` is refused as `skills/..` is. A subpath that is not a directory of the repository at the fetched commit is exit code 5. A user or token embedded in the URL is removed before the URL is used anywhere: it never enters the settings, the account repo's configuration, a trailer or an event, and the command logs one warning saying so and naming the credential helper. For an `ssh://` URL the user name (`git@`) is part of the address and is kept; only a password is removed.

**Id.** The source id is the first 16 lowercase hex characters of SHA-256 over the canonical URL. It names the remote `src-<id>` and the ref `refs/agentx/sources/<id>` in the account repo and is accepted wherever a URL is. An id that names no source entry of the settings is exit code 5 from every command that takes one, `source fetch`, `source skills`, `source remove` and `skill add`, with a hint to list the sources, since an id is a hash and names no URL that could be fetched; `source remove` still clears what the account repo holds under an id no entry names, a remote an interrupted add left behind. The one exception is an id a managed skill's lineage still records, which is a source this machine removed, or never added, while a skill installed from it stays: its URL is known, so the message names it and the hint is `agentx source add <url>` with the URL the lineage records, sanitised and quoted as the lines [import](#export-and-import) prints are, and without a pin, the pin having gone with the entry. The lineage is read for that refusal alone, in one `for-each-ref`, and an account repo git cannot read leaves the refusal as it is without it. A removal that takes such a skill off the machine, `skill remove` without `--from` or with `--from universal`, deletes its import branch and with it that record, while `--from <configuration>` keeps both; once no managed skill records the URL, the id is refused as any other is, with the hint to list the sources.

**Fetch.** `source add` opens the account repo, creating it when needed, then writes the remote in the isolated environment: `remote.src-<id>.url` is the canonical URL, `remote.src-<id>.fetch` is `+<pin>:refs/agentx/fetching/<id>`, or `+HEAD:refs/agentx/fetching/<id>` for an unpinned source so that the remote's default branch is followed whatever its name; its left side records the pin and its right side is the staging ref, never the source ref, so that `refs/agentx/sources/<id>` is written by the `update-ref` that ends a whole fetch and by nothing else – not by a fetch agentx did not make, and not by a refspec an interrupted run left behind, `remote.src-<id>.tagOpt=--no-tags`, `remote.src-<id>.promisor=true` and `remote.src-<id>.partialclonefilter=blob:none`. It then runs `git fetch --quiet --no-tags --no-write-fetch-head --recurse-submodules=no --no-show-forced-updates --refmap= --filter=blob:none src-<id> +<pin>:refs/agentx/fetching/<id>` in the user environment. A fetch lands on the source's **staging ref** and never on the source ref: filling a source takes two network round trips, and between them there is a commit the account repo can read whose blobs are not here yet, which no reader of a source ref may ever see. The refspec is built from the pin the settings hold rather than left to `remote.src-<id>.fetch`, so that a remote a run was interrupted before it could write cannot make a fetch follow a ref the settings do not name; `--refmap=` is what makes it the only refspec, since one on the command line does not replace the configured one: git also updates that one opportunistically. The remote's configuration is written under the lock, since `git config` fails rather than waits when another command holds the repository's own config lock; the fetch itself runs outside it, so that a slow network never blocks a scan. An add that does not reach its settings entry takes that remote back: a source the settings did not name before loses its remote, its source ref and its staging ref altogether, and one they did name goes back to the pin they still hold, so that the account repo never keeps a remote for a source the settings do not name – nothing would name such a remote again, `source fetch` and `source skills` both answering from the settings. The cleanup runs under the hold the failing write already has, since a run that had to win the lock back would be competing for it with whatever just made it fail; only a run that never took the lock at all can leave the remote behind, and the next `source add` or `source fetch` of the same source brings it back in line. Once the entry is written the remote belongs to it and stays, whatever else the run still fails at. The fetch brings every commit and tree of the ref and no blob; a server that does not support partial clone ignores the filter, which git reports as a warning, and the fetch is a full one. A pin that names no branch, tag or commit of the source is exit code 5; any other fetch failure, unreachable host, authentication, or not a repository, is exit code 3 with the first line of git's error and a hint naming the credential helper, worded for the dropped credential when the URL carried one. The staging ref is then read as a commit (an annotated tag is peeled; the object the ref names, tag or commit, is what the source ref will end up holding), and the skills under the subpath are listed from the trees, tree objects only: every directory holding a `SKILL.md` (a regular file; a symlink does not count), the root included, skipping any directory below the subpath whose name starts with `.` or is `node_modules`, at any depth, while a skill inside another skill's directory counts. The `SKILL.md` blobs are then fetched in one batch, by object id on the standard input of one `git fetch` carrying `-c fetch.negotiationAlgorithm=noop`, the flags above except `--no-show-forced-updates`, and `--refmap=`, `--filter=blob:none` and `--stdin`, the way git itself fills a partial clone; the batch names objects rather than refs and updates none, so it has no forced update to suppress; a server that serves the filtered fetch but refuses single objects gets one `git fetch --refetch --no-filter` with the same flags instead, which makes the fetch a full one. The batch covers every `SKILL.md` of the repository, the skipped directories included, not only those under this command's subpath: a subpath scopes one listing and is never stored, so every later listing, of any part of the source, is answered from the account repo without the network. No blob is ever fetched one at a time: every local read runs with `GIT_NO_LAZY_FETCH=1`. Every `SKILL.md` of the commit is then looked for in one `git cat-file --batch-check`; a batch a server answered without sending every object it was asked for is exit code 5 with a hint to fetch the source again, the source ref unmoved. The blobs are read in one `cat-file --batch`, and the skill list (subpath, name, description, tree id) is built in memory and never written to disk.

**Publishing a fetch.** Only once the commit is whole does `git update-ref refs/agentx/sources/<id> <fetched object>` move the source ref onto it, followed by `git update-ref -d refs/agentx/fetching/<id>`. `refs/agentx/sources/<id>` therefore never names a commit whose `SKILL.md` blobs are not in the account repo, and a fetch is invisible to every other reader – the [serve](#serve) child rebuilding its source index, a concurrent `source skills` or `source list`, the next command after a crash – until it is whole: each of them sees the commit the last complete fetch left, then the new one, and nothing in between. A fetch that fails at any step, for any cause, leaves the source ref exactly where it was, so a failed fetch never costs a machine the source it already had. The staging ref is deleted when the fetch ends, whether it finished or failed; only a killed process can leave one behind, and nothing reads it, the next fetch of that source overwrites it and `source remove` deletes it. Finally, under the lock, the settings entry is written: `url`, `pin` when set and `last_fetched` now; an existing entry for the URL is replaced, its `alias` kept, so adding a source again re-fetches it and changes its pin to what the new command said, a missing fragment included.

**A remote the settings do not name is not a source.** `source fetch` and `source skills` both answer from the settings, so a remote no entry names is a remote nothing will ever name again or clean up. It exists in the account repo only because an entry names it, or because an add is in flight for it. An add that wrote the remote and cannot write the entry therefore takes the remote back: a source that was not there before goes altogether, remote and ref, and one that was there goes back to the pin the settings still hold, which is what the next command will read. The same take-back answers a failed fetch, which also leaves a remote written and nothing recording it. It runs under the lock: where the settings write held the lock, inside that same hold, and where the settings write never won it, as a [take-back](#lock-and-version-file) that waits for the lock rather than giving up on it. The run still ends with the exit code of whatever stopped it, a lost lock still being code 7. A take-back that fails even then is reported rather than passed over: the message names the remote left in the account repo and says no source names it, and the hint gives the two repairs – `agentx source add <url>` again, which rewrites the remote and writes the entry, or `agentx source remove <id>`, which clears the remote. A take-back is itself a mutation, so an earlier mutation's journal that cannot be recovered refuses it exactly as it refuses any other command, whatever the take-back waits for: the remote then stays in the account repo, reported the same way, until the journal is resolved and the add is run again. The first hold of the lock, the one that writes the remote, is not a take-back and gives up like any other mutation: a run that loses it has written nothing.

**Fetch again.** `agentx source fetch [<url|id>]... [--all]` fetches sources that are already added, so that a source no skill was installed from, which nothing else refreshes, can be brought up to date: several arguments fetch several sources and `--all` fetches every source of the machine. Neither an argument nor `--all` is exit code 1 naming both forms, and so is giving both at once. Every argument is resolved against the settings before anything is fetched: a URL that names no added source is exit code 5 with a hint to add it and an id that names none answers as under **Id.** above; a subpath in a URL argument is ignored, since a fetch covers the whole source whatever part of it is named, and a `#<ref>` other than the entry's pin is exit code 1 naming the stored pin, the rule `source skills` follows; a source named twice, by URL and by id, is fetched once. Each source is fetched at the pin the settings hold, through the remote `source add` configured, by the fetch above and nothing else: the blobless fetch onto the staging ref, then the `SKILL.md` blobs of the whole repository in one batch, then the source ref. Each source stages on its own `refs/agentx/fetching/<id>`, so the parallel fetches of one run never share a ref, and a source that fails leaves its own source ref where it was without disturbing any other. A fetch writes the remote only to bring it back in line with the settings: the remotes of the run's sources are read in one `git config --get-regexp` under the early lock, and the refspec of one that does not record the pin the settings hold is rewritten, which a run interrupted between the remote and the settings leaves behind. A source with no remote at all is left alone rather than given half of one. That changes no pin: the pin is what the settings say, and only `source add` sets it. An account repo that does not exist is exit code 5 with a hint to add the source, nothing having been fetched on this machine at all, and so is a source whose remote the account repo no longer holds, which an interrupted removal leaves: git answers a fetch through a remote that is not there by naming that remote, which is agentx's own name for the source, and the run says what `source skills` says of the same state instead. That hint is `agentx source add <url>[#<pin>]` with the pin the settings hold, the argument sanitised and quoted as the lines [import](#export-and-import) prints are: this is the state an import leaves, and `source add` writes the pin its argument names, so the bare URL would unpin the source. The sources are fetched in parallel, at most four at a time as the handshakes of a scan are, outside the lock, and each one ends with a `progress` event of phase `fetch` carrying its URL. A source that could not be fetched is one warning naming it and the reason, and the run goes on: every other source still lands. The lock is taken once before the network, to recover an unfinished [mutation journal](#mutation-journal) and to refuse a run that could not write the settings anyway, and once at the end for one write of `last_fetched`, now, for every source that fetched. A source removed while the run fetched has no entry to write, is left out of the report rather than named as present and fresh, and has the ref its fetch published taken away again under that same lock, so that a removal a fetch raced still leaves nothing of the source. That write bumps `version` like any mutation, so the [serve](#serve) child rebuilds its source index after a fetch that moved a ref, and a fetch that moved nothing still updates `last_fetched`. One run over several sources has one exit code, and it is the code every failure agrees on: fetching one source answers exactly as adding or listing that source would, and a run whose sources all failed the same way answers for that cause. Exit code 3, the source-level refusal, is what a run whose causes disagree answers, no one code being true of them all. The `error` and `result` events name every source that failed, the `hint` answers the `code`, and each failure is one `warning:` line on stderr naming its source. `--all` on a machine with no source prints what `source list` prints for none and exits 0.

**Listing.** `source skills` resolves its argument to an entry of the settings, exit code 5 when there is none, with a hint to add it for a URL argument and the hint under **Id.** for an id; a URL argument may carry a subpath, and a fragment naming a ref other than the entry's pin is exit code 1. It reads `refs/agentx/sources/<id>` (exit code 5 when the account repo holds no ref for the source, with the hint `source fetch` gives that state, and exit code 5 with a hint to fetch the source again when an object the listing needs is missing) and lists the skills as above from the account repo alone. A local git failure in any `source` command is exit code 8, and so is a `source fetch` run over several sources when every source failed that way; it is never reported as a source that was not fetched: the account repo holding no ref for the source is exit code 5, git failing to read the refs at all is exit code 8, and each hint leads to the command that addresses that cause. `source list` reads the settings and runs two git processes: the `rev-parse --is-bare-repository` that checks the account repo, then one `for-each-ref` over `refs/agentx/sources/`.

**Removal.** `source remove` deletes the remote (`git remote remove src-<id>`), the source ref and the staging ref a killed fetch can have left (`git update-ref -d` each), then the settings entry, all under the lock, so that nothing of the source is left under `refs/agentx`. The git state goes first: were the entry deleted first and the git deletion then failed, nothing would name the source any more and its remote would be unreachable for good. The objects stay until maintenance reclaims them. A managed skill installed from the source keeps its coordinates, its import branch, its library directory and its placements, and is `source removed` in the `drift` of its [`library_skill`](#event-types) event and of its snapshot entry for as long as the settings hold no entry for that canonical URL: any command that writes the entry again ends it, whether `source add` of the same canonical URL, an install that names the source by URL, an [`agentx adopt`](#adoption) that adds it, or an [`agentx import`](#export-and-import) of settings that hold it. Any pin clears it, since the canonical URL and not the pin is the source's identity. Adding the source again changes nothing of the skills installed from it: once `source add` has added it, `skill list` is what it was before the removal, byte for byte. `source add`, an install and an adoption fetch the source anew; an import writes the entry alone, which leaves a source not fetched.

Without `--json`: `source add` prints `✓ added <url> at <short commit>: <n> skills` for a source that was not there before, and for one that was, `✓ re-fetched <url>, now at <short commit>, was <short commit>`, or `, already at <short commit>` when the fetch changed nothing, so a repeat says what moved rather than repeating that it exists; ` pinned to <ref>` follows the URL when pinned and ` under <subpath>` ends the line when scoped; `source fetch` prints one of those `re-fetched` lines per source that fetched, in the order the command named them, its arguments in their order and `--all` in the order `source list` prints, whatever order the fetches themselves finished in, and nothing for a source that failed, which is a `warning:` line on stderr instead; `source list` prints `<n> sources` and one row per source, `<url>  <pin or (unpinned)>  <short commit or not fetched>  <last_fetched>  <id>`, or `No sources. Add one with agentx source add <url>.`; `source skills` prints `<n> skills in <url>[ under <subpath>] at <short commit>` and one row per skill, `<name>  <subpath or .>  <description>`, the three of them sanitised as [Streams](#streams) prescribes, since the source writes all three; `source remove` prints `✓ removed <url>`. A short commit is its first seven characters. Every row of the `source list` and `source skills` listings is indented two spaces; the `re-fetched` lines of `source fetch` are one per source and are not indented, being confirmations rather than rows of a listing.


## Skills

The library is this machine's directory of skills managed by agentx, `AGENTX_LIBRARY` or `~/.agents/skills`. `agentx skill add <source>[/<subpath>] [--skill <name>]... [--all] [--except <name>]... [--to <configuration>]... [--copy] [--fetch]` installs skills of a source into it and places them in the configurations that should see them; `agentx skill place <name> --to <configuration>... [--copy]` places a skill the library already holds; `agentx skill remove <name> [--from <configuration>|universal]...` takes a skill out of one configuration or off the machine; `agentx skill diff <name>` shows how a managed skill differs from its base version; `agentx skill revert <name>` puts it back to that version; `agentx skill list` reports what the library holds. `add`, `place`, `remove` and `revert` are mutations; `diff` and `list` read the library and write nothing to it.

**A skill the library already holds.** The argument of `skill add` is a source in one of the [URL forms](#sources) or a source id, and anything else is exit code 1 with a hint listing the forms. When that argument is exactly the name of a skill the library holds, one `skill place` would take, whether agentx installed it or not, the refusal is still exit code 1 but says what was meant: the message is `<name> is already in the library; skill add installs a skill from a source` and the hint is `to place it in more clients, run 'agentx skill place <name> --to <configuration>'`. The hint carries each `--to` the command line gave, as `--to <id>` in the order given, in place of `--to <configuration>`, which is printed as it is when no `--to` was given, and carries `--copy` when `--copy` was given. `<name>` and each `<id>` are quoted for a shell, and a name that starts with `-` comes last after `--`, as in the commands of the warning for a kept copy under **Placements**, so the hint runs as it is printed. A source form wins over a library name: an argument that parses as a source, or that is a source id, is installed from as a source even when the library holds a skill of that exact name, so no library directory changes what an install of a source does. The refusal comes after the flag checks of **Selecting several** and reads the library alone: nothing is fetched, locked or written, and no source is added.

**What is installed.** A source URL the settings hold no entry for is added first, by the steps `agentx source add` takes and nothing else: the remote is written, the source is fetched without blobs and then its `SKILL.md` blobs, outside the lock, and the settings entry is written as a mutation of its own, so an install that fails afterwards keeps the source. The install then reads the listing that fetch built, so the source is fetched once. An id that names no source is exit code 5 with a hint to list the sources: an id names no URL to fetch. An id a managed skill's lineage records, the id of a source this machine removed, is exit code 5 as well, with the hint `agentx source add <url>` naming the URL the lineage records (see [Sources](#sources)); an install that names that source by its URL instead adds it again as above, which ends the `source removed` of every skill installed from it. A source already added is not fetched again unless `--fetch` is given, which fetches it again at the pin the settings hold, exactly as `source add` of that URL and pin would, before the install. Otherwise the account repo must hold its ref, else exit code 5 with a hint to add it, the one `source fetch` gives that state, which names the pin the settings hold even when the argument leaves it out. The version installed is the one the source ref names in the clone: an install resolves the pin the settings hold, or the remote's default branch, against what the last fetch brought, and never reaches for the network to decide what to install nor reads a working copy. The skill's upstream commit is the last commit reachable from that commit that touched the skill's directory, and that commit itself for a skill at the repository root: a commit elsewhere in the source, or a fetch at another time, leaves the upstream commit of an unchanged skill where it was, so two machines that fetched the source at different commits, or one machine before and after a fetch, write the same import commit for the same version. A `#<ref>` other than the stored pin is exit code 1 naming the stored pin, with a hint to change it with `source add <url>#<ref>`, as it is for `source skills`. The skills are those the coordinate and the selection name: a source or a subpath that holds exactly one skill needs no `--skill`, one that holds several is exit code 1 with a hint listing their names, a `--skill` that names none of them is exit code 5 with the same hint, and a coordinate that holds no skill at all is exit code 5 with a hint to list the source.

**Selecting several.** `--skill` may be given once for each skill to install, and a name given twice installs that skill once. `--all` selects every skill the coordinate holds and `--except <name>`, once for each, leaves some of them out. The two forms do not mix: `--all` with `--skill` is exit code 1, since `--all` already names everything, and `--except` without `--all` is exit code 1, since excepting from a list one wrote out is a contradiction. Both are refused before anything else happens, so such a command line adds no source. A selection of several skills from a source URL the settings do not hold adds that source first, once, like a selection of one. `--skill` and `--except` match a skill's frontmatter `name` case-insensitively, or its directory name when the frontmatter has none, which is what the vercel skills CLI accepts; when two skills share a name, `--skill` takes the first in listing order and `--except` leaves out all of them. An `--except` that names no skill of the source is exit code 5 with the same hint a bad `--skill` gets, since the run would otherwise install more than was asked for, and an `--except` that leaves nothing to install is exit code 1. The skills are installed in the order the source lists them, which is by subpath, whatever order the flags named them in, so two runs of one selection do the same things in the same order.

**What is read.** The commit's whole tree, the objects of the selected skills' trees the account repo does not hold yet and the upstream commit of every selected skill with its committer time are reads that do not depend on each other and run at once; each skill's own entries are taken out of that one listing rather than read again, so a run of thirty skills costs the reads of one. The upstream commit of each skill is the commit `git log -1 --no-renames <commit> -- :(literal)<subpath>` names for that skill alone, under git's default history simplification: a merge whose skill directory matches one of its parents' is not a change, and the history is followed down the first such parent to the commit that changed the directory, so a merge that brought an older change back onto a line that predates it names that change and not itself. The upstream commits of the whole run come out of one walk of the source's history, `git log --full-history --sparse --no-renames --diff-merges=first-parent --raw -t` from the source's commit over the selected subpaths, which git matches literally rather than as patterns: it prints every commit with its parents and what each subpath's entry becomes against the first parent, and agentx follows each subpath down that history as `git log -1` would, so the commit found for a skill does not depend on which other skills the run selected. A skill at the repository root is one more read, of that commit alone. The walk compares trees alone and never reads a blob, which the account repo does not hold. The blobs that are missing across the whole selection, which is every file but the `SKILL.md` a fetch brought, are fetched from the source's remote in one batch by object id, in the user environment, the way a listing fills a partial clone; a version whose blobs are all here already, which is how the same version installed twice looks, costs no network at all. That batch names objects and no ref, so it carries no `--refmap=`, which git refuses outright without a refspec on the same command line. A blob the batch did not bring is not reported as missing but kills the read that asks for it, the account repo being a partial clone, so the objects the run still does not hold are asked of `rev-list` and left out of a second read: a version whose files did not arrive costs its own skill and not the run. The files of every selected skill are then read in one `cat-file --batch` and each [content hash](#content-hash) is computed in process, over the frontmatter name and description and the files as the tree holds them: the version is never laid out on disk to be hashed. An entry that is neither a regular file nor a directory, a symlink or a submodule, is left out of the import with one warning naming it, since the import tree holds files alone; the content hash covers what was imported, so the library directory and the hash always agree. Every path of a selected skill's tree is checked before any of it is read or written, since the source's own bytes name where a file is laid out: an entry whose path is empty or absolute, holds a backslash or a NUL, or has an empty, `.`, `..` or `.git` component, the last in any case, refuses that skill with exit code 6 naming the entry, and nothing of it is written. git never checks such an entry out, but a fetch does not refuse one. The other skills of the source stay installable, and a listing leaves out a directory whose own path is such a path.

**The import commit.** One parentless commit per upstream version, written over the objects the source already put in the account repo. Its tree holds exactly one entry, a directory named after the upstream's own directory, the last segment of the subpath or the repository name for a skill at the root, and under it the skill's tree as the source stores it, with modes `100644` and `100755`; only the directories above an entry that had to be left out are written anew. Every entry name is the source's own bytes. A source is any repository a user adds, so a name that git's line-based formats would quote (one starting with a double quote, which git C-unquotes when it reads it back, or one holding a newline, which ends a record) is carried through unchanged: tree entries are read and written NUL-terminated, never one per line. The import tree of a version whose entries an import keeps therefore matches the source's tree name for name, and the [content hash](#content-hash) names the tree the commit holds. Its author and committer are `agentx <agentx@localhost>` and both dates are the upstream commit's committer time as epoch seconds with `+0000`. Its subject is `import <canonical URL>[/<subpath>] at <first 12 of the upstream commit> content <first 12 of the content hash>` and its trailers are `Agentx-Source`, the canonical URL, `Agentx-Path`, the subpath or `.` at the repository root, `Agentx-Upstream-Commit` and `Agentx-Content-Hash`. There are four trailers and no more: nothing about a machine, a fork or an account enters an import commit, so two machines that accept the same upstream version write the same commit id, whatever their time zone, git configuration, machine id or paths. A reader refuses a message whose `Agentx-Source` is not the canonical URL of a source, which is what tells a source from a plugin coordinate such as `<name>@<marketplace>`, whose path leaves the repository, whose commit is not an object id or whose hash is not a content hash. It refuses a message carrying a fifth `Agentx-` trailer as well, rather than ignoring the extra one: a message that carries anything else about a machine, a fork or an account was not written as an import commit, and reading it as one would credit a version to a commit that does not hold it. Nothing is written that this reader would not read back unchanged: the message an import commit is about to carry is read with that same reader first, whichever command writes it, and a version whose lineage it refuses, or hands back naming anything other than what was written, is refused instead of recorded. The two sides of an import commit are therefore one rule and not two that have to be kept in step. A trailer that is not agentx's, `Signed-off-by` among them, is ignored. Trailers are read from the last paragraph of the message alone, as git reads them, and a message of one paragraph has none; a fork's tip is read for lineage on every listing while its message is the user's own, so a body that quotes an `Agentx-Source` line is never read as lineage. Every commit of a run is written through one `git fast-import`, however many skills the run installs, each one pointing at a tree that is already in the object store: the trees are built first, one `git mktree -z --batch` per level of the deepest skill and one for the roots of all of them, every record NUL-terminated so that a name git would quote in a line-based format arrives as the source's own bytes, and the stream names the tree rather than the files, so nothing about how a run is batched can reach a commit id. One writer writes every commit, whatever the run installs, which is what makes a skill installed alone and the same skill installed among thirty end at the same id. Where `git commit-tree` accepts the same version it writes the same commit byte for byte, but it does not accept every one: it refuses `0 +0000` and any epoch that does not fit in 32 bits, both of which `fast-import` takes. An upstream committer time is refused here only when it is not a decimal integer git could have written, so what installs is what git can date. Until the mutation points the import branches at them, the commits are held by one staging ref each under `refs/agentx/importing/<run>/<n>`, a namespace of that run's own, so that the objects stay reachable while the journal is written and two runs never share a ref; the refs are deleted in one transaction when the run ends, and a run that is killed leaves them, holding nothing the account repo would not keep anyway.

**The library directory** is materialised under the skill's frontmatter `name`, falling back to the upstream directory name when it has none, which is the name `source skills` lists it under. A name agentx cannot hold as both a library directory and an import branch is exit code 6: renaming on install is not offered. That is a name that is empty, hidden or carries a separator, which no directory of the library can be, and a name git refuses as one level of a ref, which is one carrying a control character, a space or any of `~^:?*[\`, one holding `..` or `@{`, `@` by itself, or one ending in `.` or `.lock`. Both are checked before anything is written: the name comes out of the source's frontmatter, and a name only one of the two accepted would fail in the middle of the mutation, leaving a journal every later command would recover and fail on; the branch is refused here rather than on the `update-ref`, where the whole run's ref transaction would go with it. The content is built in a hidden directory beside it and read back as a scan would read it, and only a directory whose content hash is the version's is renamed into place. If the library already holds that name: the same content hash is adopted, which writes the import branch and copies nothing, and different content is exit code 6 with a hint to remove it or fork it. A dangling symlink into the agentx worktrees directory counts as absent. A library this machine cannot read or write is exit code 6 with a hint naming it and pointing at `agentx doctor`, whose `library` row says the same: unlike a placement, the library is not optional, since without it there is nothing to place.

**The import branch** `refs/heads/managed/<name>` is created with an expected old value of empty, every branch of a run in one `git update-ref --stdin` and so in one transaction, the updates wrapped in `start` and `commit`: a run writes all of its branches or none of them, and a stream that never reaches its `commit`, because the writer died part way through it, writes none rather than the prefix git had read. A branch already at this commit is the same version installed again and is left where it is; a branch at another commit is exit code 6, an install not being an update, and a name taken by a fork is exit code 6 too.

**Placements.** The explicit targets are every enabled configuration; `--to <configuration>` replaces them for that install, whatever their enabled state, and an id that names no detected configuration is exit code 5 with a hint listing the detected ones. Installing into the library exposes the skill to every client that reads the universal location whatever these choices are. A configuration whose client reads the library as one of its own skills directories, `reads_library` in a snapshot, is a universal client: the library entry is its placement and no symlink is made, since a second entry would make that client list the skill twice; the placement is recorded at the library path. A universal client sees every skill of the library, enabled or not and named by `--to` or not, and that is intended: the targets decide which other clients get a skill. So an install, and `skill place` after it, names every universal client detected on this machine, in the `universal` field of each `library_skill` event, at the end of the `result` and in the text below; a machine with none names none. For every other configuration a placement is a symlink at `<the client's own skills directory>/<name>` pointing at the library directory, and the directory is created when it does not exist. If the placement path already exists: a symlink naming the library directory, dangling or not, is already right and is left alone; a real directory whose content hash is this version's is replaced by a symlink and reported as adopted, its content retained until the outcome is verified; anything else is skipped with a warning naming the path, a symlink somewhere other than the library included however its target reads, since that is the user's link to the user's directory, and the `result` names how many placements were skipped. A placement this machine cannot make is skipped and counted the same way: a skills directory it cannot write, one on a read-only mount, one a platform privacy rule refuses, or a path that is not a directory at all. One client agentx cannot reach never costs the run the library directory, the import branch or any other placement. Whether the directory can hold the placement is settled before the journal is written, not when the step runs, so a client directory agentx cannot use leaves no mutation for a later command to trip over. `--copy` makes that install's placements copies of the library directory instead of symlinks, replacing a symlink that named the library, and records the skill and those configurations in `copy_mode` of the [machine settings](#machine-settings) in one write for the whole install. A real directory of this version at the placement path is adopted with `--copy` too, and reported as adopted: nothing is written and only `copy_mode` changes, but the directory becomes one a removal deletes, which the run has to say. A configuration `copy_mode` already records for the skill gets a copy whether or not `--copy` is given, from an install, `skill place` and `config enable --place-all` alike, so a placement never becomes a symlink while `copy_mode` still names it a copy; a copy of this version already at that placement path is left as the placement and is not reported as adopted, since agentx made it. A real directory there that does not hold this version is still that copy, the one a removal deletes, and is kept byte for byte and skipped, since replacing it would take what it holds with it; it is counted with the skipped placements and is a `warning:` of its own, two lines on stderr: `warning: <id>'s copy of <name> is different from the library, so it was left unchanged (<path>)`, then, indented by two spaces, `to replace it with the library version: agentx skill remove <name> --from <id> && agentx skill place <name> --to <id> --copy`. `<path>` is printed as every other warning prints a placement path. With `--json` it is one `log` event of level `warn`, whose message is the two lines joined by `; `: `<id>'s copy of <name> is different from the library, so it was left unchanged (<path>); to replace it with the library version: agentx skill remove <name> --from <id> && agentx skill place <name> --to <id> --copy`. The first `<name>` is the name, never quoted. In the two commands `<name>` is printed as it is when it is made of letters, digits and `._/:@%+=,#-` alone and does not start with `#`, and otherwise in single quotes, each `'` in it written `'\''`, as `import` prints the argument of the command it names, so that a POSIX shell reads it back as that one argument; a name that starts with `-` comes last in both commands, after the flags and `--`, as in `agentx skill remove --from <id> -- <name>` and `agentx skill place --to <id> --copy -- <name>`, since agentx would otherwise read it as a flag. Both lines are sanitised as [Streams](#streams) prescribes for every line on stderr, the quoted name included, so for a name holding a control character or a run of spaces the two commands are exact only in the message of the JSON `log` event. A `log` event carries no hint, so the way on is part of the message. The warning says only that the copy is different from the library, never how it came to differ: nothing records what a copy held when it was placed, so an edit of the copy and a change to the library directory since look the same. Following it gives the configuration the library's version as a copy again: the removal deletes the recorded copy, what it holds included, and takes the configuration out of `copy_mode`, and the placement with `--copy` records it there again, since `copy_mode` named it for a client that may not follow a symlink.

**The mutation.** The refs, the library directories, the placements and the one settings write are one journaled mutation under the exclusive lock, in that order, with every input read again under the lock and nothing live changed before the journal that describes all of it is on disk. A run of thirty skills is one bigger journal and not thirty journals, so an interrupted run is finished in one recovery rather than left between two of them. The refs of an install are applied first and together, which is why a run killed at that boundary is found with every branch written and no library directory made; the refs of a removal, which only delete, are applied last, so a removal killed at that boundary is found with a branch and nothing for it to name. See the [mutation journal](#mutation-journal). The lock is taken once before the network as well, to recover an unfinished journal and to refuse a run that could not write anyway; the fetch of the blobs runs outside it.

**A skill that cannot be installed** costs only itself: a run of several skills drops it with a `log` warning naming it and the reason, the rest of the run lands, and the `error` and `result` name every skill that failed and why. What is refused this way is a name the library or the account repo cannot hold, a directory the import commit cannot record, a skill directory with no regular file in it at all, an entry whose path would lay it out outside the skill's directory, a name a second skill of the same run also claims, a library directory that holds something else, a name taken by a fork or by another version, each exit code 6, and a file the source did not serve, exit code 5 with a hint to fetch the source again, as a listing of an incomplete source answers. Every refusal is decided before the run records a step for that skill, so a skill that fails leaves neither a branch nor a directory behind. The directory is refused on the rule the trailer reader keeps and before the version is read, as the name is: a subpath the reader would not read back as the directory it names is one carrying a C0 control character or `DEL`, which no trailer carries at all, and one opening or closing with whitespace, which a trailer hands back trimmed and so reads as another directory of that same source. A C1 control character is recorded and read back as it is. The directory is checked ahead of the entries under it, so a skill whose directory cannot be recorded is refused for that even when an entry below it would be refused too. The three coordinates agentx writes itself are held to the reader as well, on the whole message the commit would carry, and a version they fail is exit code 10 rather than a refusal: a canonical URL, an object id or a content hash that the reader does not take back is agentx's own bug and no fault of the version. Writing lineage anyway would install the skill with the lineage its import commit exists to provide already severed, silently: the listing would give it as `managed` with no `source`, no `subpath`, no `upstream_commit`, no `base_hash` and no `state`, or with a `subpath` naming a directory it did not come from, and no later update or revert could put either right. The exit code is the one every failure agrees on and exit code 6 when they disagree, the way exit code 3 answers for a fetch of several sources; one skill that failed in a run that installed nothing answers exactly as installing that one skill would. Anything that is not about one skill: an unreachable source, an unusable account repo, a name `--skill` or `--except` does not find, fails the whole run before it starts.

**After the install** the affected configurations are read again, a scan of the machine like any other, and the `library_skill` event reports the placements that rescan found in the configurations this install covered, rather than the ones it meant to make; `skill list` reports every placement of every library skill. That rescan, and the read of the library the report is built from, are made once for the whole run, whatever the number of skills it installed: reading the library content-hashes every directory it holds, work that grows with the library and not with the run, so a read per installed skill would cost a batch of n skills n passes over the whole library. The run emits the `source` event first, the one `source add` emits for a source the run added or fetched and the one `source skills` emits otherwise, so its `last_fetched` says how old the fetch the install read from is; then one `progress` per step per skill, `blobs`, `import` and `install`, then one for the `rescan`, then one `library_skill` event per skill it installed, in the order it installed them. `total` is `3 × <skills selected> + 1`, and a skill the run gives up on takes the steps it will no longer run out of it, so a run that ends emits a last event whose `current` is its `total`. The `result` of a run that installed everything it selected summarises what happened: `installed <name> from <url>[ under <subpath>] in <n> configurations` for one skill, `adopted` instead of `installed` when the library already held the version, `installed <name>, <name>, ... from <url> in <n> configurations` for several, with `, <n> already in the library` when some were adopted, what was made as a copy, adopted or skipped, then `, source fetched <last_fetched>`, and `; always available to universal clients: <ids, comma separated>` last, in the order of `universal`, when any universal client is detected; the list closes the line so that its commas cannot be read as those between the clauses. A run with a skill it could not install ends with `ok` `false` and the `error` message as its summary.

**Placing later.** `agentx skill place <name> --to <configuration>... [--copy]` adds a placement for a skill the library already holds. It is the placement half of an install on its own: the same targets, the same decisions about what is already at the path, the same journal steps and the same `copy_mode` write, so a placement made later is the placement the install would have made. `--to` is required, exit code 1 with a hint naming it, since placing a skill everywhere at once is what `config enable --place-all` does; an id that names no detected configuration is exit code 5 with a hint listing the detected ones, whatever its enabled state, since naming one is asking for it. A name the library does not hold as a skill is exit code 5 with a hint to list the library; a directory of the library with no `SKILL.md` is no skill of the library either and is left where it is. For a universal client the library entry is already the placement and nothing is made, as during an install. The command emits one `library_skill` event with the placements the rescan found in the configurations it covered and every universal client in `universal`, whatever `--to` named, and its `result` is `placed <name> in <n> configurations`, with `, <n> placements as copy`, `, <n> placements adopted` and `, <n> placements skipped` as an install reports them, then `; always available to universal clients: <ids, comma separated>` as an install ends its own.

**Removal.** `agentx skill remove <name> [--from <configuration>|universal]...` takes a skill out of the configurations `--from` names, or, with `--from universal` or no `--from`, off the machine: every placement, the library directory, the import branch, its candidate ref `refs/agentx/candidate/<name>` and its `copy_mode` entries, as one journaled mutation. A name the library does not hold as a skill is exit code 5, unless the account repo holds an import branch for it, `refs/heads/managed/<name>`, and no fork: that is a managed skill whose library directory was deleted, or left without its `SKILL.md`, outside agentx, which a listing warns about, see **Listing** below. Without `--from` or with `--from universal` its removal takes what is left of it off the machine, always, whatever the source holds by now: the import branch, deleted with the commit it was read at as its expected old value, its candidate ref, its `copy_mode` entries, and each placement by the rule every removal deletes by, a symlink naming the library directory, dangling now, or a recorded copy, anything else being left in place and named. A directory still at the library path is not the skill and is left too, with the `warning:` `<path> holds no skill and was left as it is; move it aside before installing <name> again`. The branch and the library path are read again under the lock, and a branch that moved, or a library that came to hold the skill meanwhile, is exit code 6 with nothing removed. `--from <configuration>` naming such a skill is exit code 6, `the library holds no skill directory for <name>, so it cannot be removed from <id> alone`, with the hint `take what is left of it off the machine with 'agentx skill remove <name>'`: with no library entry there is no skill for one configuration to keep while another loses it.

**`--from universal`** names the removal by what it does to the universal clients: they read the library entry itself, so removing the skill from them is removing that entry, which takes it from every client. It is the removal without `--from` and runs as that removal does, the refusal of a fork included, with the same output; everything said below of a removal without `--from` holds for it. Given more than once it is one request. Beside a configuration whose client is not universal it is exit code 1, as `--all` beside `--skill` is: the whole removal already takes every placement, so a configuration named beside it can only mean the removal was expected to do less than it does. Whether a client is universal is read from the machine, so this is decided once the library is found to hold the name and every other `--from` value names a detected configuration, a name the library does not hold or an id no detected configuration has being exit code 5 first. Beside a universal client, whatever else `--from` names, it is exit code 6, the refusal of the next paragraph, and not exit code 1, whose hint to drop `--from universal` would only lead to that refusal. `universal` is reserved: no configuration has that id, the registry leaving out the skills CLI's universal pseudo-agent.

**What a removal may delete.** A placement is deleted only when it is a symlink that names the library directory, dangling or not, or a real directory this machine recorded in `copy_mode` for that configuration. Anything else at a placement path – a directory the user made by hand, a symlink of theirs pointing somewhere else however it resolves, a directory holding exactly the library's version that nothing recorded as a copy, a regular file – is left exactly as it is, is one `warning:` line on stderr naming it and saying what it is, and is counted in the `result` as `<n> placements left in place`. The line for a symlink of the user's names what it points at and ends `<id> still sees it`, unless its chain of links, followed one link at a time, goes through a path the same removal deletes: the library entry when the skill comes off the machine, or a placement the removal deletes. Such a link stays but no longer leads to the skill, and the line ends `it no longer leads to <name>` instead. A placement path holding nothing is neither deleted nor left: there was nothing there. Leaving a placement alone does not fail the run, the way a skipped placement does not fail an install. A copy the settings record is deleted as asked even when its content is no longer the library's version, which is a `warning:` line of its own, worded like the one for a copy a placement leaves unchanged, so that what went does not go unsaid: `warning: <id>'s copy of <name> was different from the library; removing it deleted those changes (<path>)`, `<path>` printed as every other warning prints a placement path. With `--json` it is one `log` event of level `warn` whose message is that line without `warning: `. The line says only that the copy was different from the library, never how it came to differ, since nothing records whether the user edited the copy, replaced it with something else or had a directory of their own adopted there. Content the removal displaces is retained beside the live path and dropped only once every path holds its new state and it still hashes to what the journal captured, so an edit made while the removal ran is kept, see the [mutation journal](#mutation-journal).

**A universal-library occurrence cannot be removed for one client.** For a universal client, `reads_library` in a snapshot, there is no placement of its own to delete: the library entry is the occurrence, and taking it away takes the skill from every other client that sees it too. `--from` naming a universal client is exit code 6, whatever its enabled state and whatever other configurations `--from` names beside it, `universal` among them: the whole request is refused before the lock is taken, before any journal is written and before anything is deleted, so a run cannot half do what it cannot do at all and leaves nothing for a later command to recover. The message is `<id> reads the library directly, so <name> cannot be removed from it alone`, or `<id>, <id> read the library directly, so <name> cannot be removed from them alone` for several, naming the universal clients `--from` named in id order. The hint is `take <name> off the machine with 'agentx skill remove <name> --from universal', which removes it from <ids, comma separated>`, the ids being every detected configuration whose client sees the skill through a path that removal deletes, sorted by id: the library entry for a universal client, and for any client a symlink naming the library directory, or a copy recorded for the configuration whose skills directory holds it, in any user skills directory the client reads, its own or another client's, as Cursor reads Claude Code's, or a link of the user's there whose chain of links leads through the library entry or through such a symlink or copy: the removal leaves that link, since agentx did not make it, but it no longer leads to the skill. A directory of the user's that the removal would leave in place takes the skill from no one and is not counted, and neither is a link that reaches the skill's files without going through a path the removal deletes, such as a link straight to the directory a library entry that is itself a link names; a universal client with such a directory of its own is counted all the same, since it loses the library skill, and the removal warns about the directory that stays. For a name the account repo holds as a fork, `refs/heads/skills/<name>`, read without the lock, the hint offers no `--from universal`, since that removal refuses a fork: it is `<name> is a fork on this machine: every universal client sees it through the library entry until the fork itself is removed, which is not this command; take it from the other clients with 'agentx skill remove <name> --from <configuration>'`. With `--from universal` or without `--from` the universal clients stop seeing the skill because the library entry goes, and each is reported as a placement of mode `library`.

**What else a removal without `--from` takes.** The library directory, whatever kind of entry it is, and, when the account repo holds them, `refs/heads/managed/<name>` and `refs/agentx/candidate/<name>`, each deleted with the value it holds now, so a branch something else moved is refused rather than dropped. Those deletions are the last steps of the mutation, after the library directory and every placement, so a removal that cannot finish still has the skill's lineage to answer with. A name the account repo holds as a fork, `refs/heads/skills/<name>`, is exit code 6 before anything is planned: removing a fork is its own command, and its placements can still be taken away one configuration at a time with `--from <configuration>`, a universal client excepted, which sees the fork through the library entry until the fork itself is removed. The configurations a removal covers are the detected ones; a configuration that is no longer detected keeps whatever it holds.

**After a removal or a placement** the affected configurations are read again, a scan of the machine like any other, as after an install. `skill place` and `skill remove --from <configuration>` emit one `library_skill` event carrying the placements that rescan found in the configurations the command covered, which for a removal is what is left there: a client that reads another client's skills directory, as Cursor reads Claude Code's, may still see the skill by a path this command did not touch, and the event says so. A removal that took the skill off the machine emits no `library_skill` event, the library holding nothing to report, and fails with exit code 10 if the library still holds the name. With no event to correct it, that removal reports on its own claim instead: every configuration it covered that the rescan still finds a skill of that name in is one `warning:` line on stderr naming the configuration and the path it reads it at, since a client that reads the library loses only the library entry and a directory of its own under that name is one the removal never looks at. A placement the run already reported as left in place is not named a second time. Neither command emits `progress`: each does one thing once. The `result` of a removal is `removed <name> from the library, <n> placements and its import branch` when the skill left the machine and had one, `removed <name>, which the library no longer held: its import branch and <n> placements` when the library held no directory for it, `removed <name> from the library and <n> placements` when it had none, and `removed <name> from <the configurations it named, comma separated>: <n> placements` for a removal with `--from <configuration>`; `, <n> placements left in place` ends the line when any were. That count includes the library-mode placements of the clients that read the library, which lose the skill with the library entry.

**Comparing with the base.** `agentx skill diff <name>` shows how the library directory of a managed skill differs from its base version, the tree of the import commit its branch points at, as one unified diff per file, which git writes. The directory is read in process as git would record it, as `state` reads it, and one `state` reads as `current` costs no git beyond the lineage: the command emits no `diff` event and its `result` is `<name> matches its base version at <short upstream commit>`, which is said of that directory and of no other. Otherwise, unless the one difference is what git cannot record, the directory is written into the account repo as the tree it is: its blobs through one `git hash-object -w --no-filters --stdin-paths`, every path C-quoted so that a name holding a newline is one path, and a symlink's target written to a temporary file, since the blob of a link is the link itself; then its trees through one `git mktree -z --batch`, each tree after the ones below it. No index and no work tree is involved, so no ignore rule leaves a file out and no attribute, filter or line-ending rule changes a byte, and every id git answers with is held to the one computed in process: a file that changed between the two, or that was deleted or became something other than a file, is exit code 6 with a hint to run the command again. Nothing is written to the library; the objects stay in the account repo, where no ref holds them. git then compares the two trees in two reads run at once, `git diff-tree -r -z --no-renames --name-status` for the status of every file and `git diff-tree -r -p --no-renames --no-color` for the diffs, and the command emits one `diff` event per file, sorted by path, and a `result` of `<name> differs from its base version at <short upstream commit> in <n> files`. Every path is relative to the skill's directory: the import tree holds the skill under the upstream's own directory name, which is taken off, so a skill whose frontmatter name is not its upstream directory's, and one at the root of its repository, compare the same way. Renames are not looked for, a file moved being one deleted and one added, which is what happened to the paths an agent reads. What git cannot record, a `.git` component or a named pipe, is left out with one `warning:` per path naming it, and never reads as matching, as it never reads as `current`: the `result` then ends `, and <n> paths git cannot record` (`1 path`), or is `<name> differs from its base version at <short upstream commit> only in <n> paths git cannot record` when nothing else differs, a skill `skill list` reports as `modified` and `skill revert` refuses. A name the library does not hold as a skill is exit code 5; an unmanaged skill, a fork and a managed skill whose import branch carries no lineage agentx can read are exit code 6, none of them having a base version this command reads. Adoption offers no diff of its own: `skill diff` compares an adopted skill as it compares any other. Without `--json` the command prints the line its `result` holds, `<name> matches its base version at <short upstream commit>`, or `<name> differs from its base version at <short upstream commit> in <n> files`, or either line about the paths git cannot record, followed by every diff, printed as [Streams](#streams) prescribes for a diff, the name sanitised.

**Reverting.** `agentx skill revert <name>` puts the library directory of a managed skill back to its base version, discarding every edit made to it since, whatever tool made it: a file or a directory the base does not hold is deleted, and every file it holds is laid back with its mode. It is one journaled mutation under the exclusive lock, and the import branch does not move: the skill is `current` afterwards, and nothing leaves the machine. What it discards is what the directory held when the command began, captured first as the fingerprint a journal compares. The base version is then read out of the account repo outside the lock, one `ls-tree -r -t -z` of the import commit, whose upstream directory name is taken off every path, and one `cat-file --batch` of its blobs. Under the lock the import branch and the directory are read again: a branch that moved, or a directory that changed since it was captured, is exit code 6 and discards nothing, so an edit made meanwhile is never discarded with the rest. The base is laid out in a hidden directory beside the library directory and read back as git would record it, and only a directory whose tree is the base's is published. The journal holds a `ref` step whose old and new value are the import commit, which moves nothing and holds recovery to that version, then a `remove` of the library directory, which retains what it held, and a `publish` of the staged base, then those two steps for each copy the revert refreshes. agentx never locks out an editor or warns one; its own mutation guards instead: the `remove` step expects the captured fingerprint, and the content it retains is dropped only when it still hashes to it, so an edit made while the mutation runs is kept, see the [mutation journal](#mutation-journal). The copies `copy_mode` records for the skill are judged by what each holds now, as git would record it, since nothing records what a copy held when it was placed: a copy that already holds the base is left alone and says nothing; a copy that holds what the library directory held before the revert, which is what a placement made after the edit put there, is refreshed with the base through the same retaining `remove` and `publish`, its fingerprint checked again when the step runs; and a copy holding anything else was edited where it is and is kept byte for byte, counted as skipped and named with the warning for a kept copy under **Placements**. A copy this machine cannot read, or cannot stage a new copy beside, is left as it is and counted as skipped too, with `warning: cannot refresh <path>: <cause>; the copy was left as it is`. A path of a recorded configuration that holds no copy, nothing or a link, is left as it is, its drift saying what it is. A path two configurations share, as Zencoder and Zenflow share one skills directory, is judged once: a copy refreshed there counts for each configuration `copy_mode` records it for, and a copy kept or skipped there is one warning and one skipped placement. A library directory that holds its base version already is not touched and no mutation is made: the command still reads the machine again and emits the `library_skill` event, and the `result` is `<name> already matches its base version at <short upstream commit>; nothing was reverted`, which the text prints as it is, with no `✓`, since nothing changed. A directory holding something git cannot record, a `.git` component or a named pipe, is exit code 6 naming it: the revert would discard it with no record of it anywhere, so it is moved out of the skill first. The refusals of `skill diff` hold for the same names, with the same codes. After the mutation the machine is read again and the command emits one `library_skill` event carrying every placement of the skill, as `skill list` reports them, and a `result` of `reverted <name> to its base version at <short upstream commit>`, then `, <n> copy placements refreshed` and `, <n> placements skipped` when there were any. Without `--json` a revert that changed something prints `✓ ` and that line, the name sanitised.

**Listing.** `agentx skill list` runs a scan of the machine inside the command, reads every lineage branch in one `for-each-ref` over `refs/heads/managed/` and `refs/heads/skills/`, trailers and all, and emits one `library_skill` event per skill directory of the library, sorted by name. A directory of the library holding no `SKILL.md` is not a skill and is not listed, whatever the account repo holds for its name: a listing reports what the clients can see, and the same rule decides what a scan reports. A directory with no branch is unmanaged: it is listed with kind `unmanaged` and no upstream, and never updated or reverted. The other way round, a managed branch whose library directory is gone, deleted or left without its `SKILL.md` outside agentx, is not listed: there is no directory to compare with its base or to place, so it has no `state` and no `drift`, and no configuration is `missing` it. It is named instead in one `warning:` per skill on stderr, after the rows, `<name> is managed in the account repo but the library holds no skill directory for it; run 'agentx skill add <url> --skill <name>' to install it again, or 'agentx skill remove <name>' to stop managing it`, the URL the one its lineage records, or `<source>` for a branch that records none agentx can read, and both it and the name quoted for a shell as the warning for a kept copy quotes a name; with `--json` it is one `log` event of level `warn` with that message. A directory still at the library path, one left without its `SKILL.md`, is named in the warning instead, since an install refuses to write over it: `<name> is managed in the account repo but <path> holds no SKILL.md; move <path> aside, then run 'agentx skill add <url> --skill <name>' to install it again, or run 'agentx skill remove <name>' to stop managing it`. `skill add` lays out the version the branch records only while the source still holds it: it installs the version the source holds now, and refuses with exit code `6` while the branch names another, its hint naming `skill remove`. `skill remove` clears the warning whatever the source holds, see **Removal** above. The warning costs no git process of its own, the branches being those the listing read and the library path read from the filesystem, and a [snapshot](#snapshot) carries the same warning in `warnings`. Leaving the library is no [drift](#serve) transition. The `state` and the `drift` of every managed skill are read in process, its directory's tree and each configuration's own place, and cost no git process of their own: the tree of each import commit comes with the lineage, in the same `for-each-ref`. Lineage is read from the branches alone and never from the source refs under `refs/agentx/sources/`, so deleting every source ref between two invocations leaves the listing byte-identical, in text and in JSON. Whether a source is still added is another matter, read from the settings the listing reads anyway rather than from the account repo: a managed skill whose source has no settings entry is listed with `source removed` in `drift`, its coordinates as the lineage has them, and nothing is written for it, so removing a source changes the listing and adding it again gives back the listing from before. An account repo that does not exist is not created by a listing: every skill is then unmanaged.

**One row per configuration.** The text of `skill add`, `skill place` and `config enable --place-all` shows, for each skill, one row per configuration the command covered: the placement the rescan found at that configuration's own place, which is the library entry for a universal client and `<the client's own skills directory>/<name>` for any other. A path a client sees the skill through in another client's skills directory, as Cursor reads Claude Code's, is that other client's placement: it is that client's row when the command covered it, and never a second row of this one. A configuration the rescan finds with nothing of the skill at its own place, one whose placement `skill place` or `config enable --place-all` skipped for instance, gets one row per path it still sees the skill through instead, so that no client the command covered that sees the skill goes without a row. A copy kept for being different from the library leaves its configuration so: it does not hold the library's version, so the rescan does not find it as a placement of the skill and it has no row. The `library_skill` event is not narrowed this way: `--json` lists every path each client sees the skill through.

Without `--json`: `skill place` prints `✓ placed <name> in <n> configurations`, `<n>` counting the configurations placed into and not the rows, with `, <n> placements skipped` when some were, then one indented row per configuration it covered, as above, `<configuration>  <mode>  <path>`, a symlink ending in ` -> <library path>`, then `  adopted <path>, ...` when any placement was adopted, then `  always available to universal clients: <ids, comma separated>` when any universal client is detected, the name sanitised and every path quoted as [Streams](#streams) prescribes, since a library directory is named by whoever made it; `skill remove` prints `✓ removed <name> from <the library|the configurations it named, comma separated>: <n> placements`, `the library` for `--from universal` too, or `✓ removed <name>, which the library no longer held: <n> placements` for a skill whose library directory was gone, with `, <n> placements left in place` when some were, then one indented row per placement it deleted, `<configuration>  <mode>  <path>`, and, for a removal without `--from`, a last indented line `deleted <library path>` followed by ` and <import branch>` when there was one, or `deleted <import branch>` alone when the library held no directory for the skill, the name and the import branch sanitised and every path quoted as `skill place` prints them; `config enable --place-all` prints `✓ <id> is now enabled`, then `✓ placed <n> skills in <id>` with `, <n> placements skipped` when some were, then one indented row per skill, as above, `<name>  <mode>  <path>`, a symlink ending in ` -> <library path>`, the name sanitised and both paths quoted as [Streams](#streams) prescribes, since a library directory is named by whoever made it; for a configuration whose client reads the library it prints `✓ <id> reads the library and already sees <n> skills; nothing was placed` in place of that second line, the rows being the library entries it sees, and its `result` is `<id> is now enabled and already sees <n> skills through the library`. `skill add` prints what `source add` prints for a source the run added or fetched, then, for each skill it installed and in that order, `✓ installed <name> from <url>[ under <subpath>] at <short upstream commit>, source fetched <last_fetched>: <n> placements`, the name and the subpath sanitised since the source supplied both, a subpath that sanitising leaves empty being quoted as a path is so that the line still names a directory, `adopted` in place of `installed` when the library already held the version, `<n>` counting the rows below it, with `, <n> placements skipped` when some were, followed by one indented row per configuration it placed into, as above, `<configuration>  <mode>  <path>`, a symlink ending in ` -> <library path>`, then `  adopted <path>, ...` when any placement was adopted, then `  always available to universal clients: <ids, comma separated>` when any universal client is detected, every path quoted; a skill the run could not install is a `warning:` line on stderr naming it and the reason, and the `error:` line at the end names them all; `skill list` prints `<n> skills` and one indented row per skill, `<name>  <kind>  <state or ->  <upstream or (none)>  <n placements>`, `<n>` counting each configuration among the skill's placements once, however many paths it sees the skill through, as an install counts its rows, the state followed by `, <drift state>` for each drift state the skill is in, as in `modified, source removed`, rather than a column of its own that almost every row would leave empty, the name and the upstream sanitised as [Streams](#streams) prescribes, since a library directory is named by whoever made it and a subpath by the source, or `No skills in the library. Install one with agentx skill add <source>.`

## Adoption

`agentx adopt [--all] [--skill <name>]... [--base <commit|ref>]` takes over the skills another tool installed into the library, so that agentx knows which upstream version each one is at and can update and revert it. That tool is the vercel skills CLI, which installs into the same universal library and records what it installed in a lock file. agentx never writes that file, on any path, successful or not.

**The lock file.** It is read at `$XDG_STATE_HOME/skills/.skill-lock.json`, or at `$HOME/.local/state/skills/.skill-lock.json` when that variable is not set, and at `$HOME/.agents/.skill-lock.json`. Both are read and both may exist; the one that tool would write now – the XDG one when `XDG_STATE_HOME` is set, the `.agents` one when it is not – decides for a skill both name, and a disagreement between them is one warning naming both files. A file that is not there contributes nothing. A file that is not JSON, that holds no `skills` map, whose `skills` is not an object – `null` among them – or that is larger than 8 MiB is exit code 10 with a hint naming it, as an unreadable settings file is: a command asked to adopt what a file holds may not answer that it holds nothing. A `version` other than `3`, or none at all, is one warning and the entries are read anyway. The entries are a third party's and a user's to edit, so each is judged on its own and one bad entry never costs the others: an entry a file names twice says two things about one skill and is left out with a warning, and so is one that is not an object or that names no source, and for nothing else. A field of an entry written as something other than the text a lock file holds there is one warning naming that field, and the entry is read without it; no warning of a lock file names a type of agentx's own. `skillPath` names the skill's directory or its `SKILL.md`, written with the separator of whichever machine installed it; both are read back as one directory from the repository root, `""` at the root.

**Candidates.** One `adoption` event per entry whose library directory exists, sorted by name. An entry whose name the library cannot hold as a directory and the account repo cannot hold as a branch is left out with a warning before any path is built from it; an entry whose directory the library does not hold is no candidate at all, there being nothing on this machine to adopt. A candidate is refused, with its reason, when the library entry is not a real directory, a symlink included, when it holds no `SKILL.md`, when the name is a fork in the account repo, when the entry names a subpath that is not a directory of a repository – one that is absolute, that walks out of it, that carries a C0 control character or `DEL` or that opens or closes with whitespace, the last two being directories a repository may hold and the [import commit](#skills) cannot record on one line of a trailer – or when it names a source agentx cannot fetch: a `sourceType` other than `github`, `gitlab` or `git`, or a URL that is none of the forms `source add` accepts. A name the account repo already manages is reported as `managed` and left alone. The URL is read from the entry's `sourceUrl` first and its normalised `source` second, so that a URL agentx does not accept still leaves `owner/repo` to fall back on; a user or token in either is dropped before the URL is used anywhere and one warning says so, as it is for `source add`.

**Preview.** `agentx adopt` with no flag reports and writes nothing at all: it takes no lock, creates neither agentx home nor the account repo, makes no network call and leaves the lock file as it is. It reads the account repo's lineage branches when the repo exists, and reports a candidate whose source is not added yet with the reason that adopting adds and fetches it.

**The base version.** `--all` adopts every candidate, and `--skill <name>`, once for each, adopts the ones it names. What is recorded is the upstream version the skill was installed at, read out of the source itself; the library directory is not touched, so an edit made to it stays an edit against that version. The version is established one of three ways, tried as a cascade in the order below, each route handing on what it could not establish:

- the folder hash the entry recorded is the id of the tree the source holds at that subpath, at the source's fetched commit or at a commit behind it. Git's own content addressing is the verification, an id that names a tree naming that content and nothing else, and the search back through the history of that directory stops at 500 commits. The search follows first parents and matches the subpath literally, and it finds the newest commit of that line at which the directory holds that content, since the lock file names no commit: a version that reached the branch through a merge is found at the merge. The commit recorded is the one an install at the commit found records, the last commit reachable from it that touched the skill's directory, which holds the same version, so a merge that took the directory unchanged from one of its parents is followed to the commit that changed it. Two machines that fetched the source at two commits therefore record one commit for one version and write the same import commit for it, the one an install of that version writes. The search runs whether or not the source still holds that directory at the commit this machine fetched, an upstream-removed skill being precisely one whose version is behind the tip. A folder hash that names no version of this source (that tool's own digest of the folder, or a tree the source never held) establishes nothing and is handed on, exactly as an absent one is;
- the library directory holds exactly the version the source has at its fetched commit, which makes what is on disk an upstream version rather than an edit of one. It is the adoption an install makes for a library directory whose content hash is the version's, and the content hashes are the whole of the check: the folder hash of the lock file uses another algorithm and is comparable with nothing here. The commit recorded is the one an install at that fetched commit records, the last commit reachable from it that touched the skill's directory, which holds the same version;
- `--base <commit|ref>` names the version outright. It is exit code 1 without exactly one `--skill`, a base naming one version of one skill, and exit code 1 for a ref git would refuse. A commit id is read from the account repo, which holds the history of the source it fetched; a branch or a tag is resolved against the source itself in one `ls-remote` over the source's remote, since a fetch writes one ref per source and carries `--no-tags` and a repository's own names are therefore nowhere in the account repo. A name that is both a branch and a tag resolves to the tag and an annotated tag to the commit it peels to, which is git's own order. A name the source does not publish is exit code 5 with a hint saying what `--base` takes; one that is not in the history of the ref the source follows is exit code 6, whether it is an object another source put in the account repo or a ref of this source outside what was fetched: neither is a version of what this machine follows. The commit recorded is the last commit reachable from the one named that touched the skill's directory, which holds the same version, as an install of that commit records it. Whichever route established a version, the commit it records comes out of the reads an install makes, one history walk per source from the source's fetched commit for every skill the run adopts from it, and that walk gives the commit's committer time too. A directory no commit touched holds nothing at all, since every path a commit holds was added by one; whichever of these last two routes established its version, it refuses that skill alone with exit code 6, as a skill directory with no regular file does, and the rest of the run goes on.

**A version that cannot be established leaves the skill unmanaged.** Nothing is written for it, and the reason names every route that was tried and what each found, since the skill is left unmanaged because no route established a version and not because the first one missed. The hint names `--base`, which chooses the version, as the one explicit way on: `leave it unmanaged, or name the version it came from with 'agentx adopt --skill <name> --base <commit, branch or tag>'`. Adoption offers no diff and no fork of the directory. What the directory holds is never recorded as the version it came from, since an import commit holding an edit would be upstream content from then on and no later update or revert could tell the two apart.

**What a run writes.** A source the settings do not hold is added exactly as [`agentx source add`](#sources) adds it, at the ref the entry recorded as its pin: the remote, the fetch, the settings entry and the `source` event, which ends the `source removed` of every skill installed from it. The first entry of that source in name order gives the pin, since a machine holds one pin per source and it governs every later install from it, and entries of one source that record different refs are one warning naming them, the one taken and how to add the source at another. A source that cannot be added costs its own skills and no others. The version's files are then read out of the account repo and the blobs this machine does not hold yet are fetched in one batch per source, as an install reads a version it is about to import, and each [content hash](#content-hash) is computed in process. The [import commit](#skills) is the commit an install of that version writes, byte for byte, and `refs/heads/managed/<name>` is created with an expected old value of empty, every branch of a run in one transaction, as one journaled mutation. That mutation has no path step at all: adoption records where a skill came from and changes nothing on disk. Every input is read again under the lock, a base that only the directory established among them, so a directory edited between the two reads is refused rather than adopted at a version it no longer holds. A branch already at this commit is the same adoption again and is left where it is; a branch at another commit, and a name taken by a fork, are exit code 6.

**Events and exit codes.** One `progress` of phase `fetch` per source the run adds and one of phase `adopt` per skill it adopts, `total` being `<skills selected> + <sources to add>`, with a skill or a source the run gives up on taking its step out of it. Then one `adoption` event per entry the run covered, in name order. `adopt` emits no `library_skill` event and runs no scan, changing no placement; [`agentx skill list`](#skills) reports an adopted skill as managed afterwards, `modified` when the directory differs from its base. A run that adopted everything it selected exits 0; a run with skills it could not adopt takes the exit code every refusal agrees on and exit code 6 when they disagree, and one skill that failed in a run that adopted nothing answers exactly as adopting that one skill would, the way an install does. `--all` with `--skill` is exit code 1. A `--skill` that names no entry of the lock file is exit code 5 listing the names it holds, and one that names an entry whose directory the library does not hold is exit code 5 saying which of the two is missing.

`adoption`, emitted by `agentx adopt`, one per entry of the lock file whose library directory exists, sorted by `name`:

| Field | Type | Meaning |
|---|---|---|
| `name` | string | the library directory name, which is the entry's key in the lock file |
| `lock` | string | the lock file the entry was read from |
| `source` | string | the canonical URL of the source the entry names; absent when it names none agentx can use |
| `subpath` | string | the skill's directory in that source, `""` for its root; absent with `source` |
| `state` | string | `candidate` for an entry a preview could adopt, `adopted` for one this run adopted, `managed` for a name agentx already knows, `refused` for one that cannot be adopted |
| `upstream_commit` | string | the upstream commit of the base version: the last commit that touched the skill's directory, reachable from the commit the version was established at; absent when no base was established |
| `base_hash` | string | the content hash of the base version; absent with `upstream_commit` |
| `content_hash` | string | the content hash of what the library directory holds now, read again under the lock for an entry a run acted on; absent when the library no longer holds it as a directory |
| `modified` | boolean | whether the directory differs from the base version, decided by tree id as the `state` of a [`library_skill`](#event-types) is, so that `skill list` says the same afterwards; absent with `upstream_commit` |
| `reason` | string | why the entry was refused, or what an adoption would still have to do; absent when there is none |

Without `--json`: a preview prints `<n> skills of the vercel skills lock file in the library` and one indented row per entry, `<name>  <state>  <url>/<subpath> or (none)  <reason>`, the name, the subpath and the reason sanitised as [Streams](#streams) prescribes since the lock file supplied all three, followed by `Adopt them with agentx adopt --all.` when any can be. A run that adopts prints, per skill and in name order, `✓ adopted <name> from <url>[ under <subpath>] at <short commit>`, the name and the subpath sanitised as the preview sanitises them and a subpath that sanitising leaves empty quoted as `skill add` quotes one, and under it one indented `base <short content hash>: <how it was established>`, ending in `; the directory differs from it, so what differs is a local modification` when it does. A run with nothing left to do prints `Nothing left to adopt.`, and a machine whose lock file names nothing the library holds prints `No skill of the vercel skills lock file is in the library at <library>.`

## Export and import

`agentx export <file>` writes this machine's settings and one lineage record per branch of the account repo to `<file>` as one JSON document. `agentx import <file>` restores the settings of such a document, after confirming, and lists what the account repo of this machine can restore of the skills it records. `export` reads and writes that one file; `import` writes the settings file and nothing else. Nothing reads an export on its own: no command looks for one, there is no path a document is expected at, and an export left in agentx home is a file like any other.

**The document** is one JSON object, indented with two spaces and ending in a newline:

```json
{
  "schema_version": 1,
  "machine": { "id": "0123456789abcdef0123456789abcdef", "label": "my-laptop" },
  "settings": { "schema_version": 1, "label": "my-laptop", "...": "the machine settings file" },
  "skills": [
    {
      "name": "pdf",
      "kind": "managed",
      "commit": "<the commit refs/heads/managed/pdf points at>",
      "source": "https://github.com/example/skills",
      "subpath": "skills/pdf",
      "upstream_commit": "<the commit the version was read from>",
      "base_hash": "<the content hash of that version>",
      "placed": true
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `schema_version` | the document's own version, currently `1`. It is neither the settings schema version inside it nor the output schema version an event carries; a document of another version is refused |
| `machine.id` | the [machine id](#machine-identity) of the machine that exported |
| `machine.label` | its label as a command reports it: the setting, or the hostname while it is not set |
| `settings` | the [machine settings](#machine-settings) exactly as the settings file holds them, the label not filled in from the hostname, so that importing them does not give another machine this one's hostname |
| `skills` | one record per branch of the account repo, over `refs/heads/managed/` and `refs/heads/skills/`, sorted by name; its fields are those of the `import_skill` event above without `state`, `local_kind` and `local_commit` |

**What it never holds.** No snapshot, no tree, no blob, no file of any skill, and not the frontmatter name or description either: a record names a version, it never carries one. What restores content is the account repo, which holds it, and an install from the source, which fetches it, which is exactly why an import only lists. Nothing about the run reaches the document, no date and no order of its own, so two exports of an unchanged machine are byte-identical.

**Writing it.** `agentx export` reads the settings, then the branches in one `for-each-ref` over both namespaces as [`skill list`](#skills) does, and, only when there is a branch at all, runs a scan of the machine to decide `placed`; that boolean is all of the scan that reaches the document. The file is created readable by its owner alone, since it holds the machine settings, which never leave the machine except this way. A path that is already there is exit code 6 with a hint naming `--force`, which overwrites it; a path that names a directory is exit code 6 with a hint naming the path of a file, since `--force` cannot overwrite one; a path whose directory does not exist is exit code 5; any other failure to write is exit code 10. A branch of either namespace whose name the library cannot hold as a directory names no skill and is left out of the document, with one `warning:` line naming the ref: agentx makes no such branch, but the namespaces are shared with the account remote, and writing one into the document would write a record the reader below refuses, costing that reader the whole document over a branch that names no skill. An account repo that does not exist is not created for a listing: the document then lists no skill.

**Reading one.** `agentx import` reads the document whole and refuses anything it cannot restore before it takes the lock, so that a document agentx will not accept costs the settings on disk nothing at all. A file that is not there is exit code 5; any other failure to read it, a directory or an unreadable file, is exit code 6, and so is a file larger than 8 MiB, which is more than a machine's settings and lineage records come to and bounds every field of a document at once. Exit code 6, naming the file and the reason, is also what is given to a document that is not JSON, that is truncated, that carries anything after its one object, that carries no `schema_version` or one this agentx does not read, or that carries a field this agentx does not know – in the document or in its settings, since a field that was dropped silently would be a setting lost on restore. The settings it holds must be settings agentx would write itself, in every field and not only the ones a later command would notice: an import is the one route by which a string somebody else chose reaches the settings file, so a field nothing else in the CLI writes has this gate and no other in front of it. Their `schema_version` is the one this CLI writes; the label is one the label rule above accepts; `disabled_configurations` holds configuration ids, sorted, none of them twice; `copy_mode` maps skill names to configuration ids and is spelled as agentx spells it, which is an object sorted by key, each skill once and none of them with no configuration at all; and each source is one entry, the list sorted by `url` and no source in it twice, with `pin` a ref git accepts – the same check `source add <url>#<ref>` makes, since an import is equally a command that hands a ref of someone else's choosing to git – and `last_fetched` RFC 3339 in UTC. Both `url` and `alias` are URLs of a source and are held to the same rule: every source is stored by its canonical URL alone, a URL carrying a user or a token included, which reaches the settings by no route at all and may not reach them by this one, `alias` being the only field of the settings that no other command writes and so the only one an import can be the first to fill. Its records must be records a branch could carry: a name the library can hold as a directory and a branch can carry, no name twice, a kind that is `managed` or `fork`, a commit that is an object id, and lineage the trailer reader accepts, which is the reader of [the import commit](#skills) run over the message those four fields would make.

**Confirming.** An import replaces the machine settings, which are what only this machine decides, so it is never the default answer. `--yes` is how a caller says yes in advance. Without it, and only when the run is not in JSON mode and both stdin and stdout are terminals, the command asks on stdout, `Replace the settings in <settings path> with those of <label> from <file>? [y/N] `, and reads one line from stdin: `y` or `yes`, in any case and with any surrounding space, is a yes, and everything else is exit code 6 with the settings unchanged, an empty line and a stream that ends without one included. Where it cannot ask – in JSON mode, or with either stream not a terminal, which is every script and the desktop app – it refuses at once, exit code 6 with a hint naming `--yes`, rather than assuming the answer or waiting for input that will never come.

**What an import writes.** The settings file, whole, through the [mutation journal](#mutation-journal) as every settings write is, which bumps `version` like any mutation. Nothing else: no account repo is created, nothing is fetched, nothing is installed, nothing is placed and no library directory is written. The settings written are the document's, written as agentx writes settings, so a settings file agentx wrote round trips byte for byte; they replace what this machine had, sources, disabled configurations and copy modes and all.

**The events.** With `--json` an import emits the `settings` event with the settings it wrote, then one `import_skill` per record of the document in the order the document holds them, then `result`.

**The listing.** Every record of the document is compared with what this machine's account repo holds under that name, read exactly as `skill list` reads it and empty when there is no account repo. A record is `present` when the repo holds that name, in that namespace, at that commit; `missing` when the repo holds no branch of that name; and `different` when it holds one at another commit or in the other namespace, and what it holds is reported beside it. Nothing acts on the comparison: it is what tells the user which skills their account repo brings back on its own and which they have to install again. An account repo git cannot read is exit code 8 for either command, and for an import before anything is written: a machine whose repo is unusable is told so rather than given half an answer.

The `result` of an export is `exported the settings and <n> lineage records to <file>`; of an import, `imported the settings from <file>: <n> of <n> skills in the account repo, <n> missing, <n> at a different version`, or `imported the settings from <file>: the export lists no skills`.

Without `--json`: `export` prints `✓ exported the settings and <n> lineage records to <file>` and one indented line saying that the export holds no skill content; `import` prints `✓ imported the settings of <label> from <file>`, then `<n> skills in the export: <n> in the account repo, <n> missing, <n> at a different version` and one indented row per record, `<name>  <kind>  <state>  <upstream or (none)>`, or `No skills in the export.` when it lists none, then one indented line saying that only the settings were written, that each source is to be added again and that a missing skill is then installed with `agentx skill add <source>`, and under it one line per source of the settings, in their order and indented four spaces, `agentx source add <url>[#<pin>]`: an import restores the settings entry of a source and nothing of the source itself, so on the machine an import just made, a source has to be added again before a skill can be installed from it, and the line names the pin the settings hold because `source add` writes the pin its argument names, so the bare URL would unpin the source. These lines follow `No skills in the export.` too: a machine that added sources and installed nothing still has sources to add again. The argument is printed as it is when it is made of letters, digits and `._/:@%+=,#-` alone and does not start with `#`, and otherwise in single quotes, each `'` in it written `'\''`, so that a POSIX shell reads it back as that one argument: a URL and a pin agentx accepts may still hold `$`, `&`, `;` or a quote, and pasted bare such a line would run a command the document chose. Settings that hold no source have none to add again: the indented line then names `agentx skill add <source>` alone, and nothing follows `No skills in the export.` Every value a document supplies is sanitised before it is printed, and before it is quoted, as [Streams](#streams) prescribes for text agentx did not write.

## Serve

`agentx serve --json` is the long-running child the desktop app holds open. It scans once on start, emits that snapshot, then rescans when the machine changes and emits the snapshot again only when the inventory changed. It runs until its stdin closes or its context is cancelled, then emits `result` and exits 0. Without `--json` it prints one line per event: `snapshot <counter>: <n> configurations, <n> skills`, `refresh <request_id>: ok, snapshot <counter>`, `refresh <request_id>: failed: <error>` or `search <request_id>: <n> results` (`1 result`).

One serve child per agentx home: on start it takes an exclusive advisory `flock` on `serve.lock` in agentx home and holds it until it exits. A second `agentx serve` for the same home, `--once` included, exits at once with code 6 and a hint naming `serve.lock`. This lock is distinct from `lock`: serve never blocks a mutating command.

Snapshots: every serve process has a fresh `instance_id` (or `AGENTX_INSTANCE_ID`). The initial scan always emits a `snapshot` with `scan_counter` `1`, even when an earlier process saw identical content. Each later scan is compared with the last emitted snapshot on its serialised bytes with `instance_id` and `scan_counter` excluded; an identical snapshot emits nothing, a different one increments the counter and is emitted whole. The desktop applies snapshots only from its active child and only with increasing counters, as [snapshot ordering](snapshot-ordering.md) prescribes.

Drift: serve keeps the `library` of the last snapshot it emitted and, after every later snapshot it emits, never after the initial one, emits one `drift` event per library skill in both whose `state` or `drift` changed, in the library's order, after that snapshot and before any `refresh_complete`. A skill that arrived in the library or left it is no transition, the snapshot saying so itself: a managed skill whose library directory went is named in its `warnings`. A snapshot whose library could not be listed, the account repo being one git cannot read, carries no library entries and a warning saying so, so every skill leaves the library and comes back across it: no transition is emitted across it, and the comparison starts again from the next snapshot that lists the library. An edit made in an editor reaches serve through the change signals below, within their debounce, as every other change does: nothing watches a skill for drift on its own and nothing rescans on a timer. The event is a notification: the snapshot before it carries the skill as it now is, and is what the desktop applies. Without `--json` serve lists no library, so it emits no `drift`.

`drift`:

| Field | Type | Meaning |
|---|---|---|
| `instance_id` | string | this serve process's instance id |
| `scan_counter` | integer | the counter of the snapshot the change is in, which this event follows |
| `name` | string | the skill's library name |
| `kind` | string | its kind now, as the snapshot's `library` entry has it |
| `state` | string | its `state` now; absent when it has none, a skill that is not managed having none |
| `drift` | array of strings | its `drift` now, sorted; `[]` when it is in none |
| `previous_state` | string | its `state` in the snapshot before; absent when it had none |
| `previous_drift` | array of strings | its `drift` in the snapshot before, sorted; `[]` when it was in none |

Scans: every scan holds the shared `flock` on `lock` over its local reads, the lineage its snapshot's `library` carries included, like `agentx scan`, but waits for a mutation in progress for as long as it takes instead of giving up after a second; it takes the exclusive lock only to recover an unfinished [mutation journal](#mutation-journal). Scans are serialised, one at a time. A change signal that arrives during a scan schedules one more scan after it.

Change signals: serve watches, in this order, agentx home (where every mutating command rewrites `version` last), `account.git`, `worktrees`, the library and every user-scope skills directory a registered client reads, and then every directory below each of those trees, so an edit inside a skill is a signal too, wherever the scan reads that skill from. The skills directories come from the whole registry, not from the detected clients alone, so a client whose configuration appears while serve runs is covered by the sync that first sees its directory; a directory no detected client reads costs a rescan that finds the inventory unchanged and emits nothing. Directories are watched on their real paths after resolving symlinks, and a real path reached twice, as a library symlink to a fork worktree is, as the library itself is for every client that reads it directly, and as the Claude Code directory is for Cursor, is watched once. Hidden directories and `node_modules` are skipped, as in discovery. Before every rescan the watches are brought in line with the directories that exist then: one that appeared, or did not exist at start, is watched from then on and one that disappeared is not. How the watching is done depends on the platform. On macOS, built with cgo as the release binary is, one FSEvents stream covers every watched directory and everything below the trees, at no cost per file, plus every directory a symlink below a tree leads out of it, since FSEvents does not follow symlinks; a change is a signal when it happens in a directory the rules above cover. Everywhere else, and on macOS built without cgo, each directory gets its own non-recursive watch: one inotify watch on Linux, where a library of a few hundred skills and the client directories beside it stay within the default limit, and on macOS without cgo one kqueue descriptor per directory and per file in it, which meets the default limit of 256 open files early. A placement that is a symlink into the library resolves to a path already watched and costs nothing; a placement that is a copy is watched on its own. Events are debounced: a rescan runs 100 ms after the last event, or 500 ms after the first event of a burst, whichever comes first. Watching is a precondition of serve: when the watcher cannot be created, or a directory cannot be watched at start or later, serve ends with exit code 6 and an `error` event whose message names the directory and the cause, after any snapshot already emitted; the hint names the limit to raise. Serve never rescans on a timer.

Stdin carries requests, one JSON object per line: `refresh` and `search`. A line that is not a JSON object, a request without a known `type`, a refresh without a `request_id`, or a search without a `request_id` or without a `query` is answered with an `error` event with code `usage` on stdout, and serve keeps running; under serve an `error` event therefore does not announce the end of the run. Blank lines are ignored.

`{"type": "refresh", "request_id": "<unique id>"}` asks for a scan. A refresh is satisfied only by a scan that begins after the request was received; a scan already in progress cannot satisfy it, and every request received before the next scan begins shares that scan. After the scan, a changed snapshot is emitted first, then one `refresh_complete` per request.

`refresh_complete`:

| Field | Type | Meaning |
|---|---|---|
| `request_id` | string | the id from the request |
| `instance_id` | string | this serve process's instance id |
| `ok` | boolean | whether the scan succeeded |
| `scan_counter` | integer | the counter of the current snapshot, changed or not; absent when `ok` is `false`, since a failed scan claims no freshness |
| `error` | string | why the scan failed; present only when `ok` is `false` |

A failed rescan is also reported as a `log` warning; the last snapshot stays in force and serve keeps running. A failed initial scan ends serve with the error's exit code.

`{"type": "search", "request_id": "<unique id>", "query": "<text>"}` searches the skills of every source in [machine settings](#machine-settings), so that the app never filters a listing itself. It is answered with one `search` event:

| Field | Type | Meaning |
|---|---|---|
| `request_id` | string | the id from the request |
| `instance_id` | string | this serve process's instance id |
| `query` | string | the text from the request |
| `results` | array | one object per matching skill: `source`, `subpath`, `name`, `description` and `tree`; empty when nothing matched |

A skill matches when its name or its description contains the query, compared case-insensitively. Results are sorted by source canonical URL, then name, then subpath. `source` is the canonical URL rather than the source id that `source_skill` carries: a search spans every source, and the URL is what names one to a person and what an install takes. `subpath`, `name`, `description` and `tree` are the skill as `source skills` lists it, `subpath` being `""` for a skill at the repository root.

Serve answers from the source index it holds in memory: one skill list per source in the settings, built from that source's ref `refs/agentx/sources/<id>` in the account repo exactly as `agentx source skills` builds its listing, over the whole source rather than a subpath, since a subpath scopes one listing and is never stored. The index is built after the initial scan and rebuilt after every later one, each time after that scan's snapshot has gone out and before its `refresh_complete` events, so that a snapshot never waits for it. Building it reads the settings under the shared `lock`, as a scan does, and reads the sources and the commits their refs hold in one `for-each-ref`; a source still at the commit the last build read it at keeps that build's skills rather than being listed again, so when every source is, and none has gone or arrived, the index stands unchanged and nothing else runs, and rebuilding it after a rescan that follows a change elsewhere on the machine costs one git process, and none on a machine with no source. A source the last build could not list is listed again whatever its commit: that failure is the account repo's answer at that moment, not a property of the commit, so an index built while a source was momentarily unreadable recovers on the next build instead of holding that source empty until its ref moves. This is how a source added, fetched again or removed reaches the index: each of those is a mutation of agentx home, whose change signal schedules the scan, and a refresh acknowledged after it is answered from the new index. A source whose ref the account repo does not hold, and one it cannot list whole, contribute no skills and are one `log` warning per build.

A search takes no lock, runs no git process and makes no network call. It is answered from the index as it stands, while a scan is in progress, without waiting for it, so a search sent after a refresh can be answered before that refresh's `refresh_complete`.

`agentx serve --once` takes the serve lock, runs the initial scan, emits its snapshot and exits 0 with exactly the events `snapshot` and `result`. It watches nothing and reads no requests, and with no snapshot before its one it emits no `drift`.
